# Задания текстовых агентов

Ограничения изображений, различие CLI/API и внутренние бюджеты приложения — в [справочнике вложений](agent-image-limits.md).

Агент — внешняя программа (CLI), которую запускает Go-часть приложения в Linux и Windows. Менеджер заданий агента — `agents.Manager` из [internal/agents](../internal/agents/manager.go); он создаётся один раз при старте (`main.go`) и останавливается при закрытии окна. Настройки агента общие для проектов: `agents.SettingsStore` читает и пишет `settings.json` каталога состояния. Каждый запуск фиксирует исполнителя и модель: изменение настроек не переключает уже работающий процесс. Остальные длительные операции (инструменты, FFmpeg, отправки провайдерам) ведёт общий менеджер заданий [internal/jobs](../internal/jobs/manager.go) со своими идентификаторами `<вид>-<номер>` и журналами; записи агента он не читает.

## Провайдеры и адаптеры

Остальной код работает с агентом только через `agents.Manager` (интерфейс `agents.Runner` для потребителей) и реестр исполнителей, не проверяя, какой CLI выбран. Новый CLI подключается в этих местах:

- [frontend/src/shared/agent-providers.ts](../frontend/src/shared/agent-providers.ts) — запись реестра для интерфейса: название, имя исполняемого файла, команды входа и проверки, ссылки на инструкции и бюджет изображений проверки. Из реестра берутся варианты в настройках, подписи, уведомления и проверка истории; название — через `agentTitle(provider)`.
- [internal/agents/registry.go](../internal/agents/registry.go) — та же запись для Go (`agents.Providers`, порядок — `ProviderIDs`). `TestRegistryMatchesFrontend` сверяет её с TS-реестром.
- [internal/agents/check.go](../internal/agents/check.go) — проба `probes`: регулярное выражение версии, аргументы команды статуса и разбор её ответа. Поиск файла, запуск, тайм-ауты и общие ошибки остаются в `CheckAgent`.
- [internal/agents/adapters.go](../internal/agents/adapters.go) — адаптер `Adapter`: аргументы запуска для режимов `read` и `write`, разбор потока событий в общие `Update`, аккаунт и каталог моделей; `InputEncoder` — передача промпта и вложений через stdin. Адаптер создаётся `NewAdapterOptions` на каждый запуск. Режим, который CLI не поддерживает, адаптер отклоняет до запуска процесса.

Знак исполнителя добавляется в `AgentIcon` ([AgentIcon.tsx](../frontend/src/renderer/components/AgentIcon.tsx)). TS-таблицы реестра и знаков заданы как `Record` по исполнителю, поэтому пропуск там останавливает `yarn typecheck`. Go-карты проб и адаптеров компилятор не сверяет: пропуск обнаруживают тесты `internal/agents` (эталоны снимаются для каждого CLI).

Провайдер изображений с исполнителем-агентом относится к провайдерам медиа (`generation.image.provider`, реестр [media-providers.ts](../frontend/src/shared/media-providers.ts) и его Go-часть [internal/mediaproviders](../internal/mediaproviders/mediaproviders.go)): поле `executor` записи говорит, какую программу запускать, доступность проверяется её адаптером. Приложение запускает исполнителя отдельно от текстового агента, поэтому генерация доступна при любом выбранном агенте и без него. Контракт исполнителя — [internal/providers/agentexec](../internal/providers/agentexec/agentexec.go), подключение адаптеров — таблица в [internal/providers/providers.go](../internal/providers/providers.go). Особенности конкретного провайдера — в его документе ([список](../resources/providers/README.md)).

## Выбор агента и проверка доступа

Текстовым этапам нужен явно сохранённый агент. `SaveAgent` меняет только глобальный выбор (`null` — агент не выбран) и профиль выбранного CLI; `SaveProviderAgent` сохраняет личную модель каждого CLI, не выбирая его неявно. Значения по умолчанию разрешения не дают.

Перед запуском текстового этапа `agents.AccessChecker.RequireAccess` ([access.go](../internal/agents/access.go)) проверяет явный выбор, выполняет диагностику CLI, затем повторно сверяет выбор и отпечаток настроек: если за время диагностики агента отключили или заменили, запуск отклоняется. Тот же механизм отдаёт `window.api.ai.access` — выбор и доступность агента и провайдеров изображений и видео; агент и провайдеры медиа проверяются независимо.

## Поиск CLI и модели

Путь к CLI не настраивается. `CheckAgent` ищет файл с именем из реестра (`FindExecutable`, [command.go](../internal/agents/command.go)) в абсолютных каталогах `PATH`, затем в `~/.local/bin`, `/usr/local/bin`, `/usr/bin` и `/bin`; относительные записи `PATH` пропускаются. Вне Windows файл должен быть исполняемым для текущего пользователя. Найденный путь показывается в результате проверки. В Windows поиск идёт по `Path` (имя переменной без учёта регистра), `%USERPROFILE%\.local\bin` (нативная установка), `%APPDATA%\npm` (глобальная установка npm) и `%ProgramFiles%\nodejs`; в каждом каталоге сначала `<имя>.exe`, затем `<имя>.cmd`. Те же каталоги дописываются в `PATH` окружения запущенного CLI (`AgentEnvironment`): графическое приложение часто не наследует `PATH` терминала. CLI, установленный в другой каталог, нужно сделать доступным в одном из них, например ссылкой в `~/.local/bin`.

Проверка выполняет `<cli> --version` и команду статуса входа без shell, с пустым stdin, в домашнем каталоге, с тайм-аутом 10 секунд и пределом 32 КиБ на каждый поток вывода. Нераспознанная версия оставляет программу доступной, но не позволяет запустить рабочее задание. Отсутствие входа подтверждается только штатным ответом команды статуса; сбой команды или явная сетевая ошибка дают «неизвестно».

Поле «Модель» в настройках предлагает каталог `Adapter.Models` ([models.go](../internal/agents/models.go)), но допускает и ручной ввод: CLI может принять модель вне списка. Каталог читается при выборе исполнителя и после «Проверить» (`useAgentModels` страницы настроек). Codex отдаёт его через app-server `model/list` (все страницы видимых моделей), Claude — в ответе control protocol `initialize`, как `supportedModels()` в Agent SDK; формат Claude экспериментальный, поэтому нераспознанный ответ оставляет только ручной ввод. Псевдоним `default` Claude не показывается: он совпадает с пустым полем. Служебные вызовы не создают ход модели.

## Назначение и права

Текстовый агент готовит предложение. Промпт и необязательный контекст передаются через stdin; в аргументах находятся настройки CLI. `cwd` — выбранная папка проекта, режим разрешений — чтение. Shell для запуска не используется: команду строит `AgentCommand`, запускает общий [internal/process](../internal/process/process.go). Windows запускает `.cmd` только через интерпретатор команд с другими правилами разбора аргументов, поэтому обёртка npm (`.cmd`/`.bat`) разворачивается в прямой вызов её цели: скрипт — через `node.exe` рядом с обёрткой или из `Path`, программа `.exe`/`.com` — как есть; непонятная обёртка остаётся без изменений и даёт штатную ошибку запуска. В Windows дочерние программы запускаются с `CREATE_NO_WINDOW`, без окна консоли (`process.Prepare`). Отдельная подсистема изоляции и изменение настроек ОС не нужны.

Менеджер ставит перед задачей штатный префикс режима: для предложений — не изменять файлы проекта, не выполнять commit/push, не удалять исходники и не отправлять платные запросы. Сценарные, производственные предложения и разбор видео применяются отдельными доменными действиями после просмотра: [internal/scenarioworkflow](../internal/scenarioworkflow/workflow.go), [internal/productionworkflow](../internal/productionworkflow/workflow.go), [internal/videoreview](../internal/videoreview/review.go). Агент возвращает JSON по контракту промпта; проверки и Apply выполняет приложение.

### Промпты

Тексты промптов режима предложения встроены в бинарник из [resources/skills](../resources/skills/README.md) (`resources.Skill`, `resources.SkillFile`): `ai-clip-scenario` — сценарный проход, `ai-clip-scene` с `references/` — производство, `ai-clip-video-review` — проверка видео. В промпт производства добавляется раздел «Указания агенту» документов провайдеров, выбранных в проекте (`providers.Guide`, документы в [resources/providers](../resources/providers/README.md)). Правка этих файлов меняет промпт агента; байты промптов сверяют эталоны в [testdata/golden](../testdata/golden/README.md).

### Постоянные инструкции проекта

Постоянные инструкции текстовому агенту принадлежат проекту: необязательная строка `agent_instructions` в `plan/project.json` ([internal/projectfile](../internal/projectfile/projectfile.go)). Настройки проекта сохраняют её дословно, без обрезки пробелов и изменения переносов; отсутствие поля и пустая строка оставляют штатный промпт, значение другого типа — ошибка чтения. При редактировании нетронутые части сохраняют исходные CRLF, CR или LF; новые переводы строк записываются как LF (`instructionText.ts`). Редактор ([ProjectAgentInstructions.tsx](../frontend/src/renderer/pages/ProjectPage/components/ProjectAgentInstructions.tsx)) изначально доступен только для чтения; выбранный агент позволяет запросить разблокировку через подтверждение. Сохранение, сброс правок, смена проекта или выбранного агента вновь блокируют поле.

Каждый `Manager.Start` читает снимок инструкций из папки самого задания до асинхронной проверки CLI. Менеджер добавляет один блок между штатным префиксом и задачей; доменные процессы не вставляют его сами. Каждый явный повтор и доработка заново получают сохранённые инструкции своего проекта. Переключение открытого клипа и редактирование настроек после начала задания не меняют его снимок. `StartImages` использует независимого исполнителя медиапровайдера и этот блок не получает.

### Аргументы CLI

Claude запускается с `-p --input-format text --output-format stream-json --verbose --include-partial-messages --permission-mode dontAsk --tools Read,Glob,Grep --allowedTools Read,Glob,Grep`; с вложениями изображений `--input-format` становится `stream-json`. Codex запускается с `-a never exec --json --sandbox read-only --skip-git-repo-check --color never -`, вложения добавляются повторяемыми `--image <путь>` перед `-`. Непустая модель передаётся `--model`; пустая использует настройки самого CLI. Поддерживается стабильный контракт Claude 2.1.0 и новее в рамках 2.x и Codex 0.159.0 и новее в рамках 0.x; версия должна иметь строгий вид `X.Y.Z`, поэтому другая основная версия и prerelease отклоняются кодом `UNSUPPORTED_VERSION` с предложением обновить агента. Параметры запуска описаны в [документации Claude](https://code.claude.com/docs/en/headless) и [Codex](https://learn.chatgpt.com/docs/non-interactive-mode).

### Задания изображений

Внутренний маршрут `Manager.StartImages` запускает адаптер исполнителя в режиме `write`; адаптер, не поддерживающий этот режим, отклоняет его до запуска процесса (так поступает адаптер Claude). Codex в этом режиме получает `--sandbox workspace-write`. Рабочая папка `cwd` обязана лежать внутри `<каталог состояния>/image-jobs/` (проверяется по реальному пути): производство создаёт `image-jobs/<UUID>`, кладёт туда закреплённые копии референсов только для чтения и `job.json` со связью задания и согласованного SHA запроса ([keyframes.go](../internal/productionworkflow/keyframes.go)); исполнитель создаёт в ней только кандидатов опор. Вложения изображений в этом режиме запрещены. Модель исполнителя берётся из `generation.image.model` проекта (`agents.ImageAgent`); пустое значение оставляет выбор настройкам самой программы. Текстовый агент и его модель при этом не меняются.

Отдельного метода `startImages` в `window.api` нет: маршрут вызывается предметным `productionWorkflow.generateFrames` (`ProductionWorkflowService.GenerateFrames`). Обложка и референсы проекта ([internal/covergen](../internal/covergen/session.go), входы — [internal/referenceimage](../internal/referenceimage/inputs.go)) запускают собственный экземпляр менеджера во временной папке сессии, поэтому их задания не попадают в общую историю.

### Чего менеджер не делает

Это обычные режимы разрешений доверенного пользовательского CLI. Приложение не добавляет флаги обхода разрешений. Настройки, hooks и внешние интеграции установленного пользователем CLI остаются его ответственностью; собственную систему управления ими приложение не создаёт. Изменение файлов проекта по результату предложения относится к отдельному согласованию и в общий `agents.start` не входит. Платная отправка провайдеру генерации, удаление исходников и оригиналов, commit/push этим менеджером не выполняются.

## Аккаунт и лимиты

`Adapter.Account` ([account.go](../internal/agents/account.go)) читает сведения выбранного CLI отдельно от рабочих заданий. Настройки вызывают его после загрузки профиля, при смене исполнителя и по кнопке «Обновить»; смена модели не запускает новое чтение. Ответ прежнего исполнителя не показывается после переключения. Снимок существует только в памяти страницы: email, организация и лимиты не попадают в `settings.json`, историю заданий или журнал. Служебная сессия ограничена 10 секундами и 128 КиБ суммарного вывода; после ответа stdin закрывается, и программа, не вышедшая сама за 150 мс, завершается вместе с потомками.

Claude использует [`claude auth status --json`](https://code.claude.com/docs/en/cli-reference): email, `orgName`/`orgId`, `authMethod`, `subscriptionType`. Для Claude 2.1.273+ доступно отдельное короткое соединение control protocol в изолированном режиме (без инструментов, MCP, hooks и пользовательских настроек, без сохранения сеанса): `initialize` → `get_usage` с `skip_behaviors=true`. Оно вызывается только при входе в подписку (`authMethod` `claude.ai` или `oauth_token`, `apiProvider: firstParty`, без `apiKeySource`); при API key, `apiKeyHelper`, внешнем провайдере или неизвестном способе входа лимиты подписки не запрашиваются, чтобы не показать лимиты сохранённого личного аккаунта вместо рабочего способа списания. Тариф остаётся из `auth status`. Метод объявлен экспериментальным в [официальном Agent SDK](https://github.com/anthropics/claude-agent-sdk-typescript/blob/main/CHANGELOG.md), поэтому неподдерживаемый или изменившийся ответ оставляет показатели неизвестными. Пользовательские сообщения и обращения к модели не отправляются, анализ истории за семь дней отключён. Считываются только отчётные окна использования и время сброса.

Codex использует [штатный app-server](https://learn.chatgpt.com/docs/app-server) (`app-server --listen stdio://`): инициализацию, затем `account/read` с `refreshToken=false` и `account/rateLimits/read`; сбой одного запроса не отменяет другой. Диалоги и ходы модели не создаются. Для аккаунта ChatGPT читаются email и `planType`; способы API key и Amazon Bedrock показываются отдельно. Явный ответ сервера об отсутствии аккаунта (`requiresOpenaiAuth`) важнее локального статуса входа. При наличии `rateLimitsByLimitId` отображаются его окна (даже пустая карта не заменяется прежним `rateLimits`), иначе используется `rateLimits`. Проценты означают уже использованную долю; время сброса — Unix seconds. Нулевое использование и нулевой остаток сохраняют значение нуля. Сведения о кредитах и `ordinaryUsageAllowed` показываются, если сервер их сообщил.

Каждый неподтверждённый показатель отображается как «Не удалось уточнить». Эти интерфейсы не сообщают платёжный статус и дату окончания подписки: успешный вход, название тарифа и исчерпанное окно не превращаются в сообщение «подписка оплачена» или «подписка закончилась». Организация не выводится из домена email или названия тарифа. Сырой ответ CLI и секреты в renderer не передаются.

## Контракт API и события

Контракт задан в [frontend/src/shared/agents.ts](../frontend/src/shared/agents.ts) и [frontend/src/shared/api.ts](../frontend/src/shared/api.ts). Методы отображаются адаптером [frontend/src/platform/api.ts](../frontend/src/platform/api.ts) на сгенерированные bindings Wails-сервиса `AgentsService` ([internal/app/agents.go](../internal/app/agents.go)); Go-типы — `agents.Job`, `agents.Event`, `agents.CheckResult` и др.

| Метод `window.api.agents` | Назначение |
| --- | --- |
| `getSettings()` / `saveSettings(config)` | Выбранный текстовый агент; сохранение также обновляет его профиль |
| `getProviderSettings(provider)` / `saveProviderSettings(config)` | Независимая модель каждого CLI |
| `check(config)` | Проверка показанной конфигурации без сохранения |
| `account(config)` | Текущий аккаунт и доступные лимиты CLI без генерации и записи сведений в историю |
| `models(config)` | Каталог моделей найденного CLI служебным вызовом; при недоступном каталоге — пустой список с сообщением |
| `start({ project, task, prompt, context?, retryOf? })` | Новый явный запуск с сохранённой конфигурацией после `RequireAccess`; сразу возвращает запись `running` |
| `cancel(id)` | Останавливает дерево процессов CLI и возвращает итоговую запись |
| `get(id)` | Снимок записи или `null` |
| `list(project?)` | История от новых записей к старым |
| `onEvent(listener)` | Подписка, возвращающая функцию отключения |

Отказ `start` приходит текстом «[КОД] причина». События менеджер публикует подписчикам вне блокировки строго по порядку, а `ConfigureAgentEvents` передаёт их в renderer событием Wails `agents:event`. Виды событий: `started`, `text_delta`, `tool_started`, `tool_finished`, `completed`, `failed`. У события есть `jobId`, `project`, `sequence`, `phase`. Начало и итог содержат снимок `job`; текстовые события передают приращение `text`, события инструмента — его название без аргументов и результата чтения файлов. Остановка и прерывание передаются как `failed` с точным статусом в снимке задания.

Подписывайтесь до вызова `list`. До получения списка буферизуйте события; после ответа применяйте только события с номером больше `job.sequence`. Так событие, уже попавшее в снимок, не продублирует текст, а поздний снимок не откатит результат. Так устроены общий hook `useAgentJobs` и `applyAgentEvent` ([agentEvents.ts](../frontend/src/renderer/hooks/agentEvents.ts)), которыми пользуются страницы «Сценарий», «Производство» и журнал заданий. Настройки изображений и видео задаются независимо в проекте, отдельно от текстового агента.

## Уведомления

Системные уведомления ОС приложение пока не отправляет. Готова только граница перехода: `NativeService.RouteNotification` ([native.go](../internal/app/native.go)) принимает адрес проекта и страницы, фокусирует основное окно и передаёт renderer событие `notifications:open`.

Внутри окна общий наблюдатель renderer ([state.tsx](../frontend/src/renderer/state.tsx), правила — [backgroundJobs.ts](../frontend/src/renderer/hooks/backgroundJobs.ts)) раз в три секунды читает список заданий и сообщает об итоге задания агента, если пользователь не на странице-владельце («Сценарий» для `ai-clip-scenario`, иначе «Производство»): успех, остановку или ошибку. Сообщение об успехе означает завершение ответа: предложение ещё требуется проверить и согласовать.

## История и повтор

Запись `<каталог состояния>/jobs/agent-<UUID>.json` ([history.go](../internal/agents/history.go)) содержит `schemaVersion`, идентификатор, номер события, проект, задачу, исполнителя, модель, источник повтора, режим `read-only` или `workspace-write` для внутреннего задания опор, хеши промпта и контекста (с вложениями — их байтов и порядка), состояние, фазу, времена, код завершения, результат, служебный журнал, версию CLI, session id и диагностику. Формат и порядок полей фиксирует эталон `agents-cli`. Файлы общего менеджера заданий `<вид>-<номер>.json` лежат в том же каталоге и с ней не пересекаются. Запись атомарная; промежуточное состояние сохраняется с задержкой до 250 мс, итог — сразу.

Промпт, дополнительный контекст, сырые события и stderr не записываются. Журнал содержит только действия менеджера и краткие причины ошибок. Сообщение о сбое дополняется текстом причины от агента («Сообщение агента: «…»»): из `turn.failed` Codex или результата Claude, без секретов, в одну строку, не длиннее 400 символов; stderr только классифицирует сбой. События Codex `error` и элементы `item.type: "error"` — нефатальные уведомления (переподключение потока, предупреждение): они пишутся в журнал строкой «Агент сообщил: …» и не обрывают задание. Фатальны `turn.failed` и ненулевой код выхода; если ход закончился без результата, причиной служит последнее уведомление. Результатом Codex служит последнее завершённое `agent_message`, поэтому промежуточный комментарий не приклеивается к финальному JSON. Результат предложения хранится отдельно от журнала; распознаваемые ключи и токены в результате, задаче и журнале маскируются (`Redact`).

Пределы ([manager.go](../internal/agents/manager.go), [protocol.go](../internal/agents/protocol.go)): до 256 КиБ промпта и 256 КиБ дополнительного контекста, задача до 120 символов, до 256 КиБ на строку JSONL и на результат, 8 МиБ суммарного stdout/stderr, 12 тысяч символов служебного журнала. Время рабочего процесса ограничено 20 минутами. Renderer не может изменить эти пределы.

При старте приложения сохранённое `running` становится `interrupted`, никогда `completed`. История не удаляется. Нераспознаваемая или повреждённая запись (в том числе больше 1 МиБ) остаётся на диске, её путь пишется в журнал приложения; остальные задания продолжают читаться.

Ни повтор, ни resume автоматически не выполняются. Session id сохраняется для диагностики, но сам по себе не доказывает совместимость возобновления. У прерванного, ошибочного или остановленного задания есть явное действие повтора. В общем интерфейсе истории оно открывает новый запрос ([AgentRetryDialog.tsx](../frontend/src/renderer/components/AgentRetryDialog.tsx)); на предметной странице повтор снова подготавливает соответствующий этап по актуальным входам. Используются текущие настройки агента; прежняя запись сохраняется. Вызывающий код передаёт `retryOf`; задание другого проекта (по реальному пути) и ещё выполняющееся задание нельзя указать источником повтора. Агентный повтор не восстанавливает платную отправку провайдеру. Для уже отправленного запроса отдельный `production.resume` получает существующий ID без новой генерации; неизвестный исход требует установить ID, а не повторять отправку.

Один проект резервируется на всё время задания, начиная с диагностики; занятость сравнивается по реальному пути, поэтому путь через symlink тоже получает `PROJECT_BUSY`. Разные проекты могут иметь независимые задания. Отмена, тайм-аут и закрытие приложения завершают всё дерево процессов CLI через `process.KillTree`: в Linux — собственную группу процессов (`SIGKILL`), в Windows — `taskkill /T /F` по pid запущенного процесса из `%SystemRoot%\System32`; поиск и остановка чужих процессов по имени не используются. При закрытии `ShutdownAndWait` запрещает новые задания, прерывает текущие и ждёт фактического выхода CLI. Аварийное завершение приложения (`kill -9`, сбой) тоже не оставляет CLI работать сиротой и тратить лимит подписки: в Linux запущенная программа получает `SIGKILL` по смерти приложения (`Pdeathsig`), в Windows её завершает объект задания приложения с `KILL_ON_JOB_CLOSE`. Привязка касается прямого потомка (в Windows — и всех, кого он запустит); история заданий после такого завершения по-прежнему показывает задание прерванным.

## Коды диагностики

| Код | Значение |
| --- | --- |
| `INVALID_INPUT` | Нет проекта, агента, обязательного текста либо параметры недопустимы |
| `PROJECT_BUSY` | Для этого проекта уже есть незавершённый запуск |
| `CLI_NOT_FOUND` / `CLI_UNAVAILABLE` | CLI отсутствует или не запускается |
| `AUTH_REQUIRED` / `AUTH_UNKNOWN` | Вход отсутствует либо его нельзя подтвердить |
| `UNSUPPORTED_VERSION` | Версия не распознана или находится вне проверяемого контракта адаптера |
| `PROTOCOL_ERROR` | Некорректный JSONL или выход без завершающего события |
| `OUTPUT_LIMIT` | Превышен размер вывода, строки или результата |
| `TIMEOUT` | Рабочий процесс не завершился вовремя |
| `RATE_LIMIT` | Провайдер сообщил о лимите использования |
| `CLI_ERROR` | Ошибка рабочего запуска, ответа или сохранения состояния |
| `CANCELLED` / `INTERRUPTED` | Явная остановка либо завершение приложения/перезапуск |

Код `0` без финального события не считается успехом; финальное событие при ненулевом коде также не означает успех. Неизвестные служебные события пропускаются для совместимости, а сломанные JSON-строки останавливают задание. Отсутствие входа и лимит определяются по тексту ответа агента и stderr; произвольный ненулевой код выхода не превращается автоматически в отсутствие входа.

## Проверка

Тесты не вызывают настоящие CLI и сеть. Вместо агента запускается поддельный CLI — тестовый бинарник `internal/agents` с `SONGFRAME_FAKE_AGENT=1` ([fake_test.go](../internal/agents/fake_test.go)); `TestMain` подменяет `HOME`, `USERPROFILE` и `PATH`, чтобы установленные агенты не находились.

- `go test ./internal/agents` — эталоны `agents-protocol`, `agents-settings` и `agents-cli` ([описание](../testdata/golden/README.md)): аргументы, stdin, разбор потока обоих CLI, маскировка, настройки, диагностика, аккаунт, каталог моделей, задания и байты файлов истории. `manager_test.go` проверяет отмену дерева процессов, тайм-аут и предел вывода, восстановление после перезапуска, занятость проекта и повтор, пределы вложений и доставку событий. `command_test.go` эмулирует Windows в Linux: поиск `.exe` и `.cmd`, переменную `Path`, разворот обёртки npm. `registry_test.go` сверяет реестр и тексты с renderer.
- `go test ./internal/process` — запуск без shell, пределы, тайм-аут, завершение потомков и программа, пережившая аварийное завершение родителя (`TestChildDiesWithKilledParent`). `process_windows_test.go` (отсутствие консоли, `taskkill`) компилируется и выполняется только в Windows; в Linux-прогоне его нет.
- Маршрут изображений проверяют `internal/providers/codex`, `internal/productionworkflow` (эталоны `production-frames`) и `internal/covergen`, проверку видео — `internal/videoreview`; вместо настоящей программы-агента там подставной исполнитель (в эталонах производства и обложки — тестовый провайдер `test-agent`).
- В `frontend/`: `yarn test src/renderer/hooks/agentEvents.test.ts src/renderer/pages/ProjectPage/components/instructionEditor.test.ts src/renderer/pages/ProjectPage/components/instructionText.test.ts src/platform/agents-api.test.ts` — гонка снимка с событиями, редактор инструкций и отображение методов на bindings.

Подставные CLI не создают настоящие изображения и не отправляют платные запросы. Наличие CLI и вход проверяются в «Настройках», каталог моделей и параметров медиапровайдера — на странице «Проект». Доступ конкретного аккаунта к генерации и встроенному инструменту изображений подтверждается отдельно, при явно согласованном реальном запуске.

Нативно в Windows приложение не проверялось: эмуляция в Linux и сборка установщика не подтверждают поиск CLI, разворот обёрток npm, запуск без консоли и завершение дерева процессов в настоящей Windows.
