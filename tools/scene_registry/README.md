# scene_registry

Читает `plan/scenes.json`, проверяет кадровую шкалу и вычисляет сюжетное наследование состояния. Использовать перед описанием и генерацией кадров, при изменении событий и при продолжении отложенного запроса. Реестр не изменяет, изображений не создаёт, к сервисам не обращается.

```sh
python3 -B tools/scene_registry/scene_registry.py M37
python3 -B tools/scene_registry/scene_registry.py M37 --phase before
python3 -B tools/scene_registry/scene_registry.py M37 --phase after
```

Без `--phase` выводит обе границы. JSON содержит действие, камеру, референсы, непрерывность, источник и локальные изменения состояния, вычисленное состояние и `scene_sha256` текущей подготовки. Общий сценарий и дизайн — по [карте навигации](../../templates/project/README.md#источники-сведений).

## Данные проекта

`load_project(root)` читает [plan/project.json](../../templates/project/plan/project.json), `validate_project(data)` проверяет уже прочитанный объект, в том числе из снимка Git. Поля: `schema_version: 1`, непустое `name` и `animatic_video` — имя MP4 без пути к папке. Название идёт в документы, карточки, плеер и метаданные, имя файла — в сборку и ссылки плеера; подставного названия при отсутствии данных нет.

Необязательный для просмотра блок `generation` содержит независимые `video` и `image`. `generation_settings(data, kind='video')` возвращает копию настроек выбранного медиа и проверяет только их; `validate_project(data)` проверяет каждый представленный блок. У видео обязательны `provider` (id провайдера генерации), непустая строка `resolution` (например, `1080p`), `aspect_ratio` (например, `16:9` или `auto`), логический `watermark` (например, `false`: только видео без логотипа) и `duration_rule` — одно из `min_supported_strictly_greater_than_window` (минимальная поддерживаемая длительность строго больше монтажного окна), `min_supported_not_less_than_window`, `exact_window`. Значения проверяются по типу и форме; пригодность конкретному сервису проверяет его исполнитель. Допустимы необязательные `model` и объект `options`.

Для чтения оформления без проверки производства есть `validate_project(data, validate_generation=False)`. Именно этот режим использует `load_project(root)`; строгая проверка прочитанного файла доступна через `load_project(root, validate_generation=True)`. Так неверный блок другого медиа не мешает просмотру, локальному импорту и работе выбранного исполнителя.

У `image` обязателен только `provider`; необязательны `aspect_ratio`, `resolution`, `model`, положительное целое `outputs`, логический `watermark` и объект `options`. В новом шаблоне оба медиа имеют значение `null`: провайдеров выбирает пользователь. Неизвестные провайдеры, поля, вложенные `options` и `backend` сохраняются: пригодность параметров конкретному сервису проверяет его исполнитель.

У обоих медиа необязательный `provider_selected` принимает только логическое значение. Только `true`, записанное после явного выбора провайдера пользователем и сохранения настроек, подтверждает выбор; отсутствие поля или `false` оставляет AI-действия недоступными, даже если `provider` задан. Структурное чтение не требует `true`, не добавляет маркер и сохраняет неизвестные параметры; проверка готовности выполняется перед AI-действием. Единственный источник выбора — `plan/project.json`.

У обоих медиа `aspect_ratio` допускает пропорцию вида `16:9` либо строку `auto`. Поддержка `auto` выбранной моделью проверяется по актуальным возможностям при подготовке запроса; сохранение настроек не подменяет эту проверку.

`generation_settings` читает только `generation.video` или `generation.image`. Для генерации выбранный блок обязателен; без него или с неверными полями возникает понятный `ValueError`. Плоский объект настроек недопустим. Чтение не меняет проект и замороженные запросы.

Имена, пути и подписи референсов принадлежат кастингу `plan/cast.json`; карта `references` в `scenes.json` (`name`, `path`, необязательное `short_name`) выводится из него командой [cast_registry sync](../cast_registry/README.md), а `scene_registry` читает её из реестра. Объекты состояния адресуются ID реестра; вычисление не знает имён персонажей и локаций. Ожидания тестов проверяются на синтетическом проекте-образце.

## Контракт состояния в scenes.json

У каждого плана есть `state_from` и `state_changes`. Имена объектов и свойств — `snake_case`, значения — непустые строки по-русски. Сущности определяются постановкой проекта; записываются установленные условия, а не придуманные подробности.

### Источник состояния

- `null` — начало сюжетной линии без наследования от другого плана: состояние стартует с `initial_state` сущностей кастинга `plan/cast.json` (без кастинга — пустое), `state_changes.before` уточняет его.
- `"M01"` — состояние **после** M01. Источник относится ко всей сцене, а не к отдельному предмету.
- `{"scene":"M01","phase":"before"}` — состояние перед событием; `phase: "after"` эквивалентна строковой ссылке.
- `{"scene":"M01","phase":"same"}` — повтор того же события: обе границы M01 без копирования его изменений. Собственные изменения при `same` запрещены.

Будущие по монтажу ссылки разрешены, сюжетные циклы — нет; перестановка планов записанные связи не меняет.

### Изменения state_changes

```json
{
  "before": {"performer": {"position": "стоит у сцены"}},
  "after": {"performer": {"position": "стоит на сцене"}}
}
```

`before` уточняет вход с учётом событий между планами; для принятой сцены граница — первый кадр `accepted_edit.video`, а не начало полного оригинала. `after` описывает результат действия в плане, который наследуется далее.

Изменения накладываются по отдельным свойствам: пропущенное наследуется, `{}` означает отсутствие новых изменений, `null` удаляет больше не установленный факт. Исчезновение героя из кадра не удаляет его состояние. Разовый жест и само действие остаются в `action`, сохраняющиеся положения и последствия — в `state_changes`.

| Сведения | Как хранить |
| --- | --- |
| Установленные изменения одежды, предметов и эмоций | Отдельные свойства; наследуются до подтверждённого изменения |
| Принадлежность и положение предмета | Положение сверять с постановкой и принятым кадром |
| Разовый жест, кивок, направление взгляда | `action`; не превращать в наследуемое условие |

`action` — события, `continuity` — монтажные и пространственные связи, `state_changes` — сохраняющиеся условия; вычисленную сводку в следующих сценах не повторять.

## Производный план derived_from

Необязательное поле `"derived_from": {"shot": "M02"}` означает, что план собирается из материала другого плана (стоп-кадр, повтор, замедление) без собственной генерации. Как именно используется материал, описывается текстом в `action`; поле хранит только ссылку. Сюжетное состояние по-прежнему задают `state_from` и `state_changes`: ссылка на материал их не заменяет.

`validate` проверяет поле, `derived_from_problems(scenes)` возвращает все нарушения парами (ID плана, текст) для [lint_registry](../lint_registry/README.md). Правила и тексты ошибок:

| Правило | Ошибка |
| --- | --- |
| Объект ровно с одним ключом `shot`, значение — ID плана `Mxx` или `Mxx.n` | `M01: derived_from должен быть объектом {"shot": "Mxx"}.` |
| Источник есть в реестре | `M01: derived_from ссылается на неизвестный план M99.` |
| Источник — не сам план | `M01: derived_from не может ссылаться на сам план.` |
| У источника нет своего `derived_from`: ссылка ведёт на план с собственной генерацией | `M01: источник M03 сам собирается из другого плана; укажите исходный план.` |

Источник может стоять на шкале позже производного плана. CLI добавляет `derived_from` в вывод только у производного плана; представления помечают такой план «из Mxx» ([update_scene_views](../update_scene_views/README.md)).

## API и проверка

`load`/`validate` проверяют шкалу, ссылки, циклы и форму изменений, но не соответствие сценарию и изображениям. `shots` вычисляет длительности и подписи. `scene_state(data, sid)` возвращает независимые `before` и `after`; изменение результата не меняет исходные данные. `scene_fingerprint(data, sid)` — SHA-256 текущего контекста с унаследованным состоянием: изменение M29 обнаруживается при продолжении пакета M37. Поля `state_from` и `state_changes` обязательны у каждого плана.

После изменения реестра запускать [update_scene_views](../update_scene_views/README.md); полная сборка — по [описанию аниматика](../../templates/project/plan/animatic/README.md). Чтение состояния ничего не пересобирает.

## Тесты

Непрерывность шкалы, граф сюжетных зависимостей, входные и выходные изменения, повтор сцен и актуальность хеша отложенного пакета.

```sh
python3 -B tools/scene_registry/test_scene_registry.py
python3 -B tools/run_tests/run_tests.py --only test_scene_registry
```

Тесты находятся рядом со скриптом; рабочие сцены не изменяют. Полный набор — [run_tests](../run_tests/README.md).
