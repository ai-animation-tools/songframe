# SongFrame на Go и Wails 3

Изолированная настольная оболочка SongFrame. В бинарник встроен React/MUI frontend, работающий через сгенерированные Wails bindings. Сохранены тема, палитра, маршруты и базовая компоновка интерфейса исходного SongFrame; Electron и собственные Python/Node runtime не используются. Найденные инструменты и модели автоматически проверяются в фоне при запуске. Отсутствие ONNX Runtime не мешает открыть окно и просматривать проект; его загрузчик вызывается только для найденной библиотеки.

Сейчас работают оболочка, отдельный профиль, чтение существующего проекта и таймингов без записи, локальное аудио/видео, отдельное окно просмотра и диагностика. Создание проектов, сохранение разметки и производственные операции пока недоступны. Просмотр не вычисляет полный статус готовности клипа и не заменяет восстановление незавершённых операций в прежнем приложении. Это промежуточная версия для разработки; ранние Linux AppImage и Windows NSIS описаны в [руководстве поставки](packaging/README.md) и не является готовой заменой рабочего приложения.

## Сборка и проверки

Нужны Go 1.26+, Wails CLI 3.0.0, Node/Yarn 4.18.1 **для разработки frontend**. На Linux нужны C-компилятор и библиотеки разработки GTK4/WebKitGTK 6.0; готовое приложение использует системный WebView. Ранний Linux AppImage собирается для Ubuntu 24.04 amd64 / glibc 2.39 с GTK/WebKit внутри; рецепт, системные prerequisites и проверки — в [packaging](packaging/README.md). Windows amd64 CGO/NSIS собран и проверен по составу; нативная проверка в VM остаётся за пользователем. macOS не проверен.

При необходимости установить закреплённый CLI:

```sh
go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0
```

Из корня репозитория:

```sh
wails3 task deps
wails3 task check
wails3 task build
wails3 task run
wails3 task package:linux
```

`wails3 task` использует встроенный исполнитель Taskfile. `deps` устанавливает frontend по immutable lock. `check` генерирует bindings, выполняет Go tests/vet, TypeScript и Vitest. `build` заново генерирует bindings, собирает frontend и нативный бинарник `build/bin/songframe-go` для текущей ОС. Сборка на Windows/macOS и их нативная работоспособность этим рецептом ещё не подтверждены.

Адресные команды запускаются из этого репозитория; исходники соседних `songframe`, `songframe-go-probe` и документы `spec` для них не нужны:

| Команда | Что проверяет |
| --- | --- |
| `wails3 task check:go` | Генерация bindings, Go tests/vet, включая точку входа приложения |
| `wails3 task check:frontend` | TypeScript и все Vitest-тесты границы API |
| `wails3 task check:contracts` | Общие JSON-fixtures: Go-сериализация/чтение и настоящий TS-адаптер с подменой generated-вызовов |
| `wails3 task check:components` | Связность manifest, границы платформенной готовности, сохранение принятого CTC-рецепта |
| `wails3 task check:race` | Конкурентный доступ Go-сервисов; нужен C-компилятор для race detector |
| `wails3 task check:format` | Форматирование Go и frontend без изменения файлов |
| `wails3 task check:ui` | Свежая статическая сборка Storybook и браузерные сценарии |
| `wails3 task check:all` | Последовательно `check`, `check:race`, `check:format`, `check:ui` |

Контрактные данные и их границы описаны в [testdata/contracts](testdata/contracts/README.md). Это синтетические документы, а не копия клипа. Go-тесты разворачивают их во временных каталогах и проверяют сохранность файлов; TS-тесты используют те же ожидаемые JSON. Fixtures журналов проверяют блокировку просмотра, отсутствие записи и отката; они не означают готовность полного recovery. Профильные журналы старого приложения здесь не восстанавливаются.

В чистом checkout сначала выполнить `wails3 task deps` и установить Chromium командой ниже; затем `wails3 task check:all`. Проверки используют локальные Go/Yarn/браузерные зависимости, но не требуют настоящих клипов, Python, FFmpeg, моделей или работающего старого SongFrame. На ограниченном окружении каталог Go-кэша можно задать явно, например `GOCACHE=/tmp/songframe-go-build-cache wails3 task check:all`; это не меняет профиль приложения.

`frontend/dist` встроен через `go:embed`; в чистом checkout сначала выполнить `wails3 task bindings` или `build`. Скрипт bindings создаёт временный index только для запуска генератора до первой сборки. Vite заменяет его настоящим приложением. Нельзя считать ручную Go-сборку этого временного index готовой оболочкой; штатный `build` всегда собирает frontend.

Витрина и браузерные проверки:

```sh
wails3 task storybook
wails3 task check:storybook
```

Последняя команда проверяет статическую витрину, а не dev/HMR. Матрица содержит 20 браузерных сценариев, включая повторные mount/unmount приложения и страницы таймингов. Рабочий размер проверки — 1320×860, обе темы. Это также стартовый и минимально разрешённый размер нативного окна; меньшие размеры исключены из обязательной приёмки по поручению пользователя. Для первого запуска нужен браузер Playwright (`cd frontend && yarn playwright install chromium`). Истории оболочки и рабочих страниц используют независимые типизированные модели: открытие/повторное открытие, ошибки, блокировка незавершённого проекта, тайминги, отсутствие медиа и переход из уведомления.

## Изоляция состояния и нативная проверка

Идентификатор новой оболочки — `tools.songframe.go.dev`. Постоянное состояние находится в `songframe-go-dev` внутри стандартного каталога настроек ОС. Для проверки можно явно задать `SONGFRAME_GO_LOCAL_DIR`; старый `SONGFRAME_LOCAL_DIR` не используется. Windows WebView получает отдельную папку внутри нового профиля; ключ темы — `songframe-go.theme`.

Профиль рабочего Electron SongFrame, выбранный там проект, токены и клипы не читаются автоматически. При ошибке подготовки нового профиля UI показывает причину и оставляет повтор чтения.

Проверка настоящего Wails-окна на Linux, с отдельным временным профилем:

```sh
SONGFRAME_GO_LOCAL_DIR=/tmp/songframe-go-smoke-profile \
  ./build/bin/songframe-go --smoke \
  --smoke-report /tmp/songframe-go-smoke.json --smoke-timeout 30s
```

Smoke проходит только после успешного вызова `State` из frontend и монтирования содержимого страницы. Таймаут, преждевременное закрытие или невозможность записать отчёт означают ошибку. Проверка не подтверждает воспроизведение медиа, физический звук или платформы, на которых не запускалась. Обычный запуск не пишет smoke-отчёт и не закрывается автоматически.

## Устройство и границы

- `main.go` соединяет Wails, встроенные ресурсы, профиль и сервисы. Найденные компоненты автоматически проверяет фоновый сервис; производственные задания здесь не запускаются.
- `internal/project` — чтение маркера, текста, разметки и известных проектных журналов; файлы проекта не меняются. `internal/media` — один HTTP listener на loopback для всех окон, потоковые GET/HEAD/Range. `internal/diagnostics` — журнал ошибок и маркер сеанса нового профиля.
- `internal/app` — `ShellService`, JSON-контракт состояния и нативная проверка запуска. `internal/store` — определение и подготовка отдельного профиля. Пока используется только необходимый `ProfileStore`; интерфейсы заданий/процессов появятся с их первыми потребителями.
- `internal/components` — обнаружение, функциональные проверки и установка закреплённых компонентов. Экран «Компоненты» подключает внешние файлы, выбирает папку управляемой установки, скачивает или импортирует офлайн-пакеты; прогресс и журнал принадлежат Go. После выбора пути и успешной установки сервис автоматически проверяет функции; открытие страницы лишь читает состояние. Возврат из контекстной настройки открывает исходную страницу без запуска производства.
- `frontend/src/platform` — единственная установка `window.api`, доступность методов и перевод ошибок. Целевое устройство: каждый метод отображается на generated binding без ручной проверки ответов; переходные мосты ниже заменяются на него. Совместимый каталог из 151 метода сохраняется для дальнейшего переноса. Минимальное чтение проекта использует отдельный `WorkspaceBridge`, а не неполный `ProjectStatus`; конкретную доступность прежних методов задаёт адаптер. Удалены три прежних Whisper-метода. Синхронные методы и подписки не превращаются в Promise или успешные заглушки.
- `frontend/bindings` генерируется из Go. Не редактировать вручную; машинные заголовки принадлежат upstream-генератору. Nullable-массивы generated DTO проверяются на границе, `null` и `[]` имеют разный смысл.
- `frontend/src/shared` — выбранный замкнутый граф исходных контрактов и словарей. Контракты ещё не перенесённых доменов не означают готовность функций. Собственные Node/Electron/Python импорты для их исполнения не добавляются.
- `frontend/src/renderer` — минимальная оболочка, страницы и тема; русские подписи централизованы в `shared/texts`. При переносе следующих областей UI и истории обновляются вместе.

Решения, этапы и статус работ ведутся в соседнем приватном `../spec/`. Для самостоятельной сборки его файлы не нужны.

## Происхождение и лицензии

Выбранные frontend/shared исходники и иконки перенесены из SongFrame commit `634fd9429ba0b0cfcb984a52ce95adf8e1674635`. Исходное уведомление MIT сохранено в `LICENSE`. Версии React, MUI, Emotion, Storybook, Vite и TypeScript сохранены по исходному lock; Electron-зависимости удалены, добавлен `@wailsio/runtime` 3.0.0.

Устройство Wails services и Taskfile сверено с Forktopus `d49de381e55e40a66c5d95968f8cb7d655b44198`; продуктовые Git-функции не переносились. Применяется [официальный механизм services и generated bindings](https://v3.wails.io/features/bindings/services/). Лицензии фактических сторонних зависимостей сохраняют силу; полный комплект уведомлений для пользовательской поставки будет собран вместе с её составом.

Модели, реальные проекты, медиа, локальные отчёты, dependencies и build-артефакты в Git не входят.

## Компоненты производства

Закреплены пакеты FFmpeg/ffprobe и ORT CPU для Linux/Windows amd64, Voc FT и пара CTC/vocab с неизменными SHA принятого эксперимента. [Реестр компонентов](internal/components/README.md) содержит состав, размеры, лицензии, ABI, зависимости и воспроизводимые проверки. Это описание точных артефактов; обнаружение и статусы по функциям, Go media probes и lazy ORT реализованы через отдельный Wails-сервис. Пользовательский экран установки и скачивание компонентов реализованы; полный CTC-процесс ещё не перенесён. Windows/macOS не объявлены принятыми.

## Чтение проектов и медиа

Выберите папку существующего проекта или перетащите её в область открытия. Представление чтения показывает сохранённые тайминги, физические номера строк текста и ручные подтверждения. Оно не нормализует и не пересохраняет JSON. Обнаруженная незавершённая публикация montage/derived блокирует просмотр; журналы прежнего профиля scenario/production здесь не проверяются. На этом этапе используйте заведомо целостную копию проекта. История текущего проекта прежнего приложения не импортируется; список недавних проектов пока хранится только в текущем UI-сеансе.

Плеер принимает WAV/MP3/MP4/WebM. Файл можно выбрать диалогом или перетащить в область медиа; реальные пути передаёт Wails, синтетический браузерный File не превращается в путь диска. URL временный и остаётся в памяти приложения. Волна строится по явному действию через AudioContext; системные кодеки WebView определяют доступность форматов. Ошибка декодирования объясняется на странице, исходник не перекодируется автоматически.

Проверка настоящего WebView на синтетических файлах (FFmpeg нужен только для подготовки):

```sh
sh scripts/make-media-fixtures.sh /tmp/songframe-media-fixtures
SONGFRAME_GO_LOCAL_DIR=/tmp/songframe-native-profile ./build/bin/songframe-go \
  --native-check-dir /tmp/songframe-media-fixtures \
  --native-check-report /tmp/songframe-native-report.json \
  --smoke-timeout 90s
```

Для дополнительной проверки чтения передайте `--native-check-project "/путь/к/копии проекта"`. Копия для этого сценария должна содержать трек и непустую сохранённую разметку. Отчёт требует все 13 наблюдений медиа/HTTP/второго окна и окна плеера монтажа либо 15 вместе с проектом и notification target. Проверяется реальное движение позиции, seek, loop и декодирование сигнала; **физический звук и нажатие системного уведомления не выводятся из автоматического успеха**. Доставка OS-уведомлений заданий появится вместе с заданиями. Windows/macOS требуют собственных нативных проверок.
