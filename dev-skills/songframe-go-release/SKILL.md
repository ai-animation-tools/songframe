# Выпуск SongFrame Go

Работай в приватном `songframe-go/`; прочитай `AGENTS.md`, `packaging/README.md` и фактические `Taskfile.yml`/`scripts/`. Это адаптация полезных правил `songframe-release`, а не перенос его механических команд. `songframe/` доступен только для чтения. **Не выполняй Electron-команды `yarn release plan/prepare/publish` и не применяй его механику комплектов к Go-версии.** Итоговый канал: при переключении история songframe-go переносится в публичный `ai-animation-tools/songframe`, первый Go-выпуск — 1.0.0 (Linux AppImage и deb, Windows NSIS), после чего songframe-go архивируется. До переключения Go-версия в songframe не публикуется. Совместимость с Electron-updater не требуется: пользователи ставят 1.0.0 с нуля; проверяется лишь, что Electron, увидев этот выпуск, не повреждает свою установку и данные.

## Текущая реализация и объём поручения

Сейчас реализованы локальные Linux x86_64 AppImage и Windows amd64 NSIS (`wails3 task package:windows`); deb-пакет ещё не реализован. Linux: `wails3 task package:linux`, `packaging/VERSION`, `build/release/*.AppImage` с `*.build.json` и `*.sha256`. Для сборки и проверок применяй соседний [songframe-go-build](../songframe-go-build/SKILL.md). Полноценные version plan/prepare/publish, тегирование, публикация и автообновление пока не реализованы. Linux build/CPU smoke не подтверждают Windows или готовность обновлений.

Сначала проверь, не появилась ли новая реализация в актуальных исходниках, и установи её реальные гарантии. Не объявляй pipeline готовым по одному номеру версии, наличию `origin`, локальному артефакту или совпадению названия задачи. Если его всё ещё нет, выполни доступную часть поручения: анализ diff, план версии, описание, выявление недостающих шагов; остановись перед отсутствующим действием и объясни конкретный остаток. Полное поручение выпустить версию допускает необходимую работу в согласованных границах, но не разрешает выдавать ручную загрузку вместо несуществующего pipeline или изменять прежний продукт. Существенное проектирование нового выпуска согласуй по правилам миграции.

Просьба написать описание/спланировать не разрешает сборку, commit, push, тег и публикацию. Локальная сборка не разрешает выпуск. Разработка этого скилла также не является поручением выпустить версию. Сохраняй явно заданные пользователем ограничения; не спрашивай повторно о действиях, уже включённых в действующее поручение.

## Версия, описание и доказательства

При поручении планировать выпуск выясни точный исходный SHA и состояние рабочего дерева, предыдущий фактически опубликованный Go-релиз, если он есть. Читай существенный diff между его исходниками и выбранными новыми исходниками; сообщения коммитов сами по себе не подтверждают возможность. Для первого выпуска опиши реально реализованное назначение и ограничения.

Выбирай SemVer `X.Y.Z` по изменениям: patch — исправления, minor — возможности, major — несовместимые изменения после первого выпуска. Текущая ранняя локальная версия берётся из `packaging/VERSION`; `frontend/package.json` не является версией поставки. Без поручения версию не меняй. Не собирай другой SHA молча и не приписывай грязному дереву свойства чистого HEAD. Если будущая публикация требует фиксированных исходников, а commit не поручен, подготовь конкретный результат и назови этот оставшийся шаг.

Описание пиши по-русски: полезное пользователю изменение, действия при обновлении и существенные ограничения. Не копируй приватный план, журнал, локальные абсолютные пути и внутреннюю историю обсуждения. Разовые notes сохраняй вне Git, например в новой папке `/tmp`; не придумывай существующий Go-каталог release receipts. Ссылки на вложения разрешено включать только после определения реального целевого репозитория/тега и точных имён файлов, не по шаблону старого SongFrame.

Локальный комплект сверяй по SHA-256, размерам, версии, исходному SHA/dirty и фактическим результатам smoke. Не перезаписывай опубликованный комплект под тем же номером, не переноси тег, не удаляй релиз и не применяй `--clobber` без прямого поручения на переиздание. При будущем сбое публикации сначала выясни состояние релиза и вложений, а не повторяй изменяющие действия вслепую.

Когда публикация будет реализована и поручена, проверяй вложения через GitHub API: `digest` вида `sha256:<хэш>`, `size`, `state: uploaded`, версионный URL и состояние published. Не скачивай вложения обратно для проверки; отсутствующий/несовпадающий digest означает непроверенный результат. Успешный CI должен относиться к исходному SHA комплекта, если CI входит в принятый pipeline; не наследуй названия workflows и режимов прежнего репозитория.

В результате раздельно укажи план, локальную сборку, проверки, состояние Git/публикации и недостающую реализацию. Для локального AppImage приведи версию, путь, SHA и отчёты по `songframe-go-build`; ссылку на релиз давай только после фактической публикации. Не обещай Windows, отсутствие предупреждений ОС или обновление поверх старой версии без соответствующей реализации и проверки.
