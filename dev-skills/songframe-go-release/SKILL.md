# Выпуск SongFrame

Работай в `songframe-go/`; прочитай `AGENTS.md`, `packaging/README.md`, `packaging/windows/README.md` и фактические `Taskfile.yml`/`scripts/`. Сборку и smoke выполняй по соседнему [songframe-go-build](../songframe-go-build/SKILL.md). Electron-команды `yarn release plan/prepare/publish` к Go-версии не применяются: собственного скрипта выпуска здесь нет, механические шаги ниже выполняются `wails3 task`, `git` и `gh`.

Канал выпуска один — публичный `ai-animation-tools/songframe`. При переключении история songframe-go переносится туда, первый Go-выпуск получает тег `v1.0.0`, после чего songframe-go архивируется. Выпуски, сайт `https://ai-animation-tools.github.io/songframe/` (`www/` и `.github/workflows/pages.yml`), issues и адрес обновлений остаются в публичном songframe. В приватном songframe-go ничего не публикуется. Поставки 1.0.0: Linux x86_64 AppImage и deb, Windows amd64 NSIS. Пользователи ставят 1.0.0 с нуля; совместимость с Electron-обновлятором не требуется, но установленный Electron, увидев 1.0.0, не должен повредить свою установку и данные.

## Объём поручения

- Просьба спланировать выпуск или написать описание разрешает только чтение, анализ diff, план версии и черновик описания вне Git.
- Локальная сборка не разрешает выпуск. Изменение `packaging/VERSION`, commit, push, тег, перенос истории, создание релиза, публикация и архивирование — только по явному поручению. Поручение на один шаг не распространяется на следующие.
- Разработка этого скилла не является поручением выпустить версию.
- Сохраняй явно заданные пользователем ограничения и не спрашивай повторно о действиях, уже включённых в действующее поручение. Изменения видимого результата (имена продукта и файлов, каталоги установки, поведение для пользователей Electron) согласуй с пользователем.

Перед работой проверь, не изменилось ли состояние, описанное ниже: прочитай актуальные скрипты упаковки, адаптер `frontend/src/platform/` и README. Не объявляй выпуск готовым по номеру версии, наличию локального артефакта или названию задачи. Если условие не закрыто, выполни доступную часть и остановись перед ним, назвав конкретный остаток.

## Незакрытые условия выпуска 1.0.0

На момент написания скилла выпуск невозможен, пока не закрыты пункты ниже. Каждый пункт сверяй с исходниками; закрытый пункт подтверждай кодом и проверкой, а не записью.

1. **Итоговая приёмка.** Области Electron-версии перенесены, все методы контракта реализованы в Go. Выпуск 1.0.0 возможен только после итоговой приёмки миграции человеком (план — в соседнем приватном `spec`, если он есть в рабочей области).
2. **Имена файлов.** Скрипты выпускают `songframe-<VERSION>-linux-x86_64.AppImage` и `songframe-<VERSION>-win-x64-setup.exe` — имена, которые ищет обновление из приложения и сайт.
3. **Идентификаторы продукта** (согласованы, D-038 в spec): имя «SongFrame», бинарник `songframe`, app ID `tools.songframe.desktop`, профиль `songframe-desktop`, `songframe.desktop`, папка Windows `%LOCALAPPDATA%\Programs\SongFrame Desktop`, ключ удаления `SongFrameDesktop`. Они отличаются от Electron-версии (`tools.songframe.app`, профиль `songframe`, `Programs\SongFrame`): установщик и приложение не пишут в её папку установки, ключ удаления и профиль. Общий у них только ярлык «SongFrame» в меню «Пуск».
4. **Версия.** `packaging/VERSION` содержит раннюю версию `1.0.0-dev.N`: она младше выпуска 1.0.0 и старше выпусков Electron 0.x, поэтому ранняя сборка не предлагает «обновиться» до Electron. Выпуск требует `X.Y.Z` без prerelease-суффикса. Тег публичного выпуска — `vX.Y.Z`. Числовая версия PE для Windows выводится из того же файла. `frontend/package.json` версией поставки не является.
5. **deb-пакет.** `wails3 task package:deb` выпускает `songframe-<VERSION>-linux-amd64.deb`; проверка — `smoke:deb` (packaging/README). Сайт ищет вложение с суффиксом `.deb`.
6. **Обновление из приложения.** Реализовано (`internal/updates`): последний выпуск, вложение своей поставки по точному имени из условий 2 и 5, digest SHA-256 и размер. Поэтому каждый выпуск обязан содержать все три пакета с этими именами; пропущенный пакет пользователи этой поставки увидят как «В выпуске нет пакета для этой системы». Проверка перед выпуском — `smoke:update` для AppImage и сценарий Windows из packaging/windows/README.
7. **Нативная Windows-проверка.** Сборка установщика на Linux не доказывает работу в Windows. Прогон в VM — только по явному поручению; без него Windows в описании указывается как проверенный только по составу установщика.
8. **Лицензии комплекта.** Состав уведомлений каждой поставки сверяй по `scripts/package-notices.py` и проверкам комплекта. Компоненты, устанавливаемые кнопкой, приносят свои уведомления сами.
9. **Публичность истории.** До переноса в публичный songframe проверь всю историю songframe-go: в ней не должно быть приватных документов `spec`, клипов, весов, медиа, токенов, журналов и абсолютных путей машины. Найденное — блокер переключения. Переписывание истории согласуй с пользователем.

## Порядок выпуска

### 1. Предусловия

- Определи точный исходный SHA, ветку и состояние дерева. Комплект собирается только из чистого зафиксированного дерева. Грязное дерево означает, что изменения в выпуск не войдут; другой SHA молча не собирай.
- Один раз на этом SHA выполни полный `wails3 task check:all`. Повторять его после каждого шага не нужно: после сбоя исправь причину, перезапусти упавшее, затем выполни полный прогон снова.
- Проверь сохранность результата по правилам `AGENTS.md`: тестовый клип `../test-projects/ogorod` с откатом через его Git, готовый клип пользователя только на чтение со сравнением SHA дерева до и после.
- Ручная приёмка человеком обязательна. Финальное принятие видео и поведения остаётся за пользователем. Сборка и автоматические проверки ручную приёмку не заменяют.

### 2. Версия и описание

- Для первого выпуска версия `1.0.0`. Для следующих выбирай SemVer по существенному diff от исходников предыдущего опубликованного Go-выпуска (`gh release list --repo ai-animation-tools/songframe`): patch — исправления, minor — возможности, major — несовместимые изменения формата проекта. Сообщения коммитов возможность не доказывают; читай diff.
- Запиши версию в `packaging/VERSION` и зафиксируй её вместе с исходниками до сборки, только если commit входит в поручение. Иначе подготовь план и назови этот шаг оставшимся.
- Описание пиши по-русски в новой папке под `/tmp`, не в Git. Для 1.0.0 включи: назначение приложения; поставки и системные требования (AppImage — Ubuntu 24.04, glibc 2.39, x86_64; Windows 10/11 amd64); установку с нуля; компоненты FFmpeg/ffprobe, ONNX Runtime и модели, которые приложение находит в системе или ставит кнопкой, без них проект открывается и редактируется; Python не нужен. Отдельно для пользователей Electron-версии: проекты открываются как есть, настройки, вход провайдеров и история прежнего профиля не переносятся, а кнопка «Обновить» в Electron может заменить его Go-версией (раздел 6). Для последующих выпусков — изменения, действия при обновлении и известные ограничения.
- Ссылки на вложения давай прямыми версионными URL `https://github.com/ai-animation-tools/songframe/releases/download/v<версия>/<имя-файла>` только после фиксации точных имён. Не обещай подпись кода, отсутствие предупреждений SmartScreen, проверку в Windows или обновление из приложения без реализации и проверки.

### 3. Сборка поставок

- Linux: `wails3 task package:linux`, затем проверки по `songframe-go-build` (`smoke:host`, по задаче `smoke:appimage` и CPU smoke компонентов).
- Windows: `wails3 task package:windows`. Проверка состава встроена в рецепт и не исполняет Windows-код.
- deb: `wails3 task package:deb`, затем `smoke:deb` (условие 5).
- Результат в `build/release/`: пакеты, `<имя>.sha256` и `<имя>.build.json`. Сверь по receipt версию, исходный SHA, `dirty: false`, размер и SHA-256 каждого файла. Receipt — внутренняя проверка: в выпуск и в общую папку VM он не прикладывается, без запроса пользователю не выводится.
- Сборки долгие: запускай их в фоне с журналом и не опрашивай без нужды. Опубликованный комплект под тем же номером не пересобирай.

### 4. Переключение репозитория (только для 1.0.0)

Выполняется по отдельному поручению, после закрытия условий 1–9.

- Способ переноса истории songframe-go в публичный songframe согласуй с пользователем. Замена `main` требует force push, поэтому без прямого поручения на него не выполняй. Существующие теги `v0.*` и релизы Electron в публичном songframe не удаляй и не переноси.
- Аннотированный тег `v1.0.0` ставится в публичном songframe на исходный SHA комплекта. Тег не переносится после публикации.
- Настройки публичного репозитория (Pages из workflow, переменная раннера `CI_LINUX_RUNS_ON`, issues) сохраняются. `pages.yml` публикует `www/` только в `ai-animation-tools/songframe`; в songframe-go job пропускается.
- Если после переноса в публичном songframe действует CI, его успешный запуск должен относиться к исходному SHA комплекта.
- songframe-go архивируется (`gh repo archive ai-animation-tools/songframe-go`) только после успешной публикации и проверки 1.0.0, по поручению.

### 5. Публикация

Выполняется только по отдельному поручению выпустить эту версию.

1. Создай черновик: `gh release create v<версия> --repo ai-animation-tools/songframe --draft --verify-tag --title "SongFrame <версия>" --notes-file <описание>`. Черновик не виден как `releases/latest`, поэтому на нём безопасно проверять вложения.
2. Загрузи пакеты и их `.sha256`: `gh release upload v<версия> <файлы> --repo ai-animation-tools/songframe`, без `--clobber`.
3. Проверь каждое вложение через GitHub API: `gh api repos/ai-animation-tools/songframe/releases/<id>`. Поля `digest: sha256:<хэш>` и `size` должны совпадать с локальным комплектом, `state` — `uploaded`. Также проверь версионный `browser_download_url`. Вложения обратно для проверки не скачивай. Отсутствующий или несовпадающий digest означает непроверенный результат.
4. Опубликуй: `gh release edit v<версия> --repo ai-animation-tools/songframe --draft=false --latest`. Затем повтори проверку вложений и убедись, что `releases/latest` указывает на этот выпуск.

При сбое сначала выясни фактическое состояние релиза, тега и вложений, затем повтори только недостающий шаг. Релиз и тег не удаляй, `--clobber` не применяй и под опубликованным номером не пересобирай без прямого поручения переиздать.

### 6. Установленный Electron

Установленная Electron-версия 0.x проверяет обновление по явному действию пользователя. Ниже описано её поведение; сверять его можно только чтением замороженного оригинала.

- Electron запрашивает `releases/latest` публичного songframe. Тег должен иметь вид `vX.Y.Z`, выпуск не может быть draft или prerelease.
- Затем ищется вложение с точным именем `songframe-<версия>-linux-x86_64.AppImage` или `songframe-<версия>-win-x64-setup.exe`, у которого есть `digest` SHA-256, положительный `size` и версионный `browser_download_url` этого репозитория.
- Если такого пакета нет, Electron сообщает ошибку проверки и ничего не меняет.
- Если пакет найден и версия новее, Electron предлагает обновление. После скачивания и сверки SHA:
  - в Linux он атомарно заменяет свой AppImage скачанным файлом и запускает его по тому же пути;
  - в Windows он запускает скачанный установщик и закрывается.

С выпускными именами из условия 2 Electron найдёт 1.0.0 как обновление и по кнопке «Обновить» заменит себя Go-версией. Пользователь решил, что совместимость обновления с Electron не нужна: отдельных мер и проверки этого поведения нет, достаточно упомянуть его в описании выпуска. Общее правило остаётся: Go-версия не читает и не меняет профиль Electron.

### 7. Сайт

После переключения push в `main` с изменениями `www/**` публикует лэндинг. Скрипт страницы выбирает пакеты выпуска по суффиксам `-linux-x86_64.AppImage`, `-win-x64-setup.exe` и `.deb`. Без ответа GitHub ссылки ведут на страницу последнего выпуска. Отсутствующий deb скрывает свою ссылку. После публикации проверь, что страница показывает версию и прямые ссылки на пакеты. Утверждения сайта о составе поставки и требованиях обновляй вместе с изменением поставки.

## Что сообщить пользователю

Раздельно укажи:

- план и выбранную версию;
- исходный SHA и состояние дерева;
- результат `check:all` и ручной приёмки;
- собранные пакеты и выполненные smoke;
- состояние Git: тег и перенос истории;
- состояние публикации: черновик или published, проверка вложений по API;
- незакрытые условия.

Ссылку на релиз давай только после фактической публикации. Windows без VM-прогона указывай как проверенный только по составу установщика.
