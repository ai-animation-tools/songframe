# run_tests

Запускает все локальные тесты или выбранные наборы после изменения инструментов. Ничего не отправляет сервисам генерации: общая логика работает на тестовом провайдере `test` ([tools/testing](../testing/README.md)), адаптеры провайдеров — на поддельных локальных серверах; новые медиа, копия проекта-образца и каталог состояния (`SONGFRAME_LOCAL_DIR`, если он не задан снаружи) создаются во временных папках.

```sh
python3 -B tools/run_tests/run_tests.py
python3 -B tools/run_tests/run_tests.py --only test_media_request test_build_review
python3 -B tools/run_tests/run_tests.py --jobs 4
```

`--jobs N` запускает до N наборов одновременно, каждый отдельным процессом со своей копией образца и каталогом состояния; вывод набора печатается целиком после его завершения, в конце — число наборов с ошибками. Без параметра наборы идут последовательно в одном процессе. CI использует число ядер раннера, а в контейнере с квотой CPU — квоту из `/sys/fs/cgroup/cpu.max`: `nproc` там видит все ядра хоста.

Наборы находятся рядом со скриптами в `tools/<инструмент>/test_*.py`; имена передаются без `.py`. Неизвестные и повторные имена отклоняются. Нужны Python, Git (копия проекта-образца инициализируется `git init`), FFmpeg/ffprobe и Pillow для медиатестов. Возвращает ненулевой код при провале. Корень комплекса определяется по расположению скрипта; запуск не зависит от текущей папки.

## Проверки выбора наборов

```sh
python3 -B tools/run_tests/run_tests.py --only test_run_tests
```

`test_run_tests.py` копирует настоящий `run_tests.py` во временное дерево `tools/run_tests/`, создаёт там два маленьких unittest-набора с маркерами и пустой `tools/testing/sample_project.py`. Вложенные CLI-запуски используют только это дерево и стандартную библиотеку: не читают настоящие клипы, не создают проект-образец и не требуют медиазависимостей. Внешний штатный запуск команды выше инициализирует обычное тестовое окружение runner, но выбирает только эти пять тестов.

Проверяются изоляция `--only` от падающего соседнего набора, запуск из посторонней рабочей папки, отдельные процессы при `--jobs 2`, объединение результатов и ненулевого кода при ошибке, отказ неизвестного/повторного имени и `--jobs 0` до исполнения тестов. Это проверка CLI-контракта runner; доступность сервисов, загрузка моделей, работа FFmpeg и качество реальных инструментов здесь не проверяются.

## FFmpeg для CI

В CI `prepare_ci_ffmpeg.py --directory <временный каталог>` загружает закреплённый в `scripts/runtime/media-lock.json` архив Linux FFmpeg, проверяет его SHA-256 и извлекает только `ffmpeg` и `ffprobe` в `bin` этого каталога. Восстановленный кэш проверяется тем же способом; повреждённый архив скачивается заново, а при несовпадении хеша загрузки скрипт завершается с ошибкой. `prepare_ci_media.sh` ограничивает эту подготовку тремя минутами и при ошибке или таймауте устанавливает пакет Ubuntu; все тесты запускаются в обоих случаях. Подготовленный каталог и файлы APT размещаются в `RUNNER_TEMP`. Поставляемая пользователю версия приложения от этой подготовки не меняется.

Кэш снижает объём повторной загрузки, но для первого запуска скорость зависит от сети и не гарантирована. Если загруженный архив не уложился в лимит, время проверки включает также установку пакета Ubuntu.

```sh
python3 -B -m unittest tools.run_tests.test_prepare_ci_ffmpeg
```
