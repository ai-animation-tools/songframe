# Правила комплекса SongFrame

Комплекс для производства музыкальных клипов с помощью ИИ: настольное приложение, Python-инструменты, промпты агента и шаблон проекта. Клип ведётся только кнопками приложения: агента запускает приложение, вручную в папке клипа его не запускают и ничего ради такого режима не добавляют. Данные каждого клипа живут в отдельной папке проекта, созданной из [шаблона](templates/project/README.md); здесь хранится только код, документация и тестовые данные.

## Параллельная работа

- Независимые задачи в непересекающихся областях проекта выполнять параллельно субагентами. Каждому давать конкретную подзадачу, границы файлов, критерии приёмки, минимальные обязательные правила и только релевантный контекст.
- Если достаточно отдельного задания, запускать субагента без наследования всего чата. Не поручать ему читать весь репозиторий: передавать нужные файлы и сведения, разрешая точечное чтение зависимостей по необходимости.
- У общего изменяемого файла должен быть один владелец; зависимые шаги выполнять последовательно. Основной агент распределяет работу, интегрирует результаты и проверяет итоговое изменение.

## Текущий проект

- Инструменты работают с одной папкой проекта. Она определяется в таком порядке: аргумент `--project <папка>` в командной строке, переменная окружения `SONGFRAME_PROJECT`, файл `current-project.json` в постоянном каталоге состояния (его пишет приложение или [current_project](tools/current_project/README.md)), текущая папка, если в ней есть `plan/project.json`. Инструмент без проекта завершается с кодом 2.
- Пути `plan/...`, `assets/...`, `source/...` в командах и документации отсчитываются от папки проекта, а не от этого репозитория. В репозиторий комплекса данные клипов не записывать; состояние приложения и CLI хранится в userData либо SONGFRAME_LOCAL_DIR, не рядом с кодом.
- Владельцы сведений, защищённые исходники и порядок генерации описаны в README шаблона проекта и справках его папок; агенту нужные правила передаёт приложение в промпте задания.
- Эталонный проект служит образцом структуры и доступен только для чтения. Его расположение задаётся рабочим окружением; не вшивать путь эталона в инструкции и инструменты.

## Работа в репозитории

- Документацию, комментарии и сообщения коммитов писать по-русски; имена файлов, API и технические термины сохранять как есть. Комментарии кратко объясняют назначение решения.
- Не делать commit, push и публикацию без явного поручения. Платные запросы к сервисам генерации возможны только по правилам соответствующего скилла и с согласия пользователя.
- Приложение используют только два человека на своих компьютерах: владелец на Linux и его друг на Windows. Это локальное приложение, а не многопользовательский сервис. Не добавлять авторизацию, защиту от внешнего/параллельного доступа, обязательную сетевую изоляцию, дополнительные режимы безопасности и проверки «на всякий случай» без конкретной необходимости. Предпочитать простое решение; валидация данных, сохранность исходников и платных оригиналов, согласование платной отправки и защита от её случайного повтора остаются обязательными.
- Пути должны переживать перенос приложения/проекта и переустановку ОС: не вшивать абсолютные пути текущей машины, имя пользователя, checkout сборщика или временную папку AppImage. Ресурсы находить относительно приложения/комплекса, данные — относительно выбранного проекта, локальное состояние — в подходящем каталоге ОС. Абсолютные пути допустимо вычислять во время запуска и получать из пользовательского выбора; сохранённый путь может устареть, тогда достаточно понятной ошибки и повторного выбора.
- Нативные Windows-прогоны в VM выполнять только по явному поручению. CI и Release собирают Linux AppImage и Windows ZIP на Linux; проверка ZIP не исполняет Windows-код. Полную поддержку Windows не выводить из проверки отдельных сценариев или факта сборки ZIP. Запуск внешних Claude/Codex через менеджер заданий приложения поддерживается только на Linux; встроенный Kling работает на обеих ОС.
- До первого выпуска приложение использует один актуальный формат данных. Не добавлять чтение прежних форматов, fallback, поиск старых данных в Git или скрытые миграции ради совместимости. При изменении контракта согласованно обновлять код, шаблон, фикстуры и JSON единственного рабочего проекта `strateg-oleg`; его промпты и медиа сохранять без изменения. Разовые преобразования данных хранить вне репозитория.
- Разовые скрипты, отчёты и временные файлы хранить вне репозитория.

## Инструменты

Выбирать инструмент по [карте tools](tools/README.md) и читать README его папки; исходный код ради выяснения параметров не читать. Каждый инструмент лежит в `tools/<имя>/<имя>.py`, его тесты рядом как `test_*.py`, общие функции в `tools/common.py`. При добавлении или изменении инструмента обновлять README его папки и карту tools. Полный прогон тестов: `python3 -B tools/run_tests/run_tests.py`; он использует копию [проекта-образца](tools/testdata/README.md), настоящий проект не трогает. Стиль кода задаёт `pyproject.toml` (ruff), переформатирование существующего кода выполняется отдельным поручением.

## Приложение

Перед изменением интерфейса изучить и применять [правила UI](docs/ui/README.md): тему, структуру и компоновку страниц и элементов управления.

Страницы renderer лежат в `src/renderer/src/pages/{PageName}/{PageName}.tsx` и экспортируются через `pages/{PageName}/index.ts` и `pages/index.ts`. Страница собирается из самостоятельных компонентов в `pages/{PageName}/components/{ComponentName}.tsx` с локальным `components/index.ts`; один компонент — один файл. Публичный index.ts страницы экспортирует только саму страницу; внутренний barrel компонентов — только блоки, нужные снаружи их папки. Компоненты, используемые разными страницами, принадлежат общему `src/renderer/src/components`. Связанные только с одной страницей hooks, типы и функции остаются в её папке; не переносить монолит страницы целиком в одну новую обёртку.

Исходники приложения лежат в `src`: `main` (главный процесс, вся работа с файлами и процессами), `preload` (мост `window.api`), `renderer` (React + MUI), `shared` (типы и контракт API). Рендерер не обращается к файловой системе напрямую: любая новая возможность добавляется как функция главного процесса, канал IPC и метод в `src/shared/api.ts`. Логика главного процесса, не зависящая от Electron, проверяется тестами `src/main/*.test.ts` (`yarn test`); перед коммитом `yarn typecheck`. Страницы просмотра и редактирования не должны требовать Python и ffmpeg: они нужны только производству. Сборка идёт в `build/`, установщики в `build/release`; обе папки вне Git. Команды: `yarn dev`, `yarn build`, `yarn dist:linux`, `yarn dist:win`. AppImage после сборки оставлять в штатной `build/release`; не копировать бинарник за пределы репозитория без явного поручения.

Python запускается через общий `PythonLauncher`: в packaged только из `process.resourcesPath/runtime`, в dev допустим системный Python. Новые вызовы не должны самостоятельно искать Python или создавать второй spawn. Рецепт поставки и проверки — [scripts/runtime](scripts/runtime/README.md); `dist:*` собирает обе поставки на Linux; `dist:win` готовит Windows Python из закреплённых wheels и выпускает ZIP. Windows используется только для запуска готового приложения и проверки в VM, Node.js/Yarn/Python там не устанавливаются. Обе поставки включают FFmpeg/ffprobe через `yarn prepare:media` (`--target=win32-x64` для Windows); версии/хеши — `scripts/runtime/media-lock.json`. Веса faster-whisper устанавливаются отдельно в каталог данных пользователя или выбранную папку, в AppImage не входят. Окно разметки рекомендует модель по CPU/RAM и доступной NVIDIA CUDA, содержит кнопку фоновой загрузки и допускает ручной выбор; GPU не обязателен. Перед упаковкой проверяются ресурсы, в пользовательских действиях большие веса повторно не хешировать. Настройки settings.json, история, текущий проект и журналы используют одну постоянную папку состояния. Git необязателен для рабочих представлений; индекс и история требуют Git. Официальный Kling CLI включён в resources/kling и работает на Node из Electron; отдельная установка Node/npm не нужна. Python получает SONGFRAME_KLING_EXECUTABLE/SONGFRAME_KLING_SCRIPT; ELECTRON_RUN_AS_NODE включается только для дочернего CLI. Авторизацию и её обычный файл обслуживает сам Kling CLI, нового хранилища токенов приложение не создаёт. Авторазметка не требует `unshare`; сохранять локальную загрузку модели и офлайн-настройки без новой подсистемы изоляции.

Кнопки, запускающие Claude/Codex или открывающие интерфейс взаимодействия с агентом, обозначать присланными SVG через общий `AgentButton` (`src/renderer/src/components/AgentButton.tsx`). Это единственная кнопка действий агента, локальные копии с `AgentIcon` не создавать. Кнопка всегда показывает ровно один знак: сохранённого агента, а для уже выполняющегося задания — переданный явно provider; без выбранного агента — нейтральный значок. Подтверждение агентом в `ConfirmationDialog` — через `confirmAgent`. Кнопки отмены диалога, сохранения обычных файлов, локальных инструментов и прямых операций Kling не обозначать логотипами Claude/Codex.

## Скиллы

Папка [skills](skills/README.md) хранит тексты промптов, которые приложение вкладывает в задания агента в режиме предложения: агент возвращает JSON без записи файлов, shell и вызова инструментов, а применение и согласования выполняет приложение. Папки `.agents/skills` (Codex) и `.claude/skills` (Claude Code) репозитория содержат только символические ссылки на скиллы разработки комплекса в [dev-skills](dev-skills/README.md) (сборка, релиз, UI, контракты проектов); новый скилл разработки добавляется папкой там и двумя ссылками. Эта папка не входит в поставку. Текстовым этапам нужен явно сохранённый агент, генерации медиа — явно выбранный провайдер проекта; оба требуют проверенной доступности программы и входа. Выбранный агент не влияет на провайдеров медиа. Значения по умолчанию и поля `provider` без `provider_selected: true` не разрешают запуск. Провайдеры медиа описаны в реестре `src/shared/media-providers.ts`; общий код и интерфейс узнают о них из реестра, а не сравнением имён. Провайдер опор выбирается в `generation.image`: Codex с `image_gen` и проектной моделью агента `generation.image.model` (Codex находится автоматическим поиском, пустая проектная модель — из настроек Codex) либо Kling image через адаптер; видео использует `generation.video` (Kling), текстовые этапы — глобально выбранный Claude Code или Codex. Генерацию изображений Codex запускает приложение отдельным процессом Codex при любом выбранном агенте и без него; доступность определяется только наличием Codex и входом в него. Наличие Codex не подтверждает доступность его генератора изображений. Скачанный image original выбирается как непринятый кандидат; опоры утверждаются отдельно. Согласования производства ведёт приложение: вопрос записывается в `workflow.json` пакета, пользователь отвечает кнопками на странице «Производство»; платная отправка — только после ответа `send` по показанному SHA и цене. Новая попытка по сохранённому запросу создаётся отдельным действием и требует того же согласования. При неизвестной цене приложение допускает одну отправку после явного «Я согласен» для показанной оценки и отдельного подтверждения промпта. Согласие не переносится на обновлённую оценку, «Ещё» или повтор после ошибки; известную нехватку средств оно не отменяет.

## Шаблон проекта

[templates/project](templates/project/README.md) копируется приложением при создании клипа. Изменение контрактов хранения (манифесты, пакеты, очередь, сборка) вносится в шаблон и в инструменты одновременно; существующие проекты обновляются по поручению.
