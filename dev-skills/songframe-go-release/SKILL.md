# Выпуск SongFrame

Прочитай `AGENTS.md`, `packaging/README.md`, `packaging/windows/README.md` и фактические `Taskfile.yml`/`scripts/`. Сборку и smoke выполняй по соседнему [songframe-go-build](../songframe-go-build/SKILL.md). Собственного скрипта выпуска нет: механические шаги ниже выполняются `wails3 task`, `git` и `gh`.

Канал выпуска один — публичный `ai-animation-tools/songframe`: выпуски, сайт `https://ai-animation-tools.github.io/songframe/` (`www/` и `.github/workflows/pages.yml`), issues и адрес обновлений из приложения. Поставки: Linux x86_64 AppImage и deb, Windows amd64 NSIS. Первый Go-выпуск — `v1.0.0`; выпуски Electron 0.x и их теги `v0.*` остаются в истории, их не удаляют и не переносят.

## Объём поручения

- Просьба спланировать выпуск или написать описание разрешает только чтение, анализ diff, ревизию документации, план версии и черновик описания вне Git.
- Локальная сборка не разрешает выпуск. Изменение `packaging/VERSION`, commit, push, тег, создание релиза и публикация — только по явному поручению. Поручение на один шаг не распространяется на следующие.
- Разработка этого скилла не является поручением выпустить версию.
- Сохраняй явно заданные пользователем ограничения и не спрашивай повторно о действиях, уже включённых в действующее поручение. Изменения видимого результата (имена продукта и файлов, каталоги установки) согласуй с пользователем.

Перед работой сверь условия ниже с исходниками. Не объявляй выпуск готовым по номеру версии, наличию локального артефакта или названию задачи. Если условие не закрыто, выполни доступную часть и остановись перед ним, назвав конкретный остаток.

## Постоянные условия выпуска

1. **Имена файлов.** Скрипты выпускают `songframe-<VERSION>-linux-x86_64.AppImage`, `songframe-<VERSION>-linux-amd64.deb` и `songframe-<VERSION>-win-x64-setup.exe` — имена, которые ищут обновление из приложения и сайт.
2. **Идентификаторы продукта** (D-038 в spec): имя «SongFrame», бинарник `songframe`, app ID `tools.songframe.desktop`, профиль `songframe-desktop`, папка Windows `%LOCALAPPDATA%\Programs\SongFrame Desktop`, ключ удаления `SongFrameDesktop`. Без решения пользователя не меняются.
3. **Версия.** `packaging/VERSION` — единственный источник версии поставки; выпуск требует `X.Y.Z` без prerelease-суффикса, тег — `vX.Y.Z`. Числовая версия PE для Windows выводится из того же файла. `frontend/package.json` версией поставки не является.
4. **Обновление из приложения** (`internal/updates`): последний выпуск, вложение своей поставки по точному имени из условия 1, digest SHA-256 и размер. Каждый выпуск обязан содержать все три пакета; пропущенный пакет пользователи этой поставки увидят как «В выпуске нет пакета для этой системы». Проверка — `smoke:update` для AppImage и сценарий Windows из packaging/windows/README.
5. **Нативная Windows-проверка.** Сборка установщика на Linux не доказывает работу в Windows. Прогон в VM — только по явному поручению; без него Windows в описании указывается как проверенный только по составу установщика.
6. **Лицензии комплекта.** Состав уведомлений каждой поставки сверяй по `scripts/package-notices.py` и проверкам комплекта. Компоненты, устанавливаемые кнопкой, приносят свои уведомления сами.

## Порядок выпуска

### 1. Предусловия

- Определи точный исходный SHA, ветку и состояние дерева. Комплект собирается только из чистого зафиксированного дерева. Грязное дерево означает, что изменения в выпуск не войдут; другой SHA молча не собирай.
- Один раз на этом SHA выполни полный `wails3 task check:all`. Повторять его после каждого шага не нужно: после сбоя исправь причину, перезапусти упавшее, затем выполни полный прогон снова.
- Проверь сохранность результата по правилам `AGENTS.md`: тестовый клип `../test-projects/ogorod` с откатом через его Git (откат — только после ответа пользователя), готовый клип пользователя только на чтение со сравнением SHA дерева до и после.
- Ручная приёмка человеком обязательна. Финальное принятие видео и поведения остаётся за пользователем. Сборка и автоматические проверки ручную приёмку не заменяют.

### 2. Ревизия документации

Механическую сверку ссылок, путей, переменных и задач выполняет `wails3 task check:docs` (входит в `check:all`). Смысл текста она не проверяет, поэтому перед каждым выпуском сверь документы с кодом по существу:

- Возьми diff от тега предыдущего выпуска (`git diff --stat v<прежняя>..HEAD`) и по [карте кода](../../docs/code-map.md) определи документы-владельцы изменённых областей.
- Для каждого затронутого документа поручи субагенту без наследования чата сверить его утверждения с текущим кодом: процессы, условия, ограничения, имена кнопок, форматы файлов. Субагент получает документ, список изменённых файлов области и правило: сообщать расхождения с цитатой и местом в коде, ничего не менять.
- Расхождения разбирай по правилу «Документация и код» в `AGENTS.md`: описание устройства приводится к коду, а правило продукта, которому код не следует, — это ошибка кода или вопрос пользователю. Исправления документации входят в выпуск, исправления кода — по обычным правилам.
- В итоге перечисли проверенные документы и найденные расхождения; «расхождений нет» тоже результат.

### 3. Версия и описание

- Выбирай SemVer по существенному diff от исходников предыдущего опубликованного выпуска (`gh release list --repo ai-animation-tools/songframe`): patch — исправления, minor — возможности, major — несовместимые изменения формата проекта. Сообщения коммитов возможность не доказывают; читай diff.
- Запиши версию в `packaging/VERSION` и зафиксируй её вместе с исходниками до сборки, только если commit входит в поручение. Иначе подготовь план и назови этот шаг оставшимся.
- Описание пиши по-русски в новой папке под `/tmp`, не в Git: полезные пользователю изменения, действия при обновлении и известные ограничения. Не копируй приватный план, журнал и абсолютные пути.
- Ссылки на вложения давай прямыми версионными URL `https://github.com/ai-animation-tools/songframe/releases/download/v<версия>/<имя-файла>` только после фиксации точных имён. Не обещай подпись кода, отсутствие предупреждений SmartScreen или проверку в Windows без реализации и проверки.

### 4. Сборка поставок

- Linux: `wails3 task package:linux`, затем проверки по `songframe-go-build` (`smoke:host`, по задаче `smoke:appimage` и CPU smoke компонентов).
- Windows: `wails3 task package:windows`. Проверка состава встроена в рецепт и не исполняет Windows-код.
- deb: `wails3 task package:deb`, затем `smoke:deb`.
- Результат в `build/release/`: пакеты, `<имя>.sha256` и `<имя>.build.json`. Сверь по receipt версию, исходный SHA, `dirty: false`, размер и SHA-256 каждого файла. Receipt — внутренняя проверка: в выпуск и в общую папку VM он не прикладывается, без запроса пользователю не выводится.
- Сборки долгие: запускай их в фоне с журналом и не опрашивай без нужды. Опубликованный комплект под тем же номером не пересобирай.

### 5. Тег и публикация

Выполняется только по отдельному поручению выпустить эту версию.

1. Аннотированный тег `v<версия>` ставится на исходный SHA комплекта и отправляется в `origin`. Тег не переносится после публикации. Если CI относится к выпуску, его успешный запуск должен быть на этом SHA.
2. Создай черновик: `gh release create v<версия> --repo ai-animation-tools/songframe --draft --verify-tag --title "SongFrame <версия>" --notes-file <описание>`. Черновик не виден как `releases/latest`, поэтому на нём безопасно проверять вложения.
3. Загрузи пакеты и их `.sha256`: `gh release upload v<версия> <файлы> --repo ai-animation-tools/songframe`, без `--clobber`.
4. Проверь каждое вложение через GitHub API: `gh api repos/ai-animation-tools/songframe/releases/<id>`. Поля `digest: sha256:<хэш>` и `size` должны совпадать с локальным комплектом, `state` — `uploaded`. Также проверь версионный `browser_download_url`. Вложения обратно для проверки не скачивай. Отсутствующий или несовпадающий digest означает непроверенный результат.
5. Опубликуй: `gh release edit v<версия> --repo ai-animation-tools/songframe --draft=false --latest`. Затем повтори проверку вложений и убедись, что `releases/latest` указывает на этот выпуск.

При сбое сначала выясни фактическое состояние релиза, тега и вложений, затем повтори только недостающий шаг. Релиз и тег не удаляй, `--clobber` не применяй и под опубликованным номером не пересобирай без прямого поручения переиздать.

### 6. Сайт

Push в `main` с изменениями `www/**` публикует лэндинг. Скрипт страницы выбирает пакеты выпуска по суффиксам `-linux-x86_64.AppImage`, `-win-x64-setup.exe` и `.deb`. Без ответа GitHub ссылки ведут на страницу последнего выпуска; отсутствующий deb скрывает свою ссылку. После публикации проверь, что страница показывает версию и прямые ссылки на пакеты. Утверждения сайта о составе поставки и требованиях обновляй вместе с изменением поставки.

## Что сообщить пользователю

Раздельно укажи:

- план и выбранную версию;
- исходный SHA и состояние дерева;
- результат `check:all`, ревизии документации и ручной приёмки;
- собранные пакеты и выполненные smoke;
- состояние Git: тег;
- состояние публикации: черновик или published, проверка вложений по API;
- незакрытые условия.

Ссылку на релиз давай только после фактической публикации. Windows без VM-прогона указывай как проверенный только по составу установщика.
