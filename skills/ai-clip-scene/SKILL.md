# План Mxx в Kling

**План Mxx**: один ролик для окна из `plan/scenes.json`; сценарная сцена может включать несколько планов. Аргумент `scene` принимает `12`, `M12`, `M23.5`; сопоставляй код с реестром, не со старыми номерами сцен. Правила комплекса (текущий проект, запреты на commit и push, платные запросы только по скиллу) в [AGENTS.md комплекса](../../AGENTS.md); правила конкретного клипа, защищённые исходники и владельцы сведений в `AGENTS.md` папки проекта. Здесь они не повторяются.

Согласования идут в приложении комплекса: оно показывает пакет плана (опоры, промпт, таблицу запроса, результат) и записывает решение пользователя в `workflow.json` пакета. В чат возвращаются короткие карточки, а не таблицы и промпты. Опоры создаёт выбранный в проекте backend изображений: Codex с `image_gen` либо Kling. Текстовый агент Claude Code или Codex от этого выбора не меняется; ограничения конкретной среды описаны в разделе «Среда без image_gen».

## Вызов

| Задача                                                         | Codex                                                 | Claude Code                               |
| -------------------------------------------------------------- | ----------------------------------------------------- | ----------------------------------------- |
| Подготовка плана в режиме `approval=shot` (по умолчанию)       | `$ai-clip-scene scene=M32`                            | `/ai-clip-scene scene=M32`                |
| Согласование опор по одной для сложного плана                  | `$ai-clip-scene scene=M32 approval=frame`             | `/ai-clip-scene scene=M32 approval=frame` |
| Партия независимых планов (до трёх)                            | `$ai-clip-scene batch=M01,M03,M05`                    | `/ai-clip-scene batch=M01,M03,M05`        |
| Самый ранний неготовый план или выбор из очереди               | `$ai-clip-scene scene=next`                           | `/ai-clip-scene scene=next`               |
| Таблица статусов без подготовки и расхода                      | `$ai-clip-scene list=all` (`progress`, `completed`)   | то же с `/`                               |
| Исправленная попытка: новый пакет и новое разрешение на расход | `$ai-clip-scene scene=M32 retry="Мира ближе к окну"` | то же с `/`                               |
| Одна новая попытка по конкретному сохранённому запросу         | `$ai-clip-scene scene=M32 regenerate=true`            | то же с `/`                               |
| Продолжить или повторить с этапа существующего пакета          | `$ai-clip-scene scene=M32 stage=prompt`               | то же с `/`                               |
| Приёмка готового результата без повторного показа              | `$ai-clip-scene accept=M32 attempt=02`                | то же с `/`                               |
| Другой проект                                                  | `project=/путь/к/папке`                               | то же                                     |

Явный Mxx имеет приоритет над очередью. Без кода при непустой очереди предложи выбрать ожидающий пакет; при пустой очереди и `scene=next` первого кандидата `shot_status --next`. Списки ничего не генерируют и не спрашивают о запуске. Повторный вызов без `stage` продолжает текущий этап пакета по `shot_workflow show`, а не начинает заново. `stage=` называет этап, с которого продолжить или повторить: `description`, `frames`, `prompt`, `request`, `result` соответствуют этапам `description_review`, `keyframes_review`, `prompt_review`, `request_choice`, `downloaded` пакета; возврат назад разрешён на любой этап, всё после него согласуется заново. `accept=Mxx attempt=NN` берёт пакет `plan/batches/Mxx-attempt-NN` (или `plan/awaiting/Mxx`, если попытка там) в состоянии `downloaded` и сразу идёт на этап 6.

Папка проекта без аргумента берётся из текущего проекта комплекса (`python3 -B tools/current_project/current_project.py --json show`; `is_project` должен быть `true`). В checkout команды ниже запускаются из корня комплекса с `--project <папка>`, если проект задан аргументом. В установленном управляемом проекте используй `.songframe/run-tool ИМЯ_ИНСТРУМЕНТА …` из корня проекта вместо `python3 -B tools/ИМЯ_ИНСТРУМЕНТА/ИМЯ_ИНСТРУМЕНТА.py …`: launcher находит ресурсы приложения после переноса; не ищи checkout по старому абсолютному пути. Пути `plan/...`, `assets/...`, `source/...` отсчитываются от папки проекта.

## Предложение для приложения: output=proposal

Обложка из `source/manifest.json.cover` служит только оформлением проекта. Не добавлять её автоматически в референсы, опорные кадры, входы генерации или историю подготовки сцены; использовать явно выбранные референсы сцены и кастинга.

При `output=proposal` сначала прочитай [контракт приложения](references/app-proposal.md). Верни только один JSON `ProductionStageProposal` для заданного `stage=description|prompt|request`: описание с промптами опор, видеопромпт либо черновик запроса. Не изменяй файлы, не вызывай `ask`/`wait`, генерацию, платные команды или commit. Приложение проверяет и применяет предложение, ведёт `workflow.json` и запрашивает согласование; прямого Kling submit у агента в UI-режиме нет.

После принятия описания приложение выбирает адаптер из `generation.image.provider`. Codex запускает отдельное задание с `image_gen`, которое возвращает кандидатов `stage=frames`; это не продолжение читающего `output=proposal`. Kling готовит один замороженный image-запрос для одной Kxx: подготовка ещё не отправляет генерацию. Далее приложение ведёт отдельное подтверждение SHA/стоимости, `submit`, `resume` и выбор полученного оригинала как непринятого кандидата; подробности в [контракте приложения](references/app-proposal.md#frames). Видео готовит адаптер Kling из `generation.video`.

Без `output=proposal` действует ручной порядок ниже: агент готовит пакет, ставит `ask --executor agent` (это значение по умолчанию) и ждёт `wait`. В управляемом пакете с `executor=app` продолжение выполняет приложение; не перехватывай такой пакет ручной отправкой или `regenerate=true`.

## Настройки генерации

Настройки независимы: глобальный текстовый агент Claude Code/Codex готовит текстовые предложения; глобальный `imageAgent` задаёт путь и модель Codex CLI для image-заданий; проектный `generation` в `plan/project.json` содержит отдельные `video` и `image`. Смена backend изображений не меняет текстового агента или профиль Codex.

`generation.video` содержит `provider`, `resolution`, `aspect_ratio`, `watermark`, `duration_rule` и необязательные `model`/`options`; поддержанный backend видео — Kling. `generation.image` выбирает `provider: codex|kling` и необязательные `model`, `resolution`, `aspect_ratio`, `outputs`, `watermark`, `options`. Это предпочтения, а не перечень возможностей. Для Kling image фактические аргументы вроде `img_resolution` и `quality`, доступные модели, значения и входные слоты берутся из актуальных capabilities; для Codex размеры и форматы определяет исполнитель `image_gen`. Форматы входных референсов и фактический формат скачанного оригинала проверяются отдельно.

На этапе 1 прочитай настройки: `generation_settings(load_project(), kind='video')` либо `kind='image'` из `tools.scene_registry.scene_registry`. Отсутствующий или неверный нужный блок диагностируется до соответствующей генерации; другой блок не подставляет значения. Неизвестного провайдера не подменяй известным. Старый плоский `generation` читается как видео с совместимым image backend Codex; само открытие/чтение не пишет миграцию. Явное сохранение переводит настройки в вложенный формат, сохраняет неизвестные поля и не меняет прежние frozen requests.

Правило `generation.video.duration_rule` определяет `D` по [kling-cli.md](references/kling-cli.md#длительность-и-монтажный-запас); `generation.video.watermark: false` требует оригинал видео без логотипа. Ограничения конкретной модели, включая пропорции 21:9, подтверждай для её команды и вида медиа, а не переносом правил видео на изображения.

### Опоры Kling в том же workflow

После принятия описания подготовь одну Kxx через адаптер Kling: точный промпт, локальные референсы и параметры → `kling_request prepare` → `shot_workflow set-image-request --dir D --frame Kxx --request-dir image-NN`. Эта команда сохраняет image-историю отдельно от видео `request_dir` и создаёт `image_request_choice` с вариантами `send/park/revise`. Подтверждение относится к одному показанному image SHA и актуальной цене. В `executor=app` стоимость и отправку ведёт приложение; в `executor=agent` основной поток показывает таблицу, ждёт соответствующий `send` и отправляет ровно эту попытку.

После `submit` продолжай только тот же ID через `resume`/`watch`: `image_submitted` → `image_downloaded`. `select-image --dir D --file ПУТЬ_ИЗ_DOWNLOADS` копирует выбранный original без перекодирования в кандидата Kxx с `approved: false`. Это не принятие опоры и не перенос в assets. Следующая Kxx получает свой запрос и своё решение о расходе. После выбора всех нужных кандидатов отдельно поставь `ask --stage keyframes_review`; только `approve` этого вопроса принимает опоры. Команды и проверки — в [README shot_workflow](../../tools/shot_workflow/README.md#опоры-через-kling-в-том-же-workflow).

## Согласования в приложении

Каждый этап заканчивается вопросом в `workflow.json` пакета, который приложение показывает рядом с материалами, и ожиданием ответа. Протокол ведёт `shot_workflow`:

| Команда                                                         | Назначение                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `propose --dir D K01 ПУТЬ`                                      | Зарегистрировать кандидата опоры: файл копируется в пакет, `approved: false`. Повторный `propose` того же ID заменяет кандидата                                                                                                                                                                                                                        |
| `ask --dir D --stage ЭТАП [--question ТЕКСТ] [--options a,b,c]` | Записать ожидающий вопрос `pending_decision` для приложения и очистить прежний ответ. Этапы вопросов: `description_review`, `keyframes_review`, `image_request_choice`, `prompt_review`, `request_choice`, `downloaded`, `edit_review`. Для image-вопроса сначала используется `set-image-request`. Без `--options` приложение показывает кнопки этапа |
| `wait --dir D [--timeout СЕК] [--interval СЕК]`                 | Блокировать выполнение, пока пользователь не ответит. Печатает JSON `{"stage", "verdict", "note", "at"}`. Код 0: решение получено; 2: время вышло, вопрос остаётся и ждать можно дальше; 3: пакет изменён снаружи                                                                                                                                      |
| `decide --dir D --verdict … [--note ТЕКСТ]`                     | Записать ответ; вызывает приложение по кнопкам «Принять», «Вернуть с замечанием», «Отправить», «Сохранить», «Принять результат», «Исправить», «Собрать пробу». Для `keyframes_review` вердикт `approve` принимает всех кандидатов опор, для `prompt_review` принимает промпт; `revise` сопровождается `note` с правками                                |

Вердикты: `approve`, `revise`, `send`, `park`, `accept`, `retry`, `review`. Варианты по умолчанию зависят от этапа: `approve`/`revise` для описания, опор, промпта и участка; `send`/`park`/`revise` для image- или video-запроса (`revise` с заметкой возвращает к промпту или подготовке, отправки нет); `accept`/`retry`/`review`/`revise` для результата. Порядок на каждом этапе одинаков: субагент готовит материалы, основной поток пишет в чат одну строку (что подготовлено и где лежит), затем `ask`, затем `wait`. По `approve` идти дальше; по `revise` вносить только правки из `note` и снова `ask`; молчание и истёкший `wait` согласием не являются. После кода 2 повтори `wait` без нового `ask`, сообщив одной строкой, что решение ещё ожидается. После кода 3 прочитай `shot_workflow show`: если пользователь изменил опоры или промпт в приложении, это корректировка с его стороны, продолжай с затронутого этапа; если вопроса в пакете больше нет, задай его снова. Полученное решение не переспрашивай; изменение запроса или другой этап требуют собственного решения.

Платная отправка: после таблицы запроса и `cost_check` вызови `ask --stage request_choice`; затем `wait`. Только вердикт `send` разрешает ровно один `kling_request submit --confirm <request_sha256>` этого пакета; `park` сохраняет пакет в очередь через `shot_workflow park`. Для пакета из очереди и после пополнения счёта вопрос формулируется как «Запустить этот запрос?» (`ask --stage request_choice --question "Запустить этот запрос?" --options send,park`) после заново показанной таблицы.

Если среда не позволяет ждать (приложение не запущено, пользователь попросил вести диалог текстом), допускается обычный текстовый вопрос в чате с теми же вариантами и тем же ограниченным смыслом; форма вопроса среды, если она есть, тоже подходит. Полученный текстовый ответ запиши в пакет сам: `decide --verdict … --note …`, иначе принятие опор и промпта не состоится. Не дублируй вопрос приложения требованием набрать ответ текстом.

## Субагенты

Вся подготовка этапа делегируется субагенту, если среда их поддерживает (Codex и Claude Code поддерживают; в Codex субагент умеет `image_gen`). Субагент получает план, папку пакета, этап и, при `revise`, текст `note`; он читает настройки генерации, `scene_registry`, `continuity_brief` и кастинг, пишет описание, рисует опоры и регистрирует их через `propose`, составляет `video-prompt.txt`, готовит пакет (`prepare`, `cost_check`, `set-stage request_choice`), ждёт `watch` и собирает `contact_sheet`. В основной чат он возвращает только короткую карточку: план, этап, что сделано, абсолютные пути к файлам, что ждёт решения, замеченные несоответствия по чек-листу. Длинные таблицы, описания и промпты в чат не выводятся: они видны в приложении и лежат в файлах пакета.

В основном потоке остаются вызовы `ask` и `wait`, разбор вердикта, решения о деньгах (`submit`, `park`, `regenerate`), `accept_shot` и карточка пользователю. Субагент не вызывает `ask`, `wait`, `decide`, `submit` и не задаёт вопросов пользователю; если ему не хватает сведений, он возвращает карточку с вопросом, а основной поток решает, спросить ли пользователя. В среде без субагентов те же шаги выполняются в основном потоке, но в чат по-прежнему выводится только карточка.

## Деньги

1. Платный запрос только после вердикта `send` на таблицу этого пакета (или `send` на заново показанную таблицу отложенного пакета); в партии вердикт ставится на каждом пакете отдельно. Выбор плана, принятие описания, опор и промпта расход не разрешают.
2. `submit --confirm <request_sha256>` ровно один раз. При `submitting` или `submission_unknown` действуй по [recovery.md](references/recovery.md); повторный `submit` запрещён.
3. При вердикте `cost_check` `insufficient_balance` или `cost_or_balance_unknown` ничего не отправляй, даже при `send` или `regenerate=true`: `park` с этой причиной и сообщение пользователю. Баланс не пополняй.
4. После «счёт пополнен»: `cost_check` заново, таблица заново, `ask` «Запустить этот запрос?»; прежний `send` не действует.
5. Платные изображения Kling, `retry`, дополнительные результаты и любой запрос с изменёнными входами, промптом, моделью, длительностью или ценой требуют отдельного решения по показанному запросу. Явное поручение `regenerate=true` разрешает только одну новую попытку конкретного показанного сохранённого запроса с проверенной ценой (раздел ниже); оно не распространяется на изменённый запрос или следующий retry. После ответа сервиса запиши расход: `cost_check learn`.

## Повтор запроса: `regenerate=true`

`scene=M01 regenerate=true` — конкретное поручение на одну новую попытку показанного сохранённого video-запроса с проверенной ценой. Уже данное поручение не переспрашивается; оно не разрешает изменённые параметры, другие image-запросы, автоматические retries или неограниченные расходы. Это делает `python3 -B tools/regenerate_shot/regenerate_shot.py M01 --submit --json` (см. [README инструмента](../../tools/regenerate_shot/README.md)): он находит замороженный запрос плана (сначала последний пакет в `plan/batches` или `plan/awaiting` с `request_dir/request.json`, затем снимок принятого комплекта `assets/shots/M01/generation-request.json` в формате замороженного запроса), сверяет его с блоком `generation.video` проекта, создаёт новый пакет `plan/batches/M01-attempt-NN` с `retry_of`, готовит попытку (`prepare`), печатает `request_sha256` и таблицу `cost_check`, с `--submit` отправляет ровно один раз, записывает расход, ждёт (`watch`) и ставит этап `downloaded`. Без `--submit` он только готовит пакет и печатает таблицу. Сводку `contact_sheet --package` после получения делает скилл (субагент), затем `ask --stage downloaded`.

Правила: только относящееся к показанному запросу явное поручение `regenerate=true` разрешает одну новую отправку, поэтому уже полученное решение не запрашивается снова; вердикт `cost_check` `insufficient_balance` или `cost_or_balance_unknown` всё равно останавливает отправку (инструмент не отправляет, скилл делает `park` с этой причиной и сообщает). Если данных запроса нет, снимок в другом формате или от другого провайдера (например, генерация делалась в стороннем сервисе), инструмент завершается кодом 3 с сообщением; расхождение запроса с `generation.video` проекта тоже останавливает повтор. В обоих случаях скилл ничего не выдумывает, сообщает пользователю причину и предлагает обычный путь по этапам 1–4. Результат показывается как на этапе 5, приёмка отдельная; прежний результат и принятый комплект не удаляются и не заменяются автоматически. Каждая следующая попытка требует собственного явного поручения; автоматический повтор `regenerate=true` прежним разрешением не покрывается; с `batch=` аргумент не сочетается.

## Корректировки, retry и stage

Корректировка меняет только названное. Если меняется более ранняя опора, вернись к ней; изменение только времени не требует повторного принятия неизменённого изображения, но пакет готовится заново. `retry="…"` это новая попытка через `shot_workflow init --retry-of <прежний пакет>` с новым разрешением на расход: принятые совместимые опоры переносятся через `propose` и принимаются заново одним вердиктом, промпт и таблица проходят этапы 3–4. Исходный результат не удаляется до решения о замене; принятый комплект в assets не заменяется кандидатом автоматически. Поиск дополнительных дефектов в видео в `retry` не входит.

`stage=` возвращает существующий пакет на названный этап (`set-stage` назад разрешён всегда): `stage=frames` повторяет предложение опор, `stage=prompt` правку и согласование промпта, `stage=request` новую подготовку запроса (новый `request_sha256`, новый вердикт `send`), `stage=result` повторный показ результата и вопрос этапа 5. Всё, что стоит после названного этапа, недействительно и согласуется заново.

## Партия

`batch=M01,M03,M05` готовит до трёх планов одним диалогом по [batch.md](references/batch.md): сначала `shot_status --independent` (конфликт по состоянию исключает план, соседей по шкале подтверждает пользователь), затем `shot_workflow init --batch` для каждого, описания, опоры и промпты всех планов по одному раунду на этап: субагент готовит пакеты, основной поток ставит `ask` в каждом пакете и ждёт `wait` по очереди. Таблицы запросов с суммой расхода; вердикт `send` или `park` ставится в каждом пакете отдельно, отправка по одному `submit` на пакет с вердиктом `send`; один `watch` на всё; приёмка по планам.

## Очередь

Отложенный пакет живёт в `plan/awaiting/Mxx` по [README очереди](../../templates/project/plan/awaiting/README.md). При продолжении: `shot_workflow check` (хеши, актуальность постановки и унаследованного состояния), `kling_request status`, `cost_check`, таблица заново, `ask --stage request_choice --question "Запустить этот запрос?" --options send,park`, `wait`. Если запрос уже отправлен, продолжай его ID через `resume` или `watch`; если видео скачано, покажи результат по этапу 5. Пакет удаляется только `accept_shot --clean` после переноса принятой сцены в assets и проверки комплекта.

## Среда без image_gen

Если выбран Codex image backend, но `image_gen` в этой среде недоступен, назови ограничение на этапе 1. При выбранном Kling backend текстовый Claude Code может продолжать обычную подготовку через тот же app/agent workflow. Запасные источники для недоступного генератора: кадр из принятого клипа соседнего плана (`accepted_edit.video` из assets), кадр от пользователя (файл регистрируется через `propose`), `kling text_to_image` / `image_to_image` с показом точного запроса и отдельным разрешением на расход, а также вариант «нарисовать опоры в Codex и продолжить здесь»: пакет общий через файлы, поэтому `$ai-clip-scene scene=Mxx stage=frames` в Codex зарегистрирует опоры, а `/ai-clip-scene scene=Mxx` в Claude Code продолжит с текущего этапа. Остальные этапы одинаковы для обеих сред. Файлы показывает приложение; в чате давай абсолютный путь.

## Что скилл не делает

Не оценивает видео художественно и не ищет дефекты без поручения (чек-лист непрерывности не оценка, а сверка с записанным состоянием). Не собирает полный аниматик. Не делает commit и push. Не меняет `source/` и кастинг молча. Речевые планы готовит по [lipsync.md](references/lipsync.md), порученную проверку видео по [quality-and-state.md](references/quality-and-state.md).
