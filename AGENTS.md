# Правила SongFrame

SongFrame — комплекс для производства музыкальных клипов с помощью ИИ: настольное приложение на Go + Wails 3 с React/MUI-интерфейсом, встроенные промпты агента, руководства провайдеров и шаблон проекта. Агента запускает приложение, клип ведётся только кнопками приложения; ручной режим работы агента в папке клипа не поддерживается и ради него ничего не добавляется. Данные каждого клипа живут в отдельной папке проекта, созданной из шаблона; здесь хранятся код, ресурсы, документация и синтетические тестовые данные.

## Главный критерий

**Результат работы программы не меняется без решения пользователя.** Сохраняются:

- записываемые файлы и форматы проекта, статусы и fingerprints;
- тайминги, промпты, согласования платных операций, медиарезультаты и пользовательские процессы.

Внутреннее устройство выбирай сам: пакеты, типы, алгоритмы, процессы, границы API. Если решение лучше, оптимальнее или проще в сопровождении, применяй его сразу, без предварительного согласования; причину кратко запиши в сообщении коммита. Найденную ошибку исправляй, а не воспроизводи. Не добавляй абстракции ради самого рефакторинга.

Сохранность доказывай проверками:

- **Эталоны.** `testdata/golden/<домен>/` — зафиксированные входы и ожидаемые выходы ([описание](testdata/golden/README.md)). Не пересоздавать их из текущей реализации: расхождение означает изменение результата. Эталон меняется только по решению пользователя вместе с кодом; причина — в сообщении коммита.
- **Настоящие клипы.** Записывающие сценарии — только на тестовом клипе или копии в отдельном Git с откатом после проверки. Готовый клип пользователя — только чтение: он открывается без ошибок и без изменения файлов (SHA дерева до/после).

Спрашивай пользователя только о том, что меняет видимый результат или продукт, о платных операциях, публикации и commit/push.

## Документация и код

Источник истины зависит от того, что утверждается:

| Утверждение | Источник истины | Если код с ним расходится |
| --- | --- | --- |
| Правила продукта, процессы пользователя, согласования платных операций, форматы проекта | документы (`AGENTS.md`, `docs/`, README областей) | ошибка кода — исправить код; если правило выглядит устаревшим, спросить пользователя |
| Наблюдаемое поведение | эталоны `testdata/golden` и тесты | изменение результата — по «Главному критерию» |
| Внутреннее устройство: пакеты, типы, алгоритмы, файлы | код и его комментарии | устарел документ — исправить документ |

- Расхождение не разрешать молча: в итоге работы назвать его и какую сторону исправил.
- Перед изменением найди область в [карте кода](docs/code-map.md): там её пакеты, страницы и документы-владельцы. Изменил поведение области — обнови её документы в том же коммите.
- Новый пакет или страница получает содержательный комментарий и строку в `internal/repodocs/areas.go`, затем `wails3 task docs:map`. Карта генерируется: вручную её не править.
- История проекта — только в последнем разделе README. В коде, комментариях и документах не упоминать прежние версии, их файлы, коммиты, этапы приватного плана и решения `spec`: текст описывает то, что есть сейчас, и почему.
- Документы описывают назначение, правила, процессы и контракты, а не пересказывают код: подробности устройства живут в комментариях рядом с кодом, где их правят вместе с ним.
- `wails3 task check:docs` (входит в `check:all` и отдельный CI `docs.yml`) сверяет ссылки и якоря, пути в `обратных кавычках`, переменные `SONGFRAME_*`, задачи Taskfile, скрипты yarn, актуальность карты и отсутствие упоминаний прежней версии вне раздела «История» README. Смысл текста она не проверяет: его сверяет ревизия документации перед выпуском ([songframe-release](dev-skills/songframe-release/SKILL.md)).

## Продукт

- **Пользователи.** Приложение используют два человека на своих компьютерах: владелец на Linux и его друг на Windows. Это локальное приложение, а не сервис. Не добавлять авторизацию, защиту от внешнего/параллельного доступа, обязательную сетевую изоляцию и проверки «на всякий случай». Обязательны: валидация данных, сохранность исходников и платных оригиналов, согласование платной отправки и защита от её случайного повтора.
- **Один формат данных.** Принятый формат проектов сохраняется. Не добавлять чтение прежних форматов, fallback, скрытые миграции и поиск старых данных в Git. Разовые преобразования и скрипты хранить вне репозитория.
- **Пути.** Пути переживают перенос приложения/проекта и переустановку ОС: не вшивать абсолютные пути машины, имя пользователя или временную папку AppImage. Ресурсы находить относительно приложения, данные — относительно выбранного проекта, состояние — в каталоге ОС. Пути `plan/...`, `assets/...`, `source/...` отсчитываются от папки проекта. Сохранённый путь может устареть: тогда достаточно понятной ошибки и повторного выбора.
- **Агенты.** Codex/Claude — внешние программы, приложение запускает их без shell. В Windows — `.exe` и обёртки npm `.cmd`, без окна консоли. Текстовым этапам нужен явно сохранённый агент. Названия агентов брать из реестра `frontend/src/shared/agent-providers.ts` (`agentTitle(provider)`), в общих текстах UI говорить об «агенте». Кнопки агента — только общий `AgentButton`: ровно один знак, причина блокировки — в `disabledReason`, подтверждение — через `confirmAgent`.
- **Провайдеры медиа.** Сервисы генерации описаны в реестре `frontend/src/shared/media-providers.ts`. Общий код и интерфейс узнают о провайдере только из реестра: не сравнивают имена и не пишут название сервиса в тексты. Особенности провайдера — в одном документе на вид медиа `resources/providers/<вид>/<id>.md` ([порядок добавления и удаления](resources/providers/README.md)) и в его Go-адаптере `internal/providers/<id>/`; «Указания агенту» вкладываются в промпт. Общая логика тестируется на провайдере `test`; удаление провайдера не должно ломать остальные тесты.
- **Платные операции.** Отправка — только после ответа `send` по показанному SHA и цене. Неизвестная цена допускает одну отправку после явного «Я согласен» и отдельного подтверждения промпта. Согласие не переносится на новую оценку, «Ещё» или повтор после ошибки и не отменяет известную нехватку средств. Платные запросы в разработке — только с согласия пользователя.
- **Компоненты.** FFmpeg/ffprobe, ONNX Runtime и модели не входят в базовый пакет: их находят в системе или ставят кнопкой. Без них проект открывается и редактируется.

## Устройство

- **Renderer.** React/MUI-интерфейс; файловую систему не читает и процессы не запускает.
- **Связь с Go.** Единственный путь — контракт `window.api` (`frontend/src/shared/api.ts`): каждый метод отображается на сгенерированный binding Wails (`frontend/bindings`, вручную не править). Ручные валидаторы ответов Go не писать. Go отдаёт `[]` вместо `nil`, соответствие типов проверяет `typecheck`. Каждый метод контракта реализован в адаптере `frontend/src/platform/`; новый метод добавляется вместе с Go-реализацией, тест адаптера проверяет, что заготовок без реализации не осталось. Вне контракта — только служебные страницы нативной проверки окна: они обращаются к bindings через адаптер `frontend/src/platform/native-check.ts`; страницы и компоненты bindings не импортируют.
- **Go.** Владеет файлами проектов, заданиями, процессами, состоянием провайдеров и медиасервером: `internal/app` — Wails-сервисы, `internal/<область>` — логика.
  - Внешние программы запускаются только через общий запуск процессов: без консоли в Windows, с отменой и завершением потомков.
  - Длительные операции идут через общий менеджер заданий.
  - Проектный JSON записывается атомарно.
- **Ресурсы.** Шаблон проекта, промпты, руководства провайдеров и шрифты встраиваются в бинарник ([resources](resources/README.md)). Изменение контракта хранения (манифесты, пакеты, очередь, сборка) вносится в шаблон, код и эталоны одновременно; существующие проекты обновляются по поручению.
- **Комментарии.** У функций, методов, структур, интерфейсов и модулей писать содержательные русские комментарии: что делает, зачем устроено так и с чем взаимодействует. Для экспортируемых деклараций и нетривиальной логики это обязательно. По необходимости описывать владельца состояния, побочные эффекты, ошибки/отмену, конкурентный доступ, единицы и инварианты. Не комментировать каждую строку и не пересказывать сигнатуру; при изменении поведения обновлять пояснения.

## Интерфейс

- Перед изменением UI применять [songframe-ui](dev-skills/songframe-ui/SKILL.md) и [правила UI](docs/ui/README.md).
- Storybook поддерживается в том же изменении: истории затронутого компонента, родительской страницы и их локальные модели API. В результате перечислить обновлённые истории и браузерные проверки.
- Русские тексты интерфейса централизованы в `frontend/src/shared/texts/` по [правилам текстов](docs/ui/texts.md).
- Минимальное и стартовое окно — **1320×860**; на нём проверяются светлая и тёмная темы. Размеры меньше (960×640, 1280×720) в обязательную приёмку не входят. Геометрия окна — в `main.go`, размер браузерной проверки — в `frontend/playwright.config.ts`.

## Поставки

Поставки:

- Linux x86_64 — AppImage (`wails3 task package:linux`) и deb-пакет (`wails3 task package:deb`);
- Windows amd64 — установщик NSIS (`wails3 task package:windows`).

Все поставки собираются локально на Linux; CI их не собирает.

- Сборку и проверку поставки выполнять по [songframe-build](dev-skills/songframe-build/SKILL.md) и `packaging/README.md`.
- Выпуск — по [songframe-release](dev-skills/songframe-release/SKILL.md).
- Нативные Windows-прогоны в VM — только по явному поручению; сборка установщика не доказывает работу в Windows.
- Не превращать правку рецепта в пересборку или запуск. Дорогие сборки и матрицы выполнять в порученном объёме.
- SHA и build receipts — внутренние проверки: без запроса не выводить их пользователю и не класть в общую папку VM.

## Работа в репозитории

- Документация, комментарии и сообщения коммитов — по-русски; имена файлов, API и технические термины сохранять как есть.
- Commit, push, remote, релиз и платные запросы — только по поручению.
- Не добавлять в Git приватные документы spec, клипы, веса, аудио, видео, токены, журналы, локальные отчёты и абсолютные машинные пути.
- Разовые скрипты, отчёты и временные файлы хранить вне репозитория.
- Проверки: `wails3 task check:all`; после правки только документации достаточно `wails3 task check:docs`. Адресно — по `Taskfile.yml` и `frontend/package.json`. Во время работы гонять тесты изменённой области; после сбоя исправить и перезапустить только упавшее (`go test ./pkg -run Имя`, `yarn test файл`, `yarn test:storybook --grep` после `yarn build-storybook`), а не весь `check:all`. Полный прогон — один раз в конце; при параллельной работе его выполняет основной агент после слияния. Контракты проектов и DTO — по [songframe-project-contract](dev-skills/songframe-project-contract/SKILL.md).

## Параллельная работа

- Независимые задачи в непересекающихся областях выполнять параллельно субагентами. Каждому давать конкретную подзадачу, границы файлов, критерии приёмки, минимальные обязательные правила и только релевантный контекст.
- Если достаточно отдельного задания, запускать субагента без наследования всего чата и не поручать ему читать весь репозиторий.
- У общего изменяемого файла один владелец, зависимые шаги — последовательно. Основной агент распределяет работу, интегрирует результаты и проверяет итоговое изменение.
