# Сценарий клипа: предложение для приложения

Инструкции задания, которое запускает приложение на странице «Сценарий». Задание работает в режиме `output=proposal`: прочитай переданный контекст и верни ровно один JSON-документ без Markdown, пояснений и текста вокруг. Не записывай файлы, не вызывай shell и инструменты. Приложение само проверяет предложение, показывает сравнение и применяет его отдельным действием пользователя; согласование между проходами тоже ведёт приложение.

Сценарий строится в два прохода. Первый (`treatment`) даёт кастинг и трактовку: кто действует и что происходит в каждой части песни. Второй (`scenes`) даёт реестр сцен: планы с кадровыми окнами, постановкой и изменениями состояния. Третий вид задания (`revise`) дорабатывает выбранные планы по замечанию. Детерминированное (кадровые окна, карту референсов, проверки) делает приложение, смысл пишет агент.

## Контекст задания

Приложение передаёт JSON: `pass`, `selectedIds`, текст идеи клипа (`idea`), точный текст песни по строкам (`lyrics`), манифест исходников (`manifest`: трек, текст, идея, `references` с типами), разметку `timing` (строки и части песни со временем, `duration_decoded`), кастинг (`cast`; для `treatment` — черновик по референсам исходников с сущностью `world`), трактовку (`treatment`), реестр (`scenes`: каркас для `scenes`, текущий реестр для `revise`) и замечание `note`.

Постановку сочиняй из идеи и слов песни, привязывая действие к строкам и их времени. Обложка проекта в контекст не входит и не используется: изображения для постановки берутся только из `references` манифеста и явно заданных изображений кастинга.

## pass=treatment: кастинг и трактовка

Ответ: `{"schemaVersion":1,"pass":"treatment","cast":{...},"treatment":{...}}`. `cast` и `treatment` — полные документы форматов `CastFile` и `TreatmentFile` с `schema_version: 1`.

- Общее описание: у сущности с референсом `appearance` представляет тот же текст, что `description` референса в манифесте. Не создавай независимые версии внешности для исходников и кастинга. Предложенная правка `appearance` показывается пользователю и после применения становится общим описанием; роль персонажа записывай отдельно в `role`. Существующий выбор `images`, его порядок и пустой список сохраняй, если пользователь не просил их изменить.
- Кастинг: возьми переданный черновик и словарь `properties`, сохраняя существующие ID и референсы. Для каждой сущности заполни `role`, `appearance` (только то, что следует из идеи и референсов; не выдумывай внешность, которой нет на изображениях) и `initial_state` по словарю `properties` её типа. У `world` заполни `initial_state` по словарю `properties.world`.
- Если в идее есть герои без референсов, добавь сущности с пустым `images`; файлы не выдумывай. Приложение покажет, что их нужно нарисовать или загрузить до производства.
- Трактовка: `{"schema_version": 1, "logline": "одна фраза", "sequences": [{"id": "intro", "title": "...", "direction": "что происходит и зачем", "start": 0, "end": 18.74, "entities": ["world", "performer"], "lipsync": false, "max_shot_seconds": 6}]}`. Границы частей бери из `sections` разметки; части идут подряд от 0 до `timing.duration_decoded`. `entities` перечисляют, кто в части на экране, только по ID кастинга; `lipsync: true` для частей, где герой поёт в кадре. Логлайн и `direction` каждой части заполнены, без `ЗАПОЛНИТЬ`.

## pass=scenes: реестр сцен

Ответ: `{"schemaVersion":1,"pass":"scenes","scenes":{...}}`. `scenes` — полный `ScenesFile` с `schema_version: 1`.

Приложение передаёт каркас, построенный по утверждённым кастингу и трактовке: окна по строкам песни и инструменталу, `references` из кастинга, заготовки `ЗАПОЛНИТЬ`. Сохрани ID, `original`, `sequence`, `start_frame`, `end_frame_exclusive`, 30 fps и сплошную шкалу каркаса. Деление и объединение планов выполняет редактор приложения, не это задание.

Заполни каждый план без `ЗАПОЛНИТЬ`:

- `camera`: крупность и движение;
- `action`: что происходит, одним или двумя предложениями, без технических рецептов и истории согласований;
- `continuity`: стык с соседями;
- `references`: кто и что в кадре — только коды из карты `references` реестра (сущности кастинга с изображениями); героев без изображений описывай в `action`;
- `lipsync` и `card.primary_reference` — код из карты `references` реестра, обычно главный из `references` этого плана;
- `state_from` и `state_changes` по правилам ниже;
- `derived_from: {"shot": "Mxx"}` — только когда постановка явно собирает план из материала другого плана: стоп-кадр, повтор или замедление его клипа. Такой план не генерируется: как используется материал (отметка стоп-кадра, замедление), опиши в `action`. Источник — другой план без собственного `derived_from`. Не выдумывай повторы ради экономии и не ставь поле планам с собственным действием; у обычного плана поля нет;
- общие визуальные правила всего клипа — в `visual_direction` реестра.

## pass=revise: доработка выбранных планов

Ответ: `{"schemaVersion":1,"pass":"revise","patches":[{"id":"M01","action":"..."}]}`. Для каждого выбранного ID верни только изменяемые поля постановки: `title`, `notes`, `camera`, `action`, `continuity`, `references`, `lipsync`, `card`, `state_from`, `state_changes`, `derived_from` (`null` снимает признак производного плана). `id` выбирает план и не меняется.

Меняй только то, чего касается замечание, и только планы из `selectedIds`. Запрещены поля других планов, кадровые окна, `original`, `sequence` и глобальные поля реестра. Соседи переданы только как контекст: не переписывай их молча и не расширяй список ID. Конфликт с соседями не устраняй их правкой: его решает пользователь в редакторе.

## Состояние героев и мира

Состояние складывается из трёх источников с разными владельцами: кастинг (`appearance`, `role`, `initial_state`, `images`, словарь `properties` по типам), реестр (`state_from` и `state_changes` каждого плана) и вычисление `before`/`after` по цепочке `state_from`. Отдельного реестра состояния нет; код сущности из кастинга — ключ и в `references` плана, и в `state_changes`. Типы сущностей открыты: персонажи, транспорт, локации, предметы, мир, животные и другие.

- Разовые жесты остаются в `action`. Всё, что сохраняется дальше по сюжету (загрязнение, повреждения одежды и внешности, усталость, состояние транспорта, положение и принадлежность предметов), записывай в `state_changes` того плана, где событие происходит, только по словарю свойств кастинга: `before` уточняет вход, `after` — результат действия. Верхний уровень `state_changes` — только фазы `before` и `after`, коды сущностей вложены в них: `{"after": {"hero": {"clothes_condition": "брюки по колено в грязи"}}}`, где `hero` — код сущности кастинга типа `character`, а `clothes_condition` — свойство из её словаря; план без изменений — `{}`. Не копируй изменения во все последующие планы и не повторяй начальное состояние.
- `state_from` указывает сюжетного предшественника, а не соседа по шкале: `"M01"` — состояние после M01, `{"scene":"M01","phase":"before"}` — перед ним, `{"scene":"M01","phase":"same"}` — повтор того же события без собственных изменений, `null` — начало сюжетной линии с `initial_state` кастинга. Флешфорвард, возврат во времени и параллельные действия сопоставляй по сюжету; сюжетные циклы запрещены.
- Отсутствие героя в нескольких планах, смена ракурса, склейка или чистый референс не возвращают его в исходное состояние. Мытьё, переодевание и восстановление предметов не выдумывай.
- Устойчивое последствие отличай от временного положения предмета и разового жеста; принадлежность предмета (`owner`) не доказывает его положение.
- Имена свойств — `snake_case` из словаря `properties` типа сущности или её `initial_state`, значения — непустые строки по-русски; `null` снимает свойство, унаследованное от предыдущих планов. Записывай установленные условия, а не придуманные подробности. Из этих записей приложение строит врезку непрерывности словами, поэтому состояние каждого плана должно читаться как внятное описание кадра.

## Где что записывать

| Что изменилось | Куда записать |
| --- | --- |
| Общее описание внешности, роль, начальное состояние, выбранные изображения | Предложение кастинга: `appearance`, `role`, `initial_state`, `images` (только в `treatment`); приложение согласует общее описание с референсом |
| Действие, камера, сторона объекта, взгляд, непрерывность, набор референсов | Поля плана в реестре |
| Сохраняющиеся последствия и их сюжетный источник | `state_changes` и `state_from` плана, где событие происходит |
| План собирается из материала другого плана (стоп-кадр, повтор, замедление) | `derived_from` плана; как используется материал — в `action` |
| Правило всей части песни | `direction` части трактовки |
| Общие визуальные ограничения | `visual_direction` реестра |

Записывай действующую постановку без рассказа о том, кто и когда её изменил.

## Общие ограничения

- Все поля и значения должны пройти доменные проверки приложения: известные ID кастинга, свойства из словаря, сплошная шкала, отсутствие `ЗАПОЛНИТЬ`.
- Не меняй исходный текст песни, идею, разметку, изображения и промпты исходников; общее описание предлагай только через `appearance` кастинга; конец трактовки и сцен согласуй с `timing.duration_decoded`.
- Используй только объявленные изображения и свойства кастинга; неизвестную деталь не объявляй установленной.
- Размер ответа не больше 256 KiB.
