# Разработка SongFrame

Руководство по запуску из checkout, устройству приложения, сборке и выпуску поставок. Возможности продукта и пользовательские инструкции находятся в [README](../README.md), обязательные правила разработки — в [AGENTS.md](../AGENTS.md).

Менеджер агентских заданий, API, права и ограничения описаны в [агентских заданиях](agents.md), предложения и применение сценария — в [сценарном процессе](scenario-workflow.md), согласования и границы приёмки — в [производственном процессе](production-workflow.md), ручные пробы — в [монтаже](montage.md). Контракты Python-инструментов находятся в [карте tools](../tools/README.md) и README каждого инструмента. Рецепт подготовки встроенного Python, медиа и проверок поставки поддерживается в [scripts/runtime](../scripts/runtime/README.md).

## Состав

Страницы «Производство», «Сцены», «Проверки», «Аниматик» и «Монтаж пробы» открываются через общий `RequireScenario`. Пока нет доступных сцен, используется один полноширинный `ScenarioRequired` с одинаковым сообщением и действиями; дочерняя страница и её проверки среды ещё не запускаются. Готовность сценария определяет общий `readScenarioRegistry`, независимо от наличия инструментов генерации. Статусы Python и провайдеров генерации вычисляются отдельно от наличия сцен.

```text
tools/              Инструменты на Python: запросы провайдеров генерации, приёмка, проверки, сборка аниматика, пакет для монтажёра
tools/testdata/     Синтетический проект-образец «Пробный клип» с небольшими тестовыми медиа
skills/             Тексты промптов, которые приложение вкладывает в задания агента: ai-clip-scenario, ai-clip-scene
templates/project/  Шаблон папки нового проекта: структура, README, .gitignore
src/main/           Главный процесс Electron: проекты, статус, исходники, среда, запуск инструментов
src/preload/        Мост window.api между рендерером и главным процессом
src/renderer/       Интерфейс: React + MUI, светлая и тёмная темы
src/shared/         Типы и контракт API, общие для обеих сторон
build/              Сборка приложения (build/app) и установщики (build/release); вне Git
```

## Зависимости разработчика и временные внешние зависимости

Таблица ниже относится к запуску из checkout и сборщику. В готовые Linux AppImage и Windows-установщик входят Python, Python-библиотеки, FFmpeg/ffprobe и клиенты встроенных [провайдеров генерации](providers/README.md). Отдельно устанавливать их пользователю не нужно. Веса модели устанавливаются отдельно по [инструкции по модели распознавания](../README.md#модель-распознавания). Разработка без `yarn prepare:runtime` может использовать системный Python; клиенты провайдеров генерации — Python-модули `tools/<id>_request/`, отдельно их устанавливать не нужно, а особенности подключения при запуске из checkout описаны в документах провайдеров.

Для запуска интерфейса из checkout нужны Node.js и Yarn; готовому приложению их отдельная установка не требуется. Страница «Среда» показывает готовность встроенных ресурсов и необязательных внешних CLI.

В корне checkout выполните `nvm install` и `nvm use`: обе команды читают `.nvmrc`, как и CI. Репозиторный `.gitignore` содержит исключение для этого файла, поэтому глобальное правило `.nvmrc` не мешает хранить общую версию в Git.

### Готовое приложение на Windows

Сборка выполняется на Linux командой `yarn dist:win`. Пользователь Windows получает установщик `songframe-<версия>-win-x64-setup.exe` (NSIS, в один щелчок): он без прав администратора ставит приложение в профиль пользователя, `%LOCALAPPDATA%\Programs\songframe`, создаёт ярлыки на рабочем столе и в меню «Пуск» и запускает SongFrame. Новая версия ставится запуском её установщика поверх прежней; папка состояния приложения при обновлении и удалении сохраняется. Установка Node.js, Yarn, Python и pip не требуется. Для проверки встроенного runtime в папке установки есть `check-runtime.cmd`, он пишет отчёты в ту же папку; инструкция лежит в `ПРОЧТИ.md` рядом с EXE.

Windows-поставка включает Python, FFmpeg/ffprobe и клиенты встроенных провайдеров; в VM на прежней ZIP-поставке проверены runtime, медиа, загрузка модели и распознавание, сам установщик в Windows не проверялся; вход в провайдера проверялся прежним официальным CLI, собственный клиент провайдера в VM не проверялся. Модель устанавливается отдельно на любой ОС. Внешние Claude/Codex устанавливаются отдельно; менеджер агентских заданий приложения сейчас поддерживает только Linux.

Автоматическое распознавание на Linux и Windows запускается напрямую с `--allow-network`: флаг снимает проверку OS-изоляции, модель всё равно читается только с диска, скачивание отключено. Настраивать user namespaces или AppArmor для разметки не требуется.

## Запуск и проверки из checkout

Команды выполняются из корня checkout после установки [зависимостей разработчика](#зависимости-разработчика-и-временные-внешние-зависимости):

```sh
yarn install          # зависимости и бинарник Electron
yarn dev              # запуск с HMR интерфейса renderer
yarn build            # сборка в build/app
yarn prepare:runtime  # встроенный Python и библиотеки для текущей ОС
yarn smoke:runtime    # проверка переноса runtime без Python в PATH
yarn start            # запуск собранного приложения
yarn typecheck && yarn test
yarn lint             # ESLint по src/, scripts/ и конфигурации сборки (ошибки и предупреждения не допускаются)
yarn format:check     # Prettier: проверка форматирования; yarn format переформатирует
yarn dist:linux       # AppImage со встроенными Python и FFmpeg, без весов модели в build/release
yarn dist:win         # Windows-установщик NSIS, собирается на Linux без Wine
```

Команда `yarn dev` запускает `electron-vite dev`: HMR обновляет renderer, но главный процесс и preload автоматически не пересобираются. После изменения IPC, методов `window.api` или кода `src/main` и `src/preload` требуется полный ручной перезапуск `yarn dev`; перед ним сохраните или скопируйте текущие черновики из открытого приложения. Простое обновление страницы оставляет прежнюю сборку main/preload и не добавляет новый метод API.

Перед коммитом выполняется `yarn typecheck`. Сборка приложения находится в `build/app`, установщики — в `build/release`; обе папки вне Git. AppImage после сборки остаётся в штатной `build/release`: копирование бинарника за пределы репозитория требует явного поручения.

## Устройство и стиль кода

Исходники настольного приложения на Electron, TypeScript, React и MUI лежат в `src/main`, `src/preload`, `src/renderer` и `src/shared`. Главный процесс выполняет работу с файлами и процессами; renderer не обращается к файловой системе напрямую. Новая возможность проходит через функцию главного процесса, IPC и метод в `src/shared/api.ts`. Независимая от Electron логика главного процесса проверяется тестами `src/main/*.test.ts`. Просмотр и редактирование не требуют Python и FFmpeg — они нужны производству.

Страницы находятся в `src/renderer/src/pages/{PageName}/{PageName}.tsx`, экспортируются через `pages/{PageName}/index.ts` и `pages/index.ts`. Публичный `index.ts` страницы экспортирует только её. Внутренние компоненты, hooks, типы и функции остаются в папке страницы; общие для нескольких страниц компоненты — в `src/renderer/src/components`. Один компонент — один файл. Подробные правила, в том числе правила `AgentButton` и PythonLauncher, находятся в [AGENTS.md](../AGENTS.md#приложение).

Правила темы, структуры и компоновки интерфейса собраны в [документации UI](ui/README.md).

Типы проверяются раздельно: `tsconfig.node.json` — главный процесс и preload, `tsconfig.web.json` — интерфейс; `src/shared` входит в оба, и `yarn typecheck` проверяет каждое окружение со своими библиотеками. Корневой `tsconfig.json` — общий проект только для редактора и инструментов навигации (например, MCP-сервера Serena): в нём «найти все ссылки» на код `src/shared` видит и главный процесс, и интерфейс. Ошибки окружения (DOM в главном процессе и наоборот) он не ловит — это делает `yarn typecheck`.

Стиль кода приложения задают `.prettierrc.json` (точка с запятой в конце выражения, одинарные кавычки, строки до 160 знаков, пустая строка в конце файла) вместе с `.editorconfig` (UTF-8, LF, отступ два пробела, в Python четыре) и `eslint.config.mjs` (рекомендованные правила ESLint и typescript-eslint, правила хуков React, импорты типов через `import type`); Prettier и ESLint не спорят благодаря `eslint-config-prettier`. Python-инструменты, шаблон и скиллы этими проверками не охвачены.

Стиль Python задаёт `pyproject.toml` (ruff); переформатирование существующего кода выполняется отдельным поручением. Изменение контрактов хранения одновременно вносится в `templates/project` и инструменты; существующие проекты обновляются по поручению. Данные клипов хранятся в отдельных проектах, а не в репозитории комплекса.

## Отладка

Переменные окружения для отладки: `SONGFRAME_LOCAL_DIR` (отдельная папка локального состояния), `SONGFRAME_ROUTE` (стартовый маршрут, например `#/environment`), `SONGFRAME_SCREENSHOT` (путь PNG: снимок окна и выход), `SONGFRAME_PRICING_FILE` (подмена базовой таблицы цен провайдера в тестах); тестовый провайдер `test` и его переменные — в [документации провайдеров](providers/README.md#тестовый-провайдер), отладочные переменные конкретного сервиса — в его документе. Клавиша F12 открывает инструменты разработчика.

### Журналы и отчёт для разработчика

Все журналы лежат в каталоге состояния (`localDir`: Linux `${XDG_CONFIG_HOME:-~/.config}/songframe`, Windows `%APPDATA%\songframe` или `SONGFRAME_LOCAL_DIR`) и переживают перезапуск и сбой программы.

- `jobs/<id>.log` — вывод задания инструментов; рядом `jobs/<id>.json` — его сведения `JobInfo` без текста лога (название, вид, проект, шаги со статусами, статус, `startedAt`/`finishedAt`, код, причина ошибки). Сведения записываются атомарно при старте, смене шага и завершении. При запуске окна `Jobs` загружает последние 200 заданий, более старые `.json` удаляются вместе с `.log`; задание, которое по сведениям ещё выполнялось, получает статус `interrupted` («Прервано закрытием или сбоем программы») и сохраняется так. Повреждённый файл сведений пропускается. Текст лога прошлого сеанса читается из файла по `jobs:get`/`jobs:copyText`. Служебные проверки поставки (`SONGFRAME_LINUX_SMOKE`, `SONGFRAME_RUNTIME_SMOKE`) журнал пользователя не загружают; смена ресурсов на странице «Среда» продолжает тот же журнал.
- `jobs/agent-<id>.json` — задания агента ([агентские задания](agents.md)).
- `logs/app.log` — журнал сбоев: строки `время [вид] текст`, продолжение стека с отступом. Первая строка сеанса `[session] Запуск: SongFrame …; Electron …; Node …; ОС …; архитектура …`. Пишутся `uncaughtException` и `unhandledRejection` главного процесса, `render-process-gone` и `unresponsive` окон, `child-process-gone`, ошибка запуска (`startup`) и ошибки renderer (`renderer:error`, `renderer:unhandledrejection`: `window` `error`/`unhandledrejection` подключены в `src/renderer/src/main.tsx` и уходят по каналу `diagnostics:rendererError`). Домашний каталог заменяется на `~`, похожие на токены значения скрываются; тела запросов и сообщения агента не пишутся. Больше 1 МБ — файл переименовывается в `logs/app.1.log` (хранится одна предыдущая копия).
- `logs/session.json` — `{ startedAt, version, pid, clean }`: при старте окна записывается `clean: false`, на `will-quit` — `clean: true`. Если прошлый сеанс не помечен чистым, это записывается в `app.log`, а окно один раз показывает предупреждение со ссылкой на «Журнал заданий».

Кнопка «Сохранить отчёт для разработчика» на странице «Журнал заданий» сохраняет через диалог один файл `songframe-report-<дата>.txt` (до 5 МБ): версии приложения, Electron, Node, ОС и архитектуры, packaged ли сборка, каталог состояния, признак аварийного прошлого сеанса, `app.1.log` и `app.log`, сведения последних 50 заданий инструментов с последними 200 строками их журналов и сводку последних 20 заданий агента (id, задача, провайдер, статус, время, код выхода, диагностика — без промптов и вывода). `settings.json`, файлы входа `providers/*/` и содержимое проектов в отчёт не входят; домашний каталог заменён на `~`. Кнопка «Скопировать журнал» у задания копирует его сведения и журнал в буфер обмена.

Чтобы получить сведения у пользователя (в том числе на Windows без Git и терминала): попросите открыть «Журнал заданий», нажать «Сохранить отчёт для разработчика» и прислать сохранённый файл. Если окно не открывается, тот же каталог состояния можно заархивировать вручную без `settings.json` и `providers/`.

## CI и релизы

GitHub Actions: `.github/workflows/ci.yml` на каждый pull request и push в `main` запускает `yarn lint`, `yarn format:check`, тесты релизного скрипта (`yarn test:release`), `yarn typecheck`, `yarn test`, набор тестов Python (`tools/run_tests --jobs` по квоте CPU раннера, с ffmpeg и Pillow) и тесты скриптов поставки `scripts/runtime/test_*.py`. Раннер не запускается, если изменились только корневые `*.md`, `LICENSE`, `docs/` (кроме `docs/providers/`, их читают тесты), `dev-skills/`, папки настроек агентов и редактора и лэндинг `www/`. Для такого коммита CI запускают вручную (`gh workflow run CI --ref main`), когда он нужен выпуску. Поставки в CI не собираются: их собирает и проверяет локально скилл `songframe-build` или [выпуск релиза](#выпуск-релиза). Код не подписывается. Раннеры выбираются переменной `CI_LINUX_RUNS_ON`. Их сеть обрывает большое приветствие TLS Node 24 к Cloudflare (MTU в порядке), поэтому CI задаёт `OPENSSL_CONF=scripts/ci/node-openssl.cnf`: Node перестаёт предлагать постквантовый `X25519MLKEM768`, и его приветствие TLS снова становится маленьким. `NODE_OPTIONS` через `$GITHUB_ENV` runner не принимает. В образе раннеров нет `libfribidi`, без которой Pillow раскладывает текст карточек без Raqm, поэтому CI доустанавливает `libfribidi0`, если Raqm недоступен. CI кэширует загрузку Electron и архив FFmpeg.

### Выпуск релиза

Релиз собирается на машине владельца и публикуется в GitHub Releases командой `yarn release` (`scripts/release/release.mjs`); порядок для агента — скилл `songframe-release`. Поставки не проходят через артефакты Actions, поэтому квота хранилища Actions выпуск не ограничивает. Нужны вход `gh auth login` и всё, что требует сборка обеих поставок (см. [проверку поставок](#проверка-поставок)).

1. `yarn release plan [--version X.Y.Z]` только читает Git и GitHub: предлагает версию (первый выпуск — `version` из `package.json`, дальше следующий patch), показывает предыдущий опубликованный тег, коммиты и diff с него, чистоту дерева, совпадение с `main` на GitHub, состояние CI коммита и релиза.
2. `version` в отслеживаемом `package.json` — каноническая версия выпуска: после выбора согласованного номера её обновляют до commit/push исходников. `plan` только предлагает номер и файл не меняет. Описание пишется по-русски в `build/releases/notes-<версия>.md`.
3. `yarn release prepare --version X.Y.Z --notes build/releases/notes-X.Y.Z.md` требует чистого дерева, версии выше опубликованной и точного совпадения `--version` с зафиксированным `package.json`; несовпадение останавливает подготовку до тега и сборки. Команда сама не меняет `package.json`, ставит локальный аннотированный тег `vX.Y.Z` и собирает обе поставки с той же `SONGFRAME_VERSION`: версия попадает в пакеты через `extraMetadata.version` electron-builder. Затем выполняет `smoke:runtime`, smoke AppImage в Docker и проверку установщика. Восемь файлов выпуска (AppImage, установщик, их SHA256, `linux-distribution.json`, `linux-smoke-result.json`, `windows-installer-check.json`, `THIRD_PARTY_LICENSES.md`) жёсткими ссылками закрепляются в `build/releases/vX.Y.Z/` вместе с описанием и `release.json` с их хешами. Повторный prepare той же версии с тем же описанием переиспользует готовый комплект; каталог незавершённой подготовки нужно удалить вручную.
4. `yarn release publish --version X.Y.Z` требует, чтобы исходный коммит комплекта был в `main` на GitHub и прошёл CI. Локальная сборка не заменяет lint, типы и тесты; отменённый запуск перезапускают через `gh run rerun`. Команда сверяет комплект с `release.json`, отправляет тег, создаёт черновик `SongFrame X.Y.Z`, загружает файлы, сверяет `digest`, размер и состояние каждого вложения через GitHub API, публикует релиз как latest и заново проверяет все вложения по версионным адресам. Квитанция сохраняется в `build/releases/vX.Y.Z/public-release.json`. После сетевого сбоя ту же команду можно повторить: совпадающие вложения используются повторно, пустые незавершённые удаляются только в черновике. Опубликованные файлы, теги и релизы скрипт не перезаписывает.

Нативный Windows smoke в выпуск не входит: VM-прогоны выполняются отдельно по явному поручению.

Опубликованный выпуск становится обновлением для установленных копий. Блок «Обновления приложения» на странице «Настройки» (`src/main/updates.ts`) по кнопке читает `releases/latest` через GitHub API, берёт вложение своей ОС по имени из комплекта (`songframe-<версия>-linux-x86_64.AppImage` или `songframe-<версия>-win-x64-setup.exe`) и принимает только версионный адрес этого репозитория. Скачанные байты сверяются с размером и `digest` из того же ответа API, который проверяет `publish`; собственная подпись описания не используется. Пакет хранится в `<папка состояния>/updates`, где остаётся только последний скачанный. Установка в Windows запускает установщик NSIS и закрывает приложение, в Linux атомарно заменяет файл из `APPIMAGE` и перезапускает его. Поэтому имена поставок и черновик до публикации — контракт обновлений: переименование вложений требует изменить `packageName`. Linux не может перезапустить AppImage через `app.relaunch`: помощник Electron запускается из точки монтирования, которая исчезает вместе с приложением. Поэтому новый файл запускает отдельный `bash` после выхода процесса. Перед запуском он закрывает унаследованные дескрипторы и получает окружение без путей старого монтирования, иначе старый AppImage оставался бы смонтирован (`relaunchAppImage`). Обновление 0.1.9 → 0.2.0 проверено 31.10.2026 в Windows 11 VM вручную и в Linux на собранном AppImage: проверка, скачивание, замена и перезапуск без старого монтирования.

Лэндинг [ai-animation-tools.github.io/songframe](https://ai-animation-tools.github.io/songframe/) лежит в `www/` как статическая страница без сборки и публикуется workflow `.github/workflows/pages.yml` при изменении `www/` в `main` (в настройках репозитория Pages → Source: GitHub Actions). Ссылки на скачивание страница берёт из последнего релиза через GitHub API по суффиксам имён поставок из `scripts/release/release.mjs`; без ответа API они ведут на страницу релиза. Иллюстрация первого экрана нарисована в CSS, `images/social.jpg` — снимок этого экрана 1280×640 для превью ссылки.

`yarn dist:*` подготавливает встроенный Python и включает его, инструменты и шаблон проекта в ресурсы приложения вне ASAR. Ресурсы определяются относительно приложения, путь checkout сборщика в код не записывается. Логи и локальное состояние packaged-приложения хранятся в userData. Системный Python/pip и отдельная установка Python-библиотек пользователю такой сборки не нужны. Подготовка, версии и проверки описаны в [scripts/runtime](../scripts/runtime/README.md).

Linux AppImage и Windows-установщик включают Python и FFmpeg/ffprobe. **Веса модели в поставки не входят:** их нужно один раз скачать по [инструкции по модели распознавания](../README.md#модель-распознавания). Модель хранится отдельно и используется повторно после обновления приложения. Распознавание работает локально на CPU/int8 либо NVIDIA CUDA, без обращения к Hugging Face во время анализа. В Windows VM проверены runtime, FFmpeg/ffprobe, вход в провайдера генерации (прежним официальным CLI; собственный клиент провайдера в VM не проверялся), загрузка модели и локальное распознавание; полный производственный цикл требует отдельной нативной приёмки. Клиенты встроенных провайдеров написаны на Python и входят в поставку вместе с инструментами ([документы провайдеров](providers/README.md)). На странице «Среда» сначала проверяется вход: без авторизации доступна кнопка «Войти», при действующей — «Сменить аккаунт»; токены входа хранятся в каталоге состояния приложения (`providers/<id>/`). Git устанавливается отдельно и необязателен для локального проекта и рабочих представлений, но нужен для истории/индекса; встроенным провайдерам не нужны системные Node.js/npm и отдельные программы. Внешние Claude/Codex по-прежнему устанавливаются отдельно. Проверка встроенного runtime не подтверждает доступность внешних провайдеров и всех производственных операций: их проверяют отдельно в пользовательском окружении. `yarn build` обновляет только `build/app`; для нового AppImage выполняйте `yarn dist:linux`.

### Версия локальной сборки

Перед локальной сборкой скилл `songframe-build` читает `version` рабочего `package.json`, версию в HEAD (`git show HEAD:package.json`) и последний опубликованный релиз через `gh api repos/ai-animation-tools/songframe/releases/latest --jq .tag_name`. Без явного номера берётся зафиксированная версия, если рабочий файл содержит ту же версию и она не ниже опубликованной по SemVer; устаревший номер требует обновления канонической версии до сборки. Если успешный запрос списка releases без draft/prerelease подтверждает, что выпусков ещё нет, используется зафиксированная версия; одного 404 от `latest` недостаточно. Сетевой отказ и ошибка доступа не подтверждают отсутствие выпусков: без явного номера автоматический выбор останавливается, с явным номером сборка возможна с указанием, что свежесть не проверена.

Версия, прямо названная пользователем для локальной сборки, передаётся через `SONGFRAME_VERSION=<версия> yarn dist:linux` или `SONGFRAME_VERSION=<версия> yarn dist:win`; `package.json` ради такого override не меняется. Например, при канонической версии `0.4.0` можно отдельно собрать запрошенный AppImage `0.3.0`. Это не переиздание: опубликованные вложения, тег и локальный архив `build/releases/v0.3.0/` сохраняются. Проверка установщика получает выбранный номер в `--version`, а smoke AppImage — точный путь свежего файла через `--appimage`, поскольку в `build/release` могут лежать несколько версий.

Комплект в `build/releases/v<версия>/` хранит жёсткие ссылки на файлы из `build/release`: перезапись прежнего inode может повредить архив. Перед повторной сборкой сверяют SHA-256 и размеры архивных файлов с `release.json`, сохраняют копию метаданных вне перезаписываемой папки и проверяют inode/link count перезаписываемых путей. Для совпадающих inode удаляют только соответствующие пути в `build/release` (unlink, без усечения файла), чтобы сборщик создал новые файлы; ссылки и файлы в архиве не удаляют. Это относится и к общим именам отчётов/лицензий, если они будут перезаписаны. После сборки повторно сверяют архив с сохранёнными метаданными.

### Проверка поставок

`yarn dist:linux` собирает конечный файл в `build/release`. Веса модели не включаются. В `build/release` остаются только поставки и их отчёты: перед сборкой `scripts/runtime/release-dir.mjs` удаляет прежние SHA256 и отчёт проверки этой платформы (новый файл получает их только после своей проверки), после сборки — промежуточные `*-unpacked` и служебные файлы electron-builder. Публикация из `dist:*` отключена (`--publish never` внутри команды). Сборщику нужны Node.js/Yarn, tar, zstd, Docker (smoke AppImage) и `7z` (проверка установщика); пользователю готового приложения системные Python, Node.js, Yarn и FFmpeg не нужны. Для графического приложения остаются обычные библиотеки Linux-десктопа. Шрифт карточек аниматика DejaVu Sans входит в комплекс вместе с лицензией (`tools/render_animatic_cards/fonts/`), устанавливать его в систему не нужно.

Выпуск после сборки проверяет переносимый Python (`yarn smoke:runtime`) и выполняет smoke **конечного AppImage** в Ubuntu 22.04. Контейнер содержит графические библиотеки, виртуальный экран и espeak-ng для синтеза короткой тестовой речи; Python/Node/Yarn/Git/FFmpeg в ОС не устанавливаются. Сеть при запуске контейнера отключена. Загрузка тестовой tiny-модели происходит заранее в отдельный сборочный каталог `build/runtime/smoke-model`, за пределами упаковываемого runtime. Это техническая фикстура проверки, а не выбранная пользователем модель.

Отдельно ту же проверку можно запустить с Docker и любой заранее скачанной моделью CTranslate2:

```sh
yarn prepare:smoke-model
yarn smoke:appimage --docker --appimage="$PWD/build/release/songframe-<выбранная-версия>-linux-x86_64.AppImage" --model="$PWD/build/runtime/smoke-model" --output=/tmp/songframe-appimage-check
```

Для повторного прогона используйте новую папку отчёта. Smoke создаёт собственный проект с пробелами/кириллицей, загружает MP3, размечает его внешней моделью, сохраняет подтверждённую строку, строит каркас сцен/карточки и проверяет рабочую папку. Затем переносит проект, временно переименовывает AppImage **внутри build/release**, проверяет повторный запуск и состояние и возвращает файл на штатное место. Пользовательские проекты и текущий выбор не используются. Окна приложения, платные запросы и агентные CLI Claude/Codex не запускаются.

Контейнер использует extract-and-run, поскольку FUSE в нём недоступен; `--no-sandbox` задаётся только этому проверочному запуску. Настройки sandbox обычного приложения не меняются. `NO_CLEANUP` сохраняет распаковку до удаления контейнера. На обычном Linux основной вариант — прямой запуск AppImage. Если FUSE недоступен, поддерживается [официальный extract-and-run](https://docs.appimage.org/user-guide/troubleshooting/fuse.html#extract-and-run-type-2-appimages). Работа на произвольном старом дистрибутиве или CPU не обещается: Python-wheels/FFmpeg требуют glibc 2.28+, Linux x64 и совместимый CPU; целевая базовая проверочная ОС — Ubuntu 22.04, локальная — Ubuntu 24.04.

Перед упаковкой проверяется состав ресурсов и отсутствие весов/репозиторных тестов, сохраняются версии и уведомления поставщиков. Лицензии CPython и статических зависимостей извлекаются из полного архива того же выпуска python-build-standalone; недостающие в wheels тексты FlatBuffers/tokenizers закреплены URL и SHA256. В готовом приложении есть `resources/distribution.json` и `resources/THIRD_PARTY_LICENSES.md`, рядом с AppImage — их копии `linux-distribution.json` и `THIRD_PARTY_LICENSES.md`. После успешного smoke появляются `<имя>.AppImage.sha256` и `linux-smoke-result.json`; выпуск прикладывает эти файлы вместе с проверенным AppImage. Для Windows-установщика `scripts/runtime/check-windows-installer.py` извлекает его содержимое через `7z` без запуска и создаёт `<имя>.exe.sha256` и `windows-installer-check.json`: проверяются целостность архива, ресурсы, деинсталлятор и целевая платформа, без нативного Windows smoke ([подробнее](../scripts/runtime/README.md)).

## Перенос приложения, состояние и проекты

На Linux настройки, текущий проект, история и журналы находятся в `${XDG_CONFIG_HOME:-$HOME/.config}/songframe` — постоянном userData, общем для разработки и AppImage. Файлы: `settings.json`, `current-project.json`, `projects.json`, журналы заданий в `jobs/`, журнал сбоев и файл сеанса в `logs/` ([журналы и отчёт](#журналы-и-отчёт-для-разработчика)). Они сохраняются после перемещения или обновления AppImage. Ресурсы `tools`, `templates`, `runtime` читаются из приложения, записи в каталог AppImage и временный mount не нужны. Файлы моделей хранятся отдельно в каталоге данных по [инструкции по модели распознавания](../README.md#модель-распознавания).

Повреждённый JSON не сбрасывается молча: сообщение указывает файл, его нужно исправить или перенести в резервную папку. Запись настроек и выбора проекта атомарная, при ошибке сохранения прежний файл остаётся целым.

`SONGFRAME_LOCAL_DIR` явно задаёт другую папку для `settings.json`, выбора, истории и журналов — например отдельную постоянную папку рядом с AppImage. Папку рядом с исполняемым файлом приложение само не выбирает: это может быть временная распаковка. Путь к каталогу состояния виден на странице «Среда»; ошибка доступа на запись показывает путь и причину. Интерфейсные предпочтения Electron (например, тема) хранятся в его userData.

Открытие проекта (включая восстановление выбранного проекта при запуске) ничего не пишет в его папку: служебных файлов, launcher и копий справочников в проекте нет, поэтому перенос приложения или проекта не требует обновлять его содержимое. Инструменты запускает приложение через общий PythonLauncher, явно передавая выбранный проект. Старая запись истории с отсутствующим путём сохраняется: её можно забыть в списке проектов, а перенесённую папку открыть заново.

Настройки приложения — обычный `settings.json` в локальном каталоге состояния: Linux `${XDG_CONFIG_HOME:-~/.config}/songframe`, Windows `%APPDATA%\songframe`. `SONGFRAME_LOCAL_DIR` явно задаёт другую папку; фактический путь виден на странице «Среда». Токены входа провайдеров генерации хранит их клиент в подпапке `providers/<id>/` того же каталога, атомарно и с ограниченными правами; файлы авторизации официальных программ сервисов не используются ([документы провайдеров](providers/README.md)).

### Свежесть производных файлов

Карточки сохраняют значимые поля `project_inputs: {name}`, а полный аниматик — `{name, animatic_video}`. Настройки генерации не являются входами уже созданных документов, карточек и видео. Сохранение настроек проекта не запускает Python и не рендерит карточки. `source_hashes` содержит только фактически использованные медиа; полный файл `project.json` в него не входит.

Это единственный формат квитанций и манифестов. При изменении контракта данные рабочего проекта и тестовых фикстур приводятся к нему отдельно; чтение не выполняет скрытую миграцию и не ищет прежние версии в Git. Отсутствующий или повреждённый `project_inputs` считается ошибкой данных.

### Настройки агента

Кнопка «Сохранить настройки агента» отдельно записывает выбор в общий `settings.json` в постоянной папке состояния. Пример блока без секретов:

```json
{
  "agent": {
    "provider": "codex",
    "model": "идентификатор-выбранной-модели"
  }
}
```

Старый файл без `agent` означает «Без агента»; этот вариант также можно выбрать в форме. Остальные поля, включая `toolsRootOverride`, сохраняются. Выбор текстового агента не меняет проектные `generation.video` и `generation.image` и файлы проектов.

## Модель распознавания

В готовом приложении модель скачивается кнопкой **«Скачать модель …»** в окне «Тайминги → Разметить». Кнопка запускает [download_whisper_model](../tools/download_whisper_model/README.md) фоновым заданием приложения со встроенными Python и `huggingface_hub`; системные Node.js, Yarn, Python, pip или отдельный загрузчик hf не нужны. Модель выбирается в окне, папка определяется ею: `${XDG_DATA_HOME:-$HOME/.local/share}/songframe/models/faster-whisper-<модель>` на Linux и `%LOCALAPPDATA%\songframe\models\faster-whisper-<модель>` на Windows. Индикатор и журнал видны в том же окне, повторное нажатие после ошибки использует уже скачанные файлы, после успеха папка выбирается автоматически. Права администратора для папки модели не нужны. Сведения о моделях и ручном скачивании — в [инструкции по модели распознавания](../README.md#модель-распознавания).

При разработке из checkout тот же инструмент можно вызвать системным Python с установленным `huggingface_hub`:

```sh
python3 -B tools/download_whisper_model/download_whisper_model.py --repository Systran/faster-whisper-medium --output "${XDG_DATA_HOME:-$HOME/.local/share}/songframe/models/faster-whisper-medium"
```

Репозитории остальных моделей перечислены в `src/shared/whisper-models.ts`: `Systran/faster-whisper-small`, `dropbox-dash/faster-whisper-large-v3-turbo`, `Systran/faster-whisper-large-v3`.

Модель загружается только с диска: `local_files_only`, `HF_HUB_OFFLINE` и отключение телеметрии сохранены. Устанавливать unshare и менять AppArmor не нужно. Переменная `SONGFRAME_MODEL_DIR` задаёт внешнюю модель для ручного CLI; параметр `--model` имеет приоритет.

### Генерация общих изображений

Обложка и референсы используют общий диалог `ImageGenerateDialog`, hook `useImageGeneration` и цикл `CoverGeneration`. Режим референса сохраняет полный оригинал в архиве проекта `plan/reference-images`, а `acceptReference` только отмечает выбор кандидата. Страница исходников добавляет выбранный файл с промптом в общую форму; при сохранении `saveSourcesWithCastImages` согласует новые виды с существующим кастингом. Страница кастинга вызывает `referenceImages.attach` для сохранённой сущности: `attachReferenceImage` публикует один файл в `source` и ссылку в кастинге, откатывая оба документа при ошибке записи. Повтор привязки одной сессии не создаёт второй вид. Провайдеры и платные согласования общие с обложкой; отдельная квадратная обрезка относится только к обложке.

Генерация референса открывает большой диалог конструктора. Метод `referenceImages.context(project, drafts?)` только читает название, идею, песню и `visual_direction` из `plan/scenes.json`: он не создаёт сессию и не запускает генерацию. На странице исходников идея и песня берутся из текущего черновика формы, в составе — из сохранённых исходников. Пользователь выбирает существующие изображения объекта и отдельно включает название клипа, идею, текст песни, описание объекта и общие визуальные правила. По умолчанию выбраны все существующие опоры и доступное описание объекта; название, идея, песня и общие визуальные правила выключены. Блоки «Опоры выбранного объекта» и «Конструктор промпта» — аккордеоны, при каждом открытии диалога свёрнутые. Их заголовки показывают число выбранных элементов; раскрытие не меняет запрос и согласования. Редактор промпта и сообщения загрузки/ошибки остаются доступными. Не сокращать поле общих правил автоматически: в нём может храниться большой документ, поэтому его включение остаётся явным и отражается в полном тексте.

Итоговый промпт виден целиком в редактируемом поле с числом символов. После ручной правки переключатели контекста не переписывают текст: возврат к сборке выполняется отдельным действием с подтверждением. Метод `referenceImages.create(project, prompt, { images })` сохраняет ровно переданный текст, включая пробелы и переносы строк, без скрытого добавления названия, песни или инструкций. Счётчик помогает оценить объём; он не объявляет единый лимит всех сервисов. Ограничения выбранного провайдера проверяются его обычной подготовкой до отправки.

Только выбранные изображения копируются в архив сессии и связываются с запросом по SHA-256. Обложка и картинки других объектов автоматически не добавляются. Полный текст и снимок опор показываются при подтверждении. Изменение текста, выбранных опор или пересборка из контекста сбрасывает прежнюю сессию в интерфейсе, её кандидата, цену, SHA и согласие; новый запрос требует новой подготовки и подтверждения. Следующая попытка без изменений использует тот же снимок. Исходники не перезаписываются.

Исполнитель получает опоры из папки текущей попытки. Для провайдера-агента в дополнительный контекст включается `referenceImages` с относительными путями, подписями и хешами; инструкция требует просмотреть файлы и использовать их в `image_gen`, сохраняя внешность объекта и стиль клипа. Для медиапровайдера выбирается объявленная команда с входными изображениями и её слоты. У провайдера без нужной возможности запрос не отправляется; текстовый режим не подменяет запрос с опорами. Ни подготовка, ни выбор кандидата не отменяют прежних согласований генерации и сохранения.


### Локальные производные планы

`DerivedWorkflow` не использует контекст агента или медиапровайдера. Методы `derivedShots` сохраняют кадровый рецепт, создают задания `derive_shot build/accept` через штатные `Jobs` и читают квитанцию `preview.json`. Приёмка сверяет показанный снимок повторно и переносит готовый кандидат без рендера; Node-модуль `derived-recovery` читает тот же журнал, что Python, и восстанавливает прерванную публикацию без зависимости от runtime. `source_scene_sha256` и `source_accepted_video_sha256` проверяются согласованно в `shot-acceptance` и `scene_registry`; исторический неизвестный отпечаток не подменяется текущим.

Свежесть предпросмотра учитывает также хеш полного манифеста источника из `build.json` и `preview.json.audio_source`: путь песни и фактический SHA либо `null` при её отсутствии. Признак уже принятой пробы определяется committed-журналом проекта и текущими байтами комплекта, поэтому не зависит от очистки локальной истории заданий. Итог `derive_shot` сообщает общий наблюдатель `AppProvider` на любой странице, включая короткие задания между опросами; страница производства не дублирует уведомление. Ответы формы привязаны к исходному ключу запроса, поскольку канонический путь API может отличаться от пути открытия через ссылку.

Проверки процесса находятся в `derived-workflow.test.ts`, `derived-recovery.test.ts`, `derived-integration.test.ts`, `tools/derive_shot/test_derive_shot.py` и соседних тестах свежести. Сквозной тест использует настоящие `Jobs`/`PythonLauncher` без выбранного агента, проверяет отдельную приёмку, сохранение старого комплекта, replay, аниматик и замену источника. UI-тесты отдельно проверяют обработчики фоновых заданий, смену проекта/плана, подтверждение замены и запрет принятия устаревшего предпросмотра.


### Storybook

`yarn storybook` запускает витрину renderer на порту 6006; `yarn build-storybook` создаёт `build/storybook`. Обе команды подготавливают отобранные медиа из отслеживаемого проекта-образца, без Python/FFmpeg и пользовательского проекта. Общий `yarn typecheck` включает конфигурации Storybook и браузерного набора. `yarn test:storybook` после сборки проверяет в Chromium истории с меткой `ci`: `play`, ошибки выполнения и правила доступности WCAG A/AA. Node-тесты приложения (`yarn test`) его не запускают. Правила окружения, размещения историй и приёмки — в [справке Storybook](ui/storybook.md).


### Общее описание референса и кастинга

Для связанных по ID объектов владелец описания — `source/manifest.json.references[].description`. Поле `cast.entities[].appearance` остаётся в текущем контракте как управляемая проекция для редактора, сценария, производства и проверки видео. Это не независимый редактируемый источник: сохранение из кастинга передаёт правку в описание референса, сохранение исходников обновляет проекцию. Обе операции публикуют согласованные документы и восстанавливают прежние байты при ошибке. Явная очистка текста не подменяется прежней внешностью. У сущности без соответствующего референса описание принадлежит кастингу; при создании референса переносится в него.

Те же правила действуют при применении предложения первого прохода сценария: изменение внешности видно в сравнении кастинга, а публикация согласует общее описание с манифестом в той же транзакции и журнале восстановления. Чтение проекта только строит проекцию, не меняя файлы; Python `load_cast` следует тому же владельцу. Генерация референса с обеих страниц получает общий текст без автоматически добавленной роли персонажа. Формат данных не меняется, скрытых миграций нет.

Дополнение из исходников сохраняет массив `images` каждой прежней сущности дословно, включая порядок и пустой список. Новые сущности получают исходные виды. Сохранение и приёмка явно добавленного нового вида не меняют прежний основной.
