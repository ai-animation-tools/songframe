# Провайдеры генерации

Приложение не знает конкретных сервисов. Оно работает с провайдером, который умеет генерировать изображения (опоры, обложку) и/или видео (план). Всё, что относится к конкретному сервису, описано в одном документе на каждый вид медиа:

| Вид | Провайдер | Документ |
| --- | --- | --- |
| Видео | Kling | [video/kling.md](video/kling.md) |
| Изображения | Kling | [image/kling.md](image/kling.md) |
| Изображения | Codex | [image/codex.md](image/codex.md) |

Общая документация ([производство](../production-workflow.md), [разработка](../development.md)) и промпты агента ([skills](../../skills/README.md)) описывают только контракт провайдера и ссылаются сюда.

## Контракт

- **Реестр** [src/shared/media-providers.ts](../../src/shared/media-providers.ts) — единственный источник сведений о провайдере для общего кода и интерфейса: название, виды медиа, исполнитель (агент или прямой вызов), платность, `lipSync`, `learnsPriceFromCharges`, `generationHistory`, значения настроек по умолчанию (`defaults`), порядок моделей в настройках (`modelOrder`), подписи. Код не сравнивает имена провайдеров строками и не пишет название сервиса в тексты интерфейса: только поля реестра. При смене провайдера в настройках проекта сохраняются только поля самого проекта (`PROJECT_GENERATION_FIELDS` в [src/shared/generation-settings.ts](../../src/shared/generation-settings.ts): у видео — разрешение, пропорции, правило длительности и запрет логотипа, у изображений — запрет логотипа); всё остальное, включая модель, параметры запроса, `options` и поля, о которых общий код не знает, заменяется значениями по умолчанию нового провайдера.
- **Адаптер приложения** — папка `src/main/providers/<id>/` и строка в таблице [src/main/providers/index.ts](../../src/main/providers/index.ts). Контракт — [src/main/providers/types.ts](../../src/main/providers/types.ts): платный адаптер (`PaidProviderAdapter`) отдаёт правила нормализации запроса, проверку доступности клиента, переменные окружения для Python, строки страницы «Среда», вход и проверку авторизации, проверки поставки; адаптер-агент (Codex) исполняет задание отдельным процессом. Общий платный цикл (`PaidMediaProvider`, `selectPaidRequest`, обложка, производство) работает через эти поля.
- **Адаптер инструментов** — модуль в `tools/<id>_request/` и строка в таблице [tools/media_adapters.py](../../tools/media_adapters.py). Общий жизненный цикл попытки (заморозка, замок, единственная отправка, получение, неизвестный исход, ручной результат) ведёт [media_request](../../tools/media_request/README.md); адаптер реализует только обращения к сервису: `validate_spec`, `validate_prompt`, `capabilities`, `submit`, `poll`, `fetch`, `account`, `pricing_file`, необязательный `snapshot_warnings` ([интерфейс](../../tools/media_request/README.md#адаптеры)). Клиент сервиса — собственный Python-код адаптера: программы провайдера не устанавливаются. Токены входа клиент хранит в каталоге состояния приложения (`providers/<id>/`) атомарно и с ограниченными правами; файлы авторизации официальных программ сервиса не используются. `pricing_file` указывает базовую таблицу цен из поставки (`tools/<id>_request/pricing.json`, только чтение); наблюдения `cost_check learn` записываются в `providers/<id>/pricing-observations.json` каталога состояния и объединяются с базовой таблицей при чтении. `SONGFRAME_PRICING_FILE` подменяет базовую таблицу в тестах.
- **Документ провайдера** `docs/providers/<вид>/<id>.md` описывает сервис для людей: вход и авторизацию, подключение при запуске из checkout, особенности моделей, стоимости и получения. Раздел `## Указания агенту` приложение вкладывает в промпт задания, когда этот провайдер выбран в проекте для данного вида медиа; остальной текст агенту не передаётся. Поэтому в разделе — только то, что нужно агенту для выбора модели, слотов и параметров запроса, без рассказов об интерфейсе.

## Тестовый провайдер

Общая логика тестируется на вымышленном платном провайдере `test`, не зависящем от подключённых сервисов. В TS его регистрируют `registerTestMediaProvider()` ([src/main/testing/media-provider.ts](../../src/main/testing/media-provider.ts)) и, для интерфейса, `registerMediaProviderForTests`; в Python — `SONGFRAME_MEDIA_ADAPTERS=test=tools.testing.fake_media_request` с поведением из `SONGFRAME_TEST_MEDIA_SERVICE` ([описание](../../tools/testing/README.md)). Образец проекта `tools/testdata/sample-project` использует `test`. Тесты конкретного сервиса лежат только в папках его адаптера.

## Добавить или удалить провайдера

1. Запись в реестре `MEDIA_PROVIDERS` с полями `MediaProviderInfo`.
2. Папка `src/main/providers/<id>/` и строка в `src/main/providers/index.ts`; для платного провайдера — модуль `tools/<id>_request/` и строка в `tools/media_adapters.py`. Тесты сервиса — внутри этих папок.
3. Документ `docs/providers/<вид>/<id>.md` для каждого поддерживаемого вида медиа с разделом `## Указания агенту` и строка в таблице выше.

Удаление — те же шаги в обратном порядке; общие тесты от этого не меняются. Сохранённые запросы и комплекты проектов хранят имя провайдера как данные: повтор с удалённым провайдером останавливается с объяснением, а не подменяет провайдера.
