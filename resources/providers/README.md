# Провайдеры генерации

Приложение не знает конкретных сервисов. Оно работает с провайдером, который умеет генерировать изображения (опоры, обложку) и/или видео (план). Всё, что относится к конкретному сервису, описано в одном документе на каждый вид медиа:

| Вид | Провайдер | Документ |
| --- | --- | --- |
| Видео | Kling | [video/kling.md](video/kling.md) |
| Изображения | Kling | [image/kling.md](image/kling.md) |
| Изображения | Codex | [image/codex.md](image/codex.md) |
| Видео | Вручную вне приложения | [video/manual.md](video/manual.md) |

Общая документация ([производство](../../docs/production-workflow.md), [разработка](../../docs/development.md)) и промпты агента ([skills](../skills/README.md)) описывают только контракт провайдера и ссылаются сюда. Документы этой папки встроены в бинарник (`resources.ProviderDoc`).

## Контракт

- **Реестр** [frontend/src/shared/media-providers.ts](../../frontend/src/shared/media-providers.ts) — единственный источник сведений о провайдере для общего кода и интерфейса: название, виды медиа, исполнитель (агент или прямой вызов), платность, `manual` (способ видео без сервиса: все планы идут ручной генерацией, адаптера нет), `lipSync`, `learnsPriceFromCharges`, `generationHistory`, значения настроек по умолчанию (`defaults`), порядок моделей в настройках (`modelOrder`), подписи. Go-часть реестра — [internal/mediaproviders](../../internal/mediaproviders/mediaproviders.go), совпадение с TS проверяет `TestRegistryMatchesFrontend`. Код не сравнивает имена провайдеров строками и не пишет название сервиса в тексты интерфейса: только поля реестра. При смене провайдера в настройках проекта сохраняются только поля самого проекта (`PROJECT_GENERATION_FIELDS` в [frontend/src/shared/generation-settings.ts](../../frontend/src/shared/generation-settings.ts): у видео — разрешение, пропорции, правило длительности и запрет логотипа, у изображений — запрет логотипа); всё остальное, включая модель, параметры запроса, `options` и поля, о которых общий код не знает, заменяется значениями по умолчанию нового провайдера.
- **Адаптер** — папка `internal/providers/<id>/`. Платный адаптер реализует контракт [internal/mediaapi](../../internal/mediaapi) (нормализация и проверка запроса, возможности, отправка, опрос, получение, аккаунт, таблица цен, вход и проверка авторизации, строки страницы «Среда»; необязательные возможности — отдельные интерфейсы) и регистрируется строкой в таблице `adapters` пакета [internal/mediaadapters](../../internal/mediaadapters/mediaadapters.go). Провайдер-исполнитель на агенте выполняет задание отдельным процессом агента и регистрируется в таблице `agentAdapters` пакета [internal/providers](../../internal/providers/providers.go). Общий жизненный цикл платной попытки (заморозка, замок, единственная отправка, получение, неизвестный исход, ручной результат) ведёт [internal/mediarequest](../../internal/mediarequest); адаптер реализует только обращения к сервису. Клиент сервиса — Go-код адаптера: программы провайдера не устанавливаются. Токены входа хранятся в каталоге состояния приложения (`providers/<id>/`) атомарно и с ограниченными правами; файлы авторизации официальных программ сервиса не используются. Базовая таблица цен встраивается в бинарник вместе с адаптером (только чтение; у Kling — [pricing.json](../../internal/providers/kling/pricing.json)), наблюдения расхода записываются в `providers/<id>/pricing-observations.json` каталога состояния и объединяются с базовой таблицей при чтении.
- **Документ провайдера** `resources/providers/<вид>/<id>.md` описывает сервис для людей: вход и авторизацию, особенности моделей, стоимости и получения. Раздел `## Указания агенту` слой провайдеров (`providers.Guide`) вкладывает в промпт задания, когда этот провайдер выбран в проекте для данного вида медиа; раздел заканчивается перед следующим заголовком `## `, остальной текст агенту не передаётся. Поэтому в разделе — только то, что нужно агенту для выбора модели, слотов и параметров запроса, без рассказов об интерфейсе. Правка раздела меняет промпт, её проверяют эталоны промптов в `testdata/golden`; SHA-256 документов целиком закреплены в `TestProviderDocs` (`resources/resources_test.go`).

## Тестовый провайдер

Общая логика тестируется на вымышленном платном провайдере `test` из [internal/mediatest](../../internal/mediatest/mediatest.go), не зависящем от подключённых сервисов: поведение задаёт `service.json` рабочей папки теста, вызовы дописываются в `calls.jsonl`. Для интерфейса реестр дополняет `registerMediaProviderForTests`. Проект-образец (`testdata/golden/checks-base/project`) использует `test`. Тесты конкретного сервиса лежат только в папке его адаптера.

## Добавить или удалить провайдера

1. Запись в реестре `MEDIA_PROVIDERS` с полями `MediaProviderInfo` и соответствующая запись в `internal/mediaproviders`.
2. Папка `internal/providers/<id>/` и строка в таблице `internal/mediaadapters` (платный) или `agentAdapters` в `internal/providers` (исполнитель-агент). Тесты сервиса — внутри папки адаптера.
3. Документ `resources/providers/<вид>/<id>.md` для каждого поддерживаемого вида медиа с разделом `## Указания агенту`, его SHA-256 в `TestProviderDocs` и строка в таблице выше.

Удаление — те же шаги в обратном порядке; общие тесты от этого не меняются. Сохранённые запросы и комплекты проектов хранят имя провайдера как данные: повтор с удалённым провайдером останавливается с объяснением, а не подменяет провайдера.
