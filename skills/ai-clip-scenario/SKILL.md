# Сценарий клипа

Два прохода с подтверждением пользователя между ними. Первый проход даёт кастинг `plan/cast.json` и трактовку `plan/treatment.json`: кто действует и что происходит в каждой части песни. Второй проход даёт реестр сцен `plan/scenes.json`: планы с кадровыми окнами, постановкой и изменениями состояния. Детерминированное делают инструменты (окна, карта референсов, проверки), смысл пишет агент.

## Вызов

| Задача | Codex | Claude Code |
| --- | --- | --- |
| Первый проход: кастинг и трактовка | `$ai-clip-scenario pass=treatment` | `/ai-clip-scenario pass=treatment` |
| Второй проход: реестр сцен | `$ai-clip-scenario pass=scenes` | `/ai-clip-scenario pass=scenes` |
| Доработать существующий реестр по замечаниям | `$ai-clip-scenario pass=revise note="..."` | то же |
| Другой проект | `project=/путь/к/папке` | то же |

Команды ниже выполняются из корня клипа через управляемый `.songframe/run-tool`, который обновляет приложение при открытии проекта. Автоматически устанавливать CLI, входить в аккаунт или запускать генерацию не нужно.

Без `pass` скилл выбирает проход по состоянию проекта: нет трактовки, значит первый; есть трактовка и нет реестра, значит второй; есть реестр, значит доработка только с явным `note`.

## Предложение для приложения: output=proposal

Приложение передаёт этот режим вместе с `pass` и контекстом через stdin в CLI агента с доступом только для чтения. Верни один JSON-документ, без Markdown, пояснений и текста вокруг. Не вызывай записывающие инструменты, не создавай и не изменяй файлы: приложение само проверяет предложение, показывает preview и применяет его отдельным действием пользователя. Этот режим использует инструкции навыка через stdin; он не означает вызов Claude Skill tool.

- `pass=treatment`: `{"schemaVersion":1,"pass":"treatment","cast":{...},"treatment":{...}}`. `cast` и `treatment` — полные документы существующих форматов `CastFile` и `TreatmentFile` с `schema_version: 1`. Используй переданный черновик кастинга и словарь `properties`, сохраняя существующие ID и референсы. Не вызывай `cast_registry init`. Новые сущности без изображений оставляй с пустым `images`; не выдумывай файлы.
- `pass=scenes`: `{"schemaVersion":1,"pass":"scenes","scenes":{...}}`. `scenes` — полный `ScenesFile` с `schema_version: 1`. Приложение передаёт каркас, полученный через `scene_scaffold --dry-run --json` после утверждения кастинга и трактовки. Сохрани ID, `original`, `sequence`, `start_frame`, `end_frame_exclusive`, 30 fps и сплошную шкалу каркаса. Заполни постановку, references, состояния, continuity, lipsync, карточки и общие визуальные правила; не оставляй `ЗАПОЛНИТЬ`. Деление и объединение планов выполняет редактор.
- `pass=revise`: `{"schemaVersion":1,"pass":"revise","patches":[{"id":"M01","action":"..."}]}`. Для каждого выбранного ID верни только изменяемые поля постановки: `title`, `notes`, `camera`, `action`, `continuity`, `references`, `lipsync`, `card`, `state_from`, `state_changes`. `id` выбирает план и не меняется. Запрещены поля других планов, окна кадров, `original`, `sequence` и глобальные поля реестра. Соседи переданы только как контекст. Замечание и список разрешённых ID обязательны; не расширяй их молча.

Все поля и значения должны пройти существующие доменные проверки. Конец трактовки и сцен согласуй с переданным `timing.duration_decoded`; исходный текст и разметку не меняй. Учитывай ограничение результата 256 KiB. Согласование, запись, запуск scaffold и обновление представлений принадлежат приложению.

Без `output=proposal` действует ручной порядок ниже: скилл записывает документы и запрашивает подтверждение между проходами.

## Входы, которые читать всегда

`source/description.md` (идея клипа), `source/text.md` (точный текст по строкам), `plan/audio/timing.json` (строки и части с временем), `source/manifest.json` (референсы и их типы), `plan/cast.json`, если есть. Постановку сочинять из идеи и слов песни, привязывая действие к строкам и их времени; без этих файлов проход не начинать.

Поле `cover` манифеста используется только для оформления проекта. Не включать обложку в кастинг, референсы сцен, опорные кадры или запросы генерации. Изображения для постановки брать из `references` манифеста и явно заданных изображений кастинга.

## Первый проход: кастинг и трактовка

1. `./.songframe/run-tool cast_registry init` создаёт или дополняет кастинг по референсам исходников; сущность `world` появляется автоматически. Дописать в `plan/cast.json` для каждой сущности `role`, `appearance` (только то, что следует из идеи и референсов; не выдумывать внешность, которой нет на изображениях) и `initial_state` по словарю `properties` этого типа. У `world` заполнить время суток, погоду, сезон, ось дороги, стороны по ходу. Если в идее есть герои без референсов, добавить сущности без изображений и сказать пользователю, что их нужно нарисовать или загрузить до производства.
2. Трактовка `plan/treatment.json`: `{"schema_version": 1, "logline": "одна фраза", "sequences": [{"id": "intro", "title": "...", "direction": "что происходит и зачем", "start": 0, "end": 18.74, "entities": ["world", "performer"], "lipsync": false, "max_shot_seconds": 6}]}`. Границы частей брать из `sections` разметки, части идут подряд от 0 до `duration_decoded` разметки; `entities` перечисляют, кто в части на экране; `lipsync: true` для частей, где герой поёт в кадре.
3. Проверка: `./.songframe/run-tool cast_registry check` и `./.songframe/run-tool lint_registry` (кастинг проверяется схемой).
4. Сводка пользователю: логлайн, части с временем и действующими лицами, список сущностей с начальным состоянием. Попросить подтвердить или поправить на страницах «Кастинг» и «Сценарий» приложения. Ко второму проходу не переходить без подтверждения.

## Второй проход: реестр сцен

1. `./.songframe/run-tool scene_scaffold --dry-run`, затем без `--dry-run`: каркас реестра с окнами по строкам песни и инструменталу, `references` из кастинга, заготовками `ЗАПОЛНИТЬ`. Существующий реестр инструмент не трогает без `--force`.
2. Заполнить каждую сцену: `camera` (крупность и движение), `action` (что происходит, одним или двумя предложениями, без технических рецептов и истории согласований), `continuity` (стык с соседями), `references` (кто и что в кадре, по кодам кастинга), `lipsync`, `card.primary_reference`. Разовые жесты остаются в `action`; всё, что сохраняется дальше по сюжету, записывать в `state_changes` (`before` уточняет вход, `after` результат действия) только по словарю свойств кастинга; `state_from` указывает сюжетного предшественника. Общие визуальные правила в `visual_direction`. При необходимости планы дробить или объединять, сохраняя сплошную шкалу кадров.
3. Проверка после каждой пачки сцен: `./.songframe/run-tool lint_registry` (схема и владение сведениями) и `./.songframe/run-tool continuity_brief Mxx` для спорных сцен: врезка должна читаться как внятное описание кадра. `./.songframe/run-tool update_scene_views` обновляет раскадровку и монтажный список.
4. Сводка пользователю: число планов по частям, где использован липсинк, какие сущности меняют состояние и где. Предложить пройти планы в редакторе сценария приложения.

## Доработка

С `note` менять только затронутые планы и их состояние; соседей не переписывать молча, конфликты показывать пользователю. После правок те же проверки и обновление представлений.

## Что скилл не делает

Не рисует референсы и опоры, не запускает генерацию, не меняет `source/`, не подменяет разметку трека, не делает commit.
