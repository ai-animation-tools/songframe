# Релиз SongFrame

Работай в корне репозитория SongFrame (в рабочем пространстве AI Animation Tools это папка `songframe/`). Сначала прочитай `AGENTS.md`, раздел «CI и релизы» в `docs/development.md`, `.github/workflows/release.yml`, `.github/workflows/ci.yml` и `scripts/release/release.mjs`. Это источники текущего порядка: при изменении workflow не подменяй его старой памяткой. Не меняй другие репозитории и пользовательские проекты.

## Подготовка

1. Выясни, что поручено: подготовить предложение, собрать файлы или опубликовать релиз. Проверь состояние Git, точный коммит и изменения с предыдущего опубликованного тега; если релиза ещё не было, опиши первый выпуск по доступному состоянию. Учитывай незакоммиченные изменения и сообщай, входят ли они в выбранный коммит; не включай их без поручения пользователя.
2. Предложи номер `X.Y.Z` без `v` и без ведущих нулей, исходя из характера изменений и истории релизов. Если пользователь указал номер, используй его. Проверь, что точные тег `vX.Y.Z` и релиз, включая черновик, не заняты; при конфликте не перезаписывай их. Подготовь краткое описание на русском для пользователя: что нового, что исправлено и важные изменения работы. Не приписывай непроверенные возможности.
3. Базовая версия разработки лежит в `package.json`, поле `version`. Текущий Release workflow принимает отдельное поле `version` и меняет `package.json` только в сборочных checkout; он не создаёт коммит с этой версией. Не меняй версию в репозитории автоматически только ради workflow. Если пользователь поручил изменить её постоянно, проверь согласованность зависимых файлов и проверок.
4. Убедись, что CI прошёл для **того же SHA**, из которого планируется релиз. Текущий Release workflow не заменяет полный CI: CI проверяет ESLint, Prettier, типы, тесты приложения, Python и скриптов поставки; поставки собирает и проверяет только сам Release (локально — `songframe-build`). Для локальных проверок используй команды из `docs/development.md` и `.github/workflows/ci.yml`; результаты ограничь действительно выполненными проверками.

## Сборки и публикация

- Следуй актуальному Release workflow: обе поставки собираются из одного SHA с выбранной версией. Linux проходит проверку runtime и конечного AppImage; Windows ZIP проверяется на состав и целостность без исполнения Windows-кода. Нативную проверку Windows или VirtualBox проводи только по явному поручению.
- Проверь версию, контрольные суммы и отчёты. Привязку к исходному SHA проверяй по `github.sha` запуска workflow и его artifacts: сами файлы отчётов не доказывают SHA. Если выбран ref ветки, учти, что её HEAD может измениться до запуска; используй доступный неизменяемый ref, когда это возможно, и сообщи о расхождении SHA. Текущий `release.mjs` сверяет два дистрибутива, их SHA256, отчёты Linux и Windows и инвентарь Linux; файл уведомлений о лицензиях он проверяет только на наличие и непустой размер. При ошибке сообщи конкретную неуспешную проверку; черновик после сбоя загрузки не считай опубликованным релизом.
- Релиз запускается через GitHub Actions → Release → Run workflow: выбрать нужный ref, задать `version` и подготовленное `description`. Workflow публикует релиз автоматически после успешных сборок; запуск этого workflow является запуском публикации, а не только проверкой. Выполняй его только если пользователь поручил публикацию. Коммит и push также делай только по явному поручению; до публикации ref должен быть доступен GitHub.
- Временные файлы и отчёты размещай вне репозитория, при требовании пользователя — в `/tmp`. Собранный AppImage оставляй в штатном `build/release`, если пользователь не указал иначе. Отдельные локальные сборки выполняй по `songframe-build` и не выдавай их за проверенный релиз CI.

## Что сообщить пользователю

Укажи номер, SHA/ref, описание изменений и фактический статус CI, сборок и публикации. Для опубликованного релиза дай ссылку на него; для локальных сборок — пути к файлам и SHA256. Дай краткие шаги установки: скачать AppImage для Linux или ZIP для Windows, проверить SHA256, разрешить выполнение AppImage либо распаковать ZIP и запустить приложение; модель распознавания ставится отдельно по README. Укажи отдельно, если Windows проверен только по архиву. Если подготовка завершена, а публикация ещё не поручена, покажи готовые номер и описание и инструкцию запуска workflow пользователем.
