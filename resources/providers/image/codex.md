# Codex: изображения

Генерация опорных кадров и обложки встроенным инструментом `image_gen` Codex CLI. Бесплатна для приложения (`paid: false`): расход идёт по лимитам подписки Codex. Общий контракт провайдера — в [README](../README.md).

## Подключение

- Codex CLI устанавливается пользователем отдельно и находится автоматическим поиском, как текстовый агент. Доступность определяется только наличием Codex и выполненным входом; это не подтверждает, что `image_gen` доступен аккаунту — недоступный инструмент сообщает ошибку при первой генерации.
- Генерацию запускает приложение отдельным процессом Codex при любом выбранном текстовом агенте и без него. Опоры идут внутренним маршрутом `Manager.StartImages` ([internal/agents](../../../internal/agents/manager.go)): Codex получает `--sandbox workspace-write`, рабочая папка `<каталог состояния>/image-jobs/<UUID>` содержит копии референсов ([задания изображений](../../../docs/agents.md#задания-изображений)). Обложка и референс проекта ([internal/covergen](../../../internal/covergen/session.go)) работают так же, но в папке `image-jobs/<ID>` своей сессии: у обложки это временная папка, у референса — архив `plan/reference-images/<ID>` проекта. До применения кадры остаются кандидатами вне проекта.
- Адаптер — [internal/providers/codex](../../../internal/providers/codex/images.go) (опоры) и [cover.go](../../../internal/providers/codex/cover.go) (обложка и референс); подключается строкой таблицы `agentAdapters` в [internal/providers](../../../internal/providers/providers.go).
- **Windows не проверен.** Генерацию исполняет Codex через тот же менеджер заданий, что и в Linux; маршрут в Windows подтверждается только ручной проверкой в VM.

## Значения реестра

`paid: false`, `executor: codex`, `lipSync: null`, `learnsPriceFromCharges: false`, `generationHistory: null`, `requestParameters: false`, подпись пустой модели «Как указано в настройках Codex». Реестр — [media-providers.ts](../../../frontend/src/shared/media-providers.ts).

## Модель и параметры

- `generation.image.model` выбирает модель агента, который вызывает `image_gen`; внутреннюю модель генератора оно не переключает. Каталог читается штатным `model/list` Codex. Пустая модель — конфигурация Codex CLI без `--model`.
- Исполнитель создаёт один вариант каждой опоры. Параметров `resolution`, `aspect_ratio` и `outputs` нет, значений по умолчанию у провайдера тоже нет. При выборе Codex в настройках проекта сохраняется только запрет логотипа (`watermark`); модель, параметры запроса, `options` и прочие поля сбрасываются, а при выборе другого провайдера берутся его значения по умолчанию ([generation-settings.ts](../../../frontend/src/shared/generation-settings.ts)).
- Размер через текст запроса не гарантируется: горизонтальное изображение может иметь `1672×941` даже при просьбе о 4K. Это наблюдаемый размер, а не объявленный максимум инструмента; настройки проекта напоминают об этом (`settingsNotes` реестра).

## Указания агенту

- Размер и формат изображения определяет исполнитель `image_gen`; пропорции кадра описывай в промпте словами (например «горизонтальный кадр 16:9»), не обещая точного разрешения.
- Референсы кастинга передаются файлами рядом с заданием; в промпте называй, что взять из каждого.

## Контекст и опоры общего референса

Генерация изображения объекта из «Исходников» и «Состава» использует точный текст из редактора. Пользователь отдельно выбирает части контекста клипа, описание, общие визуальные правила и изображения. По умолчанию выбраны только опоры и доступное описание; остальные части контекста включаются явно. После подготовки контекст не дописывается. Существующие выбранные изображения объекта закрепляются копиями и SHA-256 до отправки. Они передаются исполнителю как `referenceImages` с путями внутри его рабочей папки; агент обязан просмотреть их и передать в `image_gen`, сохраняя внешность и указанный пользователем стиль. Изменение промпта или опор требует новой подготовки и подтверждения.

Это отдельный запуск провайдера изображений, не задание выбранному текстовому агенту. Его постоянные инструкции не подмешиваются. Копии опор и полный промпт сохраняются в архиве сессии, а исходные изображения не изменяются. Изменённые байты согласованной копии отклоняются до запуска исполнителя.

Полный сериализованный контекст (`userPrompt` и метаданные `referenceImages`, включая JSON-экранирование) проверяется по внутреннему лимиту менеджера при подготовке, до выдачи SHA и токена подтверждения. Исполнитель использует тот же сериализатор при запуске, поэтому переносы строк и подписи не могут незаметно превысить проверенный бюджет.

Для генерации референса доступны и дополнительные файлы пользователя: это выбранные опоры запроса, а не автоматически созданные исходники. При генерации обложки можно явно выбрать изображения референсов; по умолчанию их нет. В обоих случаях исполнитель получает проверенные локальные копии и инструкцию передать их `image_gen`. Назначение опор и композицию определяет показанный пользовательский промпт; обложка остаётся квадратной.
