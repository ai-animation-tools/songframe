# Релиз SongFrame

Работай в корне репозитория SongFrame (в рабочем пространстве AI Animation Tools это папка `songframe/`). Механические операции выполняет `scripts/release/release.mjs` (`yarn release`). Порядок, требования к машине сборщика и состав выпуска описаны в разделе «Выпуск релиза» файла `docs/development.md`. При расхождении источником считается он, а не эта памятка. Пользовательские проекты не меняй. Соседний приватный план обновляй только в рамках поручения и правил рабочей области; его содержимое не входит в публичный выпуск.

## Версия и описание

1. Выполни `yarn release plan`, а если пользователь назвал версию, то `yarn release plan --version <версия>`. Команда только читает Git и GitHub, незакоммиченные изменения ей не мешают. План относится к HEAD, поэтому грязное дерево означает, что эти изменения в выпуск не войдут.
2. Возьми из результата `previousTag`, `previousRevision`, `revision`, `commits` и `changes`. Предыдущий выпуск определяется по опубликованным релизам, а не по локальным тегам. Посмотри существенный diff от `previousRevision` до `revision`: сообщения коммитов сами по себе не доказывают, что возможность есть. Для первого выпуска изучи README и текущие возможности приложения.
3. Выбери SemVer `X.Y.Z` без `v` по составу изменений и сообщи его пользователю. Если номер не задан, полное поручение выпустить релиз разрешает выбрать корректную новую версию без отдельного подтверждения; просьба только спланировать выпуск публикации не разрешает. Patch — для исправлений, minor — для новых возможностей, major — для несовместимых изменений формата проекта после первого выпуска. Версия в плане — только начальная рекомендация: первый выпуск берёт `version` из `package.json`, следующие — patch после последнего опубликованного. `version` в отслеживаемом `package.json` — каноническая версия выпуска. После выбора номера в пределах поручения обнови её до commit/push исходников в рамках имеющегося поручения на Git; `plan` ничего не записывает, а `prepare --version` требует точного совпадения с `package.json` и сам его не меняет. `SONGFRAME_VERSION` передаёт эту же версию сборщику; отдельный локальный override описан в скилле `songframe-build`. Существующий выпуск без прямого поручения не переиздавай.
4. Напиши описание по-русски и сохрани его в `build/releases/notes-<версия>.md` (папка `build/` вне Git). Для первого выпуска опиши назначение приложения, поставки и установку. Для следующих — полезные пользователю изменения с предыдущего выпуска, необходимые действия при обновлении и известные ограничения, если они действительно есть. Пустые разделы не добавляй, внутреннюю историю разработки не переноси.

В таблице установки ссылки на пакеты делай прямыми версионными URL `https://github.com/ai-animation-tools/songframe/releases/download/<tag>/<имя-файла>`. В выпуске две поставки:
- Linux x64 AppImage `songframe-<версия>-linux-x86_64.AppImage`;
- Windows x64 установщик `songframe-<версия>-win-x64-setup.exe`. Он ставится в профиль пользователя без прав администратора, обновление — установкой новой версии поверх.

Код не подписан: Windows может показать предупреждение SmartScreen. Веса модели распознавания устанавливаются отдельно (README). Запуск внешних Claude/Codex в Windows подтверждается только ручной проверкой в VM. Не обещай отсутствие предупреждений ОС или проверку установщика в Windows, если её не было.

## Подготовка и публикация

Учитывай точный объём поручения. Просьба спланировать выпуск или написать описание не разрешает prepare и publish. Явное поручение выпустить согласованную версию разрешает обе команды, повторно разрешения не спрашивай. Прямой запрет на коммиты, теги или публикацию важнее.

- До подготовки сохрани снимок существующих комплектов `build/releases/v*/` и проверь жёсткие ссылки из `build/release` по разделу «Версия локальной сборки» в `docs/development.md`. Отвязывай только перезаписываемые рабочие файлы, архивы не меняй; после сборки сверяй их с исходным снимком.
- `yarn release prepare --version <версия> --notes build/releases/notes-<версия>.md` требует чистого дерева и совпадения версии с зафиксированным `package.json`. Команда ставит **локальный** аннотированный тег, собирает на этой машине обе поставки и проверяет их: AppImage — smoke в Docker с тестовой моделью, установщик — состав без запуска Windows-кода. Комплект складывает в `build/releases/<tag>/`. На GitHub ничего не отправляет. Сборка идёт долго: запускай в фоне и не опрашивай. Фоновый процесс должен переживать закрытие инструментальной оболочки; используй отдельную сессию процесса с журналом и сохранением кода завершения. После SIGHUP/SIGTERM сначала проверь активные процессы и фактическое состояние GitHub, прежде чем продолжать подготовку или публикацию. Если поручено только спланировать, остановись до prepare: даже локальный тег меняет Git.
- Скрипт не создаёт коммиты и не отправляет main. Каноническую версию нужно зафиксировать вместе с исходниками до prepare; выполняй commit/push, только если они входят в поручение. При грязном дереве подготовь план и описание; если Git не поручен, сообщи, что исходники и версию нужно зафиксировать отдельным действием. Проверку чистоты не обходи, другой коммит не собирай, чужую незавершённую работу в выпуск не включай.
- `yarn release publish --version <версия>` выполняй только в рамках поручения выпустить эту версию. Перед публикацией исходный коммит комплекта должен быть в main на GitHub, а его CI — успешным: локальная сборка не заменяет lint, типы и тесты CI. HEAD при публикации может быть новее исходного коммита. Команда отправляет тег, создаёт черновик `SongFrame <версия>`, загружает 8 файлов и сверяет каждый, затем публикует релиз как latest и заново проверяет все вложения через GitHub API.
- При сетевом сбое повтори ту же команду один раз. Уже загруженные совпадающие файлы используются повторно, незавершённые `starter`-вложения без digest скрипт удаляет только в черновике, если размер нулевой либо равен ожидаемому: GitHub может сразу записать полный Content-Length. При повторном отказе остановись и назови этап. Несовпадение SHA-256, описания или Git-состояния требует разбирательства. Не удаляй релиз, не используй `--clobber`, не переноси тег и не пересобирай под опубликованным номером.
- Если CI исходного коммита отменён либо отсутствует, в рамках полного поручения на выпуск сам перезапусти его (`gh run rerun <id>`) либо запусти workflow для того же коммита (`gh workflow run CI --ref main`) и дождись результата. Сверь `headSha`: успешный запуск другого коммита не подтверждает комплект. Если запуск падает, изучи журнал и исправь причину; новый исходный SHA требует нового плана/комплекта, прежний тег не переноси.
- Повторный publish уже опубликованного релиза только проверяет его и сохраняет квитанцию, файлы не меняются. Отказ после публикации не означает, что релиз остался черновиком: проверь фактическое состояние.

Вложения проверяй только по метаданным GitHub API: `digest` (`sha256:<хэш>`), `size`, `state: uploaded` и версионный URL. **НЕ СКАЧИВАЙ ВЛОЖЕНИЯ ОБРАТНО ДЛЯ ПРОВЕРКИ.** Отсутствующий или несовпадающий digest останавливает проверку, скачивание запасным способом не служит. Нативный запуск Windows в VM выполняй только по явному поручению.

При прямом поручении переиздать ту же версию сначала сохрани описание, тег и комплект в резервную копию. Затем удали только согласованные релиз и тег и выполни обычные prepare и publish из зафиксированных исходников.

## Проверка изменений скрипта

Изменение только инструмента выпуска не требует Storybook или тестов интерфейса: CI выбирает адресный job через `scripts/ci/classify-changes.mjs`. Сверяй реальный выбор jobs/steps на GitHub; полный ручной запуск оставляй для проверки общих изменений.

`yarn test:release` проверяет сценарий на временных репозиториях с подменённым GitHub и сборкой, без сети и публикации. Тесты проверки установщика: `python3 -B -m unittest discover -s scripts/runtime -p 'test_*.py'`.

## Что сообщить пользователю

Укажи версию, точный исходный коммит, выполненный этап, состояние CI и GitHub. Публикацию подтверждают `published: true, assetsVerified: true, verification: "github-api-sha256"` и квитанция `build/releases/<tag>/public-release.json` с хешами всех 8 вложений; дай ссылку на релиз. Кратко опиши установку:
- Linux: скачать AppImage, проверить SHA256, разрешить выполнение и запустить;
- Windows: скачать и запустить установщик;
- модель распознавания ставится отдельно по README.

Отдельно оговори, что Windows проверен только по составу установщика, если не было VM-прогона.
