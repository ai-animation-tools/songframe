# План Mxx: предложение этапа производства

Инструкции задания, которое запускает приложение на странице «Производство» для одного плана Mxx: один ролик для кадрового окна из сценария; сценарная сцена может включать несколько планов. Задание работает в режиме `output=proposal` и готовит один этап: `description` (постановка и опоры) или `prompt` (видеопромпт). Запрос видео собирает приложение без задания. Ответ — ровно один JSON по [контракту этапов](references/app-proposal.md), промпты — по [правилам промптов](references/prompt-template.md). Задание работает в папке проекта клипа только на чтение: файлы не записываются, а материалы клипа можно открывать по путям из контекста, все пути — относительно папки проекта.

Согласование, применение предложения, генерацию опор и видео, стоимость и отправку ведёт приложение. Принятие предложения не утверждает этап и не разрешает расход; кнопки согласования нажимает пользователь.

## Контекст задания

Приложение передаёт JSON:

| Поле | Содержание |
| --- | --- |
| `stage` | Запрошенный этап |
| `scene` (и его копия `shot`) | План из сценария: окно, `camera`, `action`, `continuity`, `references`, `lipsync`, `state_from`, `state_changes`, а также `visual_direction` сценария и `sequence_direction` его части песни |
| `cast` | Сущности кастинга в кадре и `world`: `appearance`, `role`, `initial_state`, изображения (`images`) и примечания пользователя к ним (`imageNotes`: `path`, `note`) |
| `references` | Карта референсов плана: подписи и пути в `source/` |
| `brief.before`, `brief.after` | Врезка непрерывности на первый и последний кадр: `paragraph` — состояние словами для промпта опоры и источник фактов видеопромпта, `checklist` с вопросами проверки кадра, полный текст |
| `settings` | Блок `generation.video` проекта: провайдер, `resolution`, `aspect_ratio`, `watermark`, `duration_rule`, необязательные `model` и `options` |
| `existing`, `description`, `prompt`, `keyframes` | Состояние пакета, принятое или текущее описание, видеопромпт и план опор с промптами |
| `speech` | Подготовленный точный WAV речевого плана: `path` и `sourceSeconds` (начало и конец среза в песне); `null`, пока WAV не нарезан |
| `lipSync` | Для речевого плана — допустимая длина звукового входа провайдера видео (`min`/`max`, с); иначе `null` |
| `allowedPaths` | Единственные пути, которые можно указывать как референсы и входы: исходники плана, принятые опоры, а на этапе description — кадры других планов из `continuityFrames` |
| `windowSeconds` | Монтажное окно `T` в секундах |
| `capabilities`, `capabilitiesProblem` | Актуальные объявления моделей аккаунта провайдера видео или причина, почему их нет |
| `keyframeCount` | Число опор, выбранное пользователем; передаётся только при явном выборе, без него число опор выбирает задание |
| `manualGeneration` | `true` у речевого плана, видео которого пользователь создаёт на сайте провайдера по одной опоре; у остальных планов поля нет |
| `manualVideo` | `true`, если для этой попытки пользователь выбрал создать видео вне приложения по утверждённым опорам и видеопромпту; иначе поля нет |
| `promptMaxChars` | Предел длины видеопромпта провайдера видео в символах; передаётся только этапу prompt, если предел известен |
| `attachedFrames` | Только этапу prompt: утверждённые опоры попытки (`id`, `role`, `timeSeconds`, `path`) по порядку плана и при стыке — последний кадр сюжетного предшественника (`shot`, `position`). У приложенных изображением `attached: true`, вложения идут в этом порядке; неприложенный кадр открой по `path` сам |
| `materials` | Только этапу prompt: материалы клипа для просмотра по необходимости — `sources` (изображения сущностей плана, текст и описание песни), `acceptedShots` (связанные принятые планы: `frames` — их опоры по порядку входов, `video` — монтаж), `problem` — почему вложения не подготовлены. Открывай их сам, если на приложенных опорах чего-то не хватает |
| `continuityFrames` | Только этапу description плана со связанными планами: `frames` — кадры уже принятых планов (`shot`; `position` — `first` или `last`, первый или последний кадр его монтажа; `reason` — `state_from` или `continuity`; `path` — путь для `referencePaths`; `attached` — кадр приложен изображением, вложения идут в порядке `frames` с `attached: true`), `missing` — связанные планы, которые ещё не приняты, `problem` — почему кадры не приложены |
| `stateSources` | Только этапу description: откуда взято каждое значение врезки, `before`/`after` → сущность → свойство → `cast` (начальное состояние кастинга) или `Mxx.before`/`Mxx.after` (изменение плана Mxx на его первом или последнем кадре) |
| `frame` | Только плану с точкой съёмки: факты кадра, посчитанные приложением по точке и схеме локации. `camera` — сторона (`side`), крупность (`size`), угол обзора по горизонтали в градусах (`fov`); `start` и, если кадр меняется, `end` — первый и последний кадр: куда смотрит камера (`looks`), её высота (`camera_height`), герои (`subjects`: `entity`, `lead` — главный, `in_frame`, `x` от −1 у левого края до +1 у правого, `place`, `distance` — до камеры в метрах, `height` — рост в метрах, `frame_height` — доля высоты кадра, `whole` — виден целиком, `hidden_by` — кто закрывает) и объекты схемы (`objects`: `name`, `entity`, если объект — сущность кастинга, `in_frame`, `x` — от и до по горизонтали кадра, `place`, `distance` — до ближайшего края, `height`). `note` — почему фактов нет или они неполны |
| `scheme` | Только плану с точкой съёмки и схемой её локации: схема места вид сверху без цвета — объекты с формой (`rect`, `ellipse`, `polygon`, `line`, `point`; координаты в метрах), высотой и объёмом. По ней видны форма, протяжённость и высота каждого объекта и подъём его низа над землёй |
| `savedLooks` | Только этапам description и prompt, если у провайдера видео есть модель, которая держит облик сущности по сохранённому образу, и у героев плана такой образ есть: `model` — модель видео, которая получит образы (модель проекта, а если она образов не принимает — первая модель провайдера с образами), `limit` — сколько образов она примет в одном запросе, `entities` — герои с образом (`code`, `name`, `kind`). Если образов больше предела, здесь только герои, выбранные пользователем |
| `note` | Замечание пользователя при доработке |

После этих инструкций приложение добавляет раздел «Указания провайдера» для провайдеров видео и изображений, выбранных в проекте: модели, слоты, обязательные параметры и ограничения конкретного сервиса. Следуй им вместе с `capabilities`; если раздела нет, опирайся только на объявления.

Используй сведения только для выбранного плана. Сохраняй принятые совместимые опоры и исправляй только затронутый этап; при доработке меняй только названное в `note`. Если контекста недостаточно, заверши задание понятной ошибкой — вместо JSON верни одну-две фразы с причиной, приложение покажет их как отказ. Противоречия сценария на этапе description — не такой отказ: о них отвечай по разделу «Противоречия сценария». Не выдумывай внешность, файлы, параметры модели, путь WAV, цену или факт согласования. Обложка проекта не используется как референс, опора или вход генерации.

## Состояние и непрерывность

Состояние плана вычислено из кастинга (`initial_state`) и цепочки `state_from`/`state_changes` сценария; врезка `brief` — его запись словами. Собственного хранилища состояния у задания нет.

- Для первого кадра используй `before`; изменения текущего плана происходят во время действия и дают `after`, а не появляются заранее.
- Учитывай последствия прежних событий: загрязнение и влажность, повреждения одежды и внешности, усталость и развитие эмоций, состояние транспорта, положение и принадлежность предметов. Они действуют до предусмотренного сценарием изменения. Отсутствие героя в нескольких планах, смена ракурса, склейка или чистый референс не возвращают его в исходное состояние; мытьё, переодевание и восстановление предметов не выдумывай.
- Устойчивое последствие отличай от временного положения предмета и разового жеста; принадлежность предмета (`owner`) не доказывает его положение.
- Кадры `continuityFrames` — кандидаты, а не требование. Приложение отобрало сюжетного предшественника (`state_from`) и более ранние планы, названные в `continuity`, но не знает, продолжает ли план их изображение. Решай по `continuity` и постановке:
  - если `continuity` требует совпадения с планом (планировка, свет, поза, ракурс, положение предмета, одежда), сверяй с его кадром и укажи `path` кадра в `referencePaths` опоры, которой это совпадение нужно; в промпте опоры назови кадр («последний кадр плана M05») и скажи, что из него взять, а что меняется (ракурс, крупность, движение камеры). Кадр в `referencePaths` уходит генератору целиком, со всеми, кто на нём есть, и со своим ракурсом. Поэтому не добавляй его, если нужное совпадение уже задают `frame` и `scheme` (стороны, расстановка, форма ориентиров) или его можно передать словами (сторона дороги, направление движения): сверь кадр сам и опиши совпадение в промпте опоры. Тем более не добавляй, если на кадре есть герои, которых нет в этом плане;
  - если план продолжает изображение без смены точки и крупности (камера стоит там же, где в конце предшественника, и первый кадр должен совпасть с его последним), сделай первую опору самим этим кадром: копией (`copyOf` с `path` кадра, пустой промпт, без референсов). Кадр, заново нарисованный по референсу, немного отличается, и на стыке будет заметный скачок. Остальные опоры строй от этой копии;
  - если план не продолжает изображение (жёсткая склейка в другое место, упоминание для контраста, ссылка на событие без общих предметов в кадре), кадр не используй;
  - на стыке с предшественником положения сверяй с его последним кадром: пропущенное перемещение уже входит в `before`. Расхождение кадра с врезкой назови в описании, а не исправляй молча.
- В разделе «Непрерывность» описания назови кадры, с которыми сверялся, и планы из `missing`, совпадение с которыми не проверено. Без `continuityFrames` или при `problem` сверяй только по врезке и так и напиши.
- Внешность описывай признаками из `appearance` кастинга. Сущность в кадре без изображения и описания внешности назови в описании: её нужно нарисовать или загрузить до генерации, выдумывать внешность нельзя.
- Если у сущности несколько изображений, выбирай `referencePaths` по их примечаниям (`imageNotes`): ракурс, свет, состояние (включённый свет, открытая дверь, одежда героя). Первое изображение — основное для карточек, но не обязательно подходящее этому плану; если примечания не решают выбор, открой изображения по путям. В «Непрерывности» назови, какое изображение взято и почему.
- Место действия из «В кадре (референсы)», видимое на опоре, всегда идёт в её `referencePaths`: без изображения места генератор придумает окружение сам, а изображения героев его не заменяют. Из изображения места бери вид и фактуру, ракурс задают точка съёмки и промпт опоры.
- При конфликте врезки, изображения кастинга или замечания с действующей постановкой обозначь расхождение в описании. Постановку, кастинг и состояние исправляет пользователь в сценарии и кастинге приложения; задание не подменяет их своим текстом и не объявляет неизвестную деталь установленной. Если расхождение не даёт подготовить непротиворечивые опоры, верни отказ по разделу «Противоречия сценария».

## Противоречия сценария (этап description)

Промпт опоры переносит состояние из врезки, поэтому противоречие врезки с действием, камерой или кадрами `continuityFrames` переходит в изображение. Если из-за него непротиворечивые опоры не подготовить, вместо описания верни отказ `stage: "blocked"` ([форма](references/app-proposal.md#blocked)). Пользователь не видит вычисленного состояния: отказ должен сам объяснить, что не так, где это задано и чем заменить.

- Каждое противоречие — отдельный элемент `problems`. Не объединяй разные поля в один элемент и не включай то, что опорам не мешает.
- Противоречие значения врезки: `phase` — кадр (`before` — первый, `after` — последний), `entity` и `property` — ключи из `brief.<phase>.state`. В `conflict` процитируй текущее значение, процитируй текст, с которым оно расходится (действие, камера, `continuity`, другое значение врезки, кадр плана из `continuityFrames`), объясни, почему вместе они невозможны, и назови источник значения из `stateSources`: «из начального состояния кастинга», «задано на первом кадре M08».
- `fix` — полное новое значение этого свойства на этом кадре этого плана, в стиле значений врезки и согласованное с действием и остальными значениями. Приложение по кнопке пользователя запишет его в `state_changes` текущего плана; кастинг и другие планы не меняются, следующие планы унаследуют новое значение. Если значение из кастинга или более раннего плана неверно и там (например, поза из другого места дошла через начало плана заново), всё равно предложи `fix` для текущего плана и в `conflict` назови, где ещё стоит его поправить.
- Если противоречие не снять значением этого кадра (нужна правка действия, камеры, кастинга или другого плана), укажи `fix: null` и в `conflict` напиши, что и где поправить.
- Расхождение внутри постановки без поля состояния (действие против камеры, `continuity` против действия) — элемент с `field` (`action`, `camera`, `continuity`, `references` или `viewpoint`) и `conflict`, без исправления.
- Если в контексте есть `frame`, до расстановки сверь с ним `camera`, `action` и `continuity`. Противоречие — когда текст требует видеть в кадре то, что по `frame` за его краем или под ним, или обещает, что видное по `frame` в кадр не попадёт; называет у героя или ориентира другую сторону кадра, другую сторону съёмки или направление взгляда; задаёт другую крупность фигуры (в полный рост, по пояс — против `whole` и `frame_height`); называет камеру неподвижной, хотя точка меняет её место, направление, высоту или наклон за план. Противоречие и событие действия у ориентира, которого по `frame` нет в кадре в этот момент (герой останавливается у бордюра, а бордюр под нижним краем): модель видео дорисует такой ориентир где придётся. Каждое расхождение — отдельный элемент `problems` с `field` того поля, где написан текст (`camera`, `action`, `continuity`), или с `field: "viewpoint"`, если правильнее подвинуть точку съёмки на карте. В `conflict` процитируй текст, приведи факт из `frame` словами — где, на каком расстоянии, какая часть кадра — и скажи, что поменять: текст или точку. Расхождение, которое кадр не меняет («в двух шагах» вместо 1,8 м), не включай.
- `reason` и `conflict` читает пользователь, а не программа: поля называй так, как он видит их на странице «Сценарий» — «Камера», «Действие», «Непрерывность (стыки с соседями)», «В кадре (референсы)», «Точка съёмки», свойства состояния — словами врезки (`paragraph`). Ключи JSON (`camera`, `action`, `frame`, `whole`, `position`) в этих текстах не пиши: «поправьте поле camera» пользователю непонятно, «поправьте «Камеру» плана» — понятно.
- `reason` — одна фраза итога: сколько противоречий и что они ломают.

## Длительность и опоры (этап description)

Длительность запроса `D` (`requestSeconds`) вычисляется из окна `T` по `settings.duration_rule` и сетке длительностей подходящей модели из `capabilities` (у сборки из опор — иначе, см. «Сборка из опор» ниже):

| `duration_rule` | Правило | Примеры при шаге 1 с |
| --- | --- | --- |
| `min_supported_strictly_greater_than_window` | Минимальная поддерживаемая длительность строго больше окна | 4,9 с → 5 с; ровно 5 с → 6 с; 5,1 с → 6 с. Если доступны только 5 и 10 с, окну ровно 5 с нужен запрос на 10 с |
| `min_supported_not_less_than_window` | Минимальная поддерживаемая длительность не меньше окна | 4,9 с → 5 с; ровно 5 с → 5 с; 5,1 с → 6 с |
| `exact_window` | Длительность равна окну | 5 с → 5 с; 5,1 с → ошибка: нужна другая модель или окно |

Секунду до округления не добавляй. Окно длиннее предела модели требует разбиения или другой постановки у владельца сценария: не сдвигай окна и не склеивай генерации. Запрос более короткой длительности предпочтительнее ускорения клипа выше 1,2× при монтаже.

Сколько опор и где:

Если передан `keyframeCount`, число опор выбрал пользователь: верни ровно столько (при 1 — одна опора `K01` первого кадра, при 2 — первый и последний кадр), а правила ниже определяют только их назначение и время. Ответ с другим числом опор приложение отклоняет.

1. По умолчанию — две опоры: первый и последний кадр (`before` и `after`). Конец плана тогда держит изображение, а не слова, и модель видео точнее приходит к нужной позе и кадрированию.
2. Одна опора (только `K01`, конечное состояние описывает видеопромпт словами) — в двух случаях:
   - конечную опору трудно сделать согласованной с первой: камера сильно меняет ракурс, открывает пространство, которого нет на первой опоре, или конечный кадр требует выдумать место. Две опоры с разной перспективой видео не исправит: предметы поплывут, модель начнёт склеивать;
   - камера неподвижна, а первый и последний кадр почти совпадают: тот же фон, герои на тех же местах в тех же или близких позах, за план меняется немного (герой подошёл на несколько шагов, повернул голову, перехватил предмет). Две почти одинаковые опоры модель видео держит неподвижными: застывают герои и среда (осадки, вода, дым, листва), а чтобы заполнить переход, модель вводит постороннее движение — транспорт, свет фар, прохожих. С одной опорой движение свободнее, но конец, описанный словами, выходит приблизительным, поэтому видеопромпт называет главное.

   При неподвижной камере две опоры нужны, когда последний кадр заметно отличается от первого: герой пересёк кадр, целиком сменил позу (сидел — встал), положение главного предмета стало другим.
3. Три и больше — только когда без промежуточного кадра не передать контакт или поворот в середине плана: рука уже держит предмет, герой завершил поворот, машина достигла нужной стороны кадра, в кадре на время появился персонаж (пункт 8). Каждая лишняя опора — новый риск: предметы между опорами, нарисованными по отдельности, плывут и меняют размер. Опоры ради заполнения лимита не нужны; 5–6 — только для длинных планов с несколькими фазами.
4. Для каждой опоры укажи в описании, что она фиксирует. Между опорами оставляй физически достаточное время. Время опоры — желаемый ориентир, а не подтверждение его передачи сервису: если модель не объявляет параметр времени кадра, момент описывается в промпте, точное попадание не обещается.
5. Различай шкалу запроса `D` и монтажный участок `T`. Конечная опора — конечное состояние плана в конце запроса `D`. Отдельную опору к концу участка `T` и опору-копию для удержания до конца запроса не делай: секунды после окна приёмка отрезает или подгоняет скоростью, а неподвижное начало или конец держит удержанием кадра. Событие, которое должно завершиться к стыку с соседним планом, ставь в «Событиях плана» к концу участка `T`, а не к `D`.
6. Две одинаковые опоры в одном плане не делай: модель видео держит неподвижным всё, что на них совпадает, — героев и среду (осадки, вода, дым). Если между двумя моментами ничего видимого не меняется, второй опоры не нужно: опиши удержание позы в видеопромпте или оставь одну опору по пункту 2. Копией (`copyOf`) бывает только первая опора — кадр принятого плана из `continuityFrames` по правилу о кадрах других планов выше.
7. Изображения сущностей из кастинга помогают нарисовать опоры и идут референсами, но сами опорами не становятся.
8. Если персонаж, транспорт или предмет есть в кадре только между первой и последней опорой (входит и уходит, пробегает, проезжает мимо), добавь промежуточную опору в момент, когда он хорошо виден, и укажи изображения его сущности из кастинга в `referencePaths` этой опоры. Без такой опоры модель видео знает о нём только по словам промпта и придумывает его сама: лишние люди, чужая внешность, размытые фигуры. Если ни одна модель провайдера видео не объявляет промежуточных опор или число опор задано `keyframeCount` и места для такой опоры нет, напиши в описании, что этот персонаж будет только в промпте и его внешность не закреплена.

**Сборка из опор.** Если в плане `static_shot: true`, видео не генерируется: приложение собирает его из опор, показывая каждую со своего времени до следующей, а изменившуюся область берёт из опоры только там, где она отличается от `K01`; медленный наезд или отъезд делает сборка, поэтому «наезд», «отъезд» или «камера неподвижна» в постановке опор не меняют — все они одного ракурса и крупности, а при отъезде `K01` показывает весь кадр, которым план закончится. Правила числа опор выше к такому плану не применяются. Длительность запроса — окно `T`, округлённое вверх до целого: `settings.duration_rule` и сетка длительностей моделей к такому плану не относятся. `K01` — первое состояние на 0 с, каждая следующая опора — следующее состояние со временем начала по постановке; конечной опоры нет. Если постановка не называет смен, опора одна — `K01`: неподвижный кадр на весь план. Промпт `K01` описывает кадр целиком. Промпт каждой следующей опоры — правка `K01`: тот же кадр, ракурс, крупность, фон и предметы, меняется только названное состояние (какая секция горит, что на табло) и его прямые следствия — свет лампы и отблески на ближайших поверхностях. Не вводи между опорами движения и новых предметов: всё, что меняется вне области состояния, на сборке пропадёт. Свет сцены меняй, только если постановка называет смену всего кадра (время суток, погода, освещение всей сцены): такая опора меняет освещение и цвет кадра целиком, а ракурс, крупность, предметы и их положение остаются как у `K01` — сборка плавно растворит в неё весь кадр, длину растворения задаёт пользователь на шаге «Сборка». Свет от источников за кадром (фары, вспышки) и осадки в такие опоры не рисуй: их добавляют эффекты после сборки. В описании перечисли состояния с моментами смены и отметь те, что сменяют весь кадр.

Пример для окна 6,8 с, правила «строго больше окна» и запроса 7 с: K01 исходное положение; K02 около 3,5 с, колёса остановились; K03 конечное состояние на 7 с. Для спокойного плана той же длины хватит двух опор.

Описание словами включает постановку, первый кадр, расстановку, события плана, план опор и рекомендуемые модель и режим с причиной выбора: пользователь видит их вместе с описанием, отдельного согласования модели нет.

## События плана (этап description)

В описании выдели раздел «События плана» — нумерованный список из 1–5 обязательных видимых событий внутри ролика в том порядке, в котором они должны произойти. Для каждого события укажи:

- время от начала запроса: интервал («2–4 с») или момент («к 5,5 с»);
- наблюдаемое действие: кто, что делает, с каким предметом, в какую сторону;
- строку или слово песни из `scene.original`, на которые приходится событие, если постановка связывает его с песней;
- «короткое», если событие длится меньше секунды (жест, взгляд, касание).

События берутся из `action`, `state_changes` и акцентов песни плана; событий, которых нет в постановке, не добавляй. Состояния `before` и `after` — начало и итог плана, событиями они не считаются. Опоры фиксируют положения между событиями: в плане опор ссылайся на события номерами («K02 — после события 2»). Видеопромпт описывает те же события в том же порядке и времени, а проверка полученного видео ищет их на кадрах, поэтому список — общий источник для обоих этапов.

**Действия должно хватить на весь запрос.** Секунды без видимого действия модель видео заполняет неподвижностью: герой доходит до места и застывает до конца, а растянутое на весь план короткое действие выходит неестественно медленным. Перед ответом прикинь время действия: путь героя (по точке съёмки — расстояние между его `start` и `end` на схеме, иначе по постановке) при обычном шаге — около 1,3 м/с у взрослого и около 1 м/с у ребёнка — и время остальных событий. Если действия меньше длительности запроса больше чем на пару секунд, не замедляй его: разверни действия постановки в цепочки видимых шагов, чтобы у каждого героя в кадре было действие на каждый отрезок (например, «ищет что-то в карманах» — хлопает по ним, заглядывает в один, проверяет другой, возвращается к первому). Новых событий не добавляй. Если и так действия не хватает, напиши в описании отдельной строкой: «Действия мало: около N с из M с», — чтобы пользователь дополнил «Действие» плана или сократил план.

**Действие должно поместиться в запрос.** Обратная проверка той же прикидки: сложи минимальное время событий по порядку. Мелкая работа руками — достать предмет из кармана или из-под одежды, положить, перехватить, нащупать и повернуть деталь, застегнуть — занимает у модели видео не меньше 1–1,5 с на каждое действие и выходит разборчивой, только если идёт медленно; поворот головы или корпуса — около секунды; удержание итоговой позы, если оно нужно сюжету, — не меньше секунды. Если сумма больше длительности запроса, модель видео не сделает всё: пропустит события, перескочит через них или смажет руки. Не сжимай события и не выбрасывай их сам: верни отказ `stage: "blocked"` ([форма](references/app-proposal.md#blocked)) с элементом `problems` с `field: "action"`; в `conflict` перечисли события с оценкой времени, назови сумму против длительности запроса и предложи, что сократить: начать план с уже выполненного действия (предмет уже в руке — «Первый кадр» плана), перенести действие в соседний план или оставить одно главное действие.

## Расстановка (этап description)

В описании выдели раздел «Расстановка»: где камера, герои и неподвижные ориентиры места на первом кадре, а при конечной опоре — и на последнем. Пользователь проверяет его текстом до того, как нарисована хоть одна опора, поэтому расстановка однозначна и не оставляет генератору выбора, кого куда поставить. У крупного плана, деталей и вставок без ориентиров места хватает одной-двух фраз.

- Камера: откуда снимает (сторона, высота — уровень глаз взрослого, ребёнка, у земли), куда смотрит и что поэтому уходит в глубину кадра.
- Каждый герой и предмет в кадре: где по горизонтали (левая, средняя, правая треть), по глубине (передний, средний, дальний план), какую часть высоты кадра занимает, в фокусе или размыт и рядом с каким ориентиром стоит: «у правого края барной стойки, в двух шагах за барменом, примерно в половину его высоты в кадре».
- Ориентиры места — то, что не двигается и по чему зритель узнаёт место: стены, колонны, двери, окна, мебель, деревья, края дороги. Назови те, что попадают в кадр при этом направлении камеры, с их местом в кадре. Заметный ориентир, который остаётся за кадром, отметь одной фразой («люстра выше верхней границы»): пользователь увидит, что он учтён. В промпт опоры такой ориентир не переносится: названный объект генератор склонен нарисовать.

Если в контексте есть `frame`, геометрию расстановки бери из него: это не догадка по словам `camera` и изображениям места, а расчёт по точке съёмки, которую поставил пользователь. Сторону и высоту камеры, направление взгляда, треть по горизонтали, расстояние до камеры, долю высоты кадра, видна ли фигура целиком и кто её закрывает переноси как есть. Объекты схемы с `in_frame: true` — ориентиры в кадре на месте из `place`; остальные за кадром с той стороны, что в `place`, и заметные из них отметь в расстановке одной фразой по правилу выше. Форму, протяжённость и высоту ориентиров бери из `scheme` и называй в промпте опоры прямо, иначе генератор додумает их сам: `line` без `smooth` — прямые отрезки между точками, а не кривая; объект с `elevation` поднят над землёй — назови, на чём он держится, если это видно в кадре. Чего во `frame` нет — точное место внутри трети, позы, свет, мелкие предметы, — выбирай по постановке. Расхождение `camera`, `action` и `continuity` с `frame` проверь до расстановки по разделу «Противоречия сценария». Если в `frame` есть `note`, фактов кадра в нём нет или они неполны: расставляй по остальным источникам. На этапе prompt движение камеры в видеопромпте ведёт от кадра `start` к кадру `end` и не вводит в кадр то, что во `frame` остаётся за ним.

Источники расстановки по старшинству: `frame`, если он есть; `camera` и `action` плана; принятый кадр соседнего плана из `continuityFrames` — где стояли герои и ориентиры; `layout` врезки и изображения места. Положение героя на стыке берётся из последнего кадра предшественника: если он остановился у колонны у входа, в следующем плане он у той же колонны, как бы ни менялся ракурс. Ориентиры с кадра предшественника, попадающие в новый ракурс, переходят в расстановку все; не упоминай их, только если они остаются за кадром. Чего нет ни в постановке, ни в кадрах, выбери сам без противоречия им и пометь «выбрано агентом»: пользователь увидит это и поправит текстом. Расхождение постановки с принятым кадром назови по разделу «Состояние и непрерывность».

Промпт каждой опоры переносит расстановку своего кадра целиком своими словами, без ссылок на описание, кроме ориентиров за кадром.

## Герои с сохранённым образом

Если в контексте есть `savedLooks`, облик героев из `savedLooks.entities` в видео держит сохранённый образ у провайдера видео, а не только опоры: образ сделан по референсам героя и уходит в запрос вместе с опорами. Облик остальных героев держат только опоры и видеопромпт.

- Этап description. Героя с образом можно поставить так, как без образа рискованно: спиной или боком к камере, срезанным краем кадра, далеко в глубине, входящим в кадр после первой опоры. Постановку сценария ради этого не меняй: образ расширяет выполнимое, а не отменяет `camera` и `action`. Опоры такого героя по-прежнему рисуются по его референсам: генератор изображений образ не получает. Насколько модель держит облик героя, которого нет на опоре, сказано в указаниях провайдера видео. Опор делай столько, сколько примет `savedLooks.model` (её слоты кадров в `capabilities`): при большем числе опор запрос уйдёт модели без образов, и облик героев будут держать только опоры.
- Этап prompt. Каждое упоминание героя из `savedLooks.entities` отмечай меткой по правилу указаний провайдера видео — и в `prompt`, и в `translation`, у тех же упоминаний: к отправке пользователь может выбрать любой из двух текстов. Героев без образа не отмечай; разных героев с меткой — не больше `savedLooks.limit`. Без `savedLooks` меток в промпте нет.

## Изображения опор

Промпты опор из описания приложение без изменений передаёт выбранному в проекте провайдеру изображений; как писать их для него — в указаниях провайдера изображений. Само задание изображений не рисует. Ограничения `generation.video` и правила конкретной видеомодели (пропорции, слоты) к опорам автоматически не применяются.

## Запрос видео

Запрос к провайдеру видео собирает приложение: утверждённые опоры по порядку плана — в слоты кадров модели (первая — начальный кадр, последняя — конечный, остальные — промежуточные), срез речи — в звуковой слот, длительность — `requestSeconds`, разрешение и пропорции — из настроек проекта. Модель — предпочтение `settings.model`, если оно совместимо, иначе совместимая модель провайдера. Поэтому видеопромпт обозначает входы в порядке опор, а описание выбирает `requestSeconds` и число опор, которые примет модель из `capabilities`: промежуточные опоры — только если в `capabilities` есть модель с такими слотами.

## Речевые планы

Для плана с `lipsync: true` губы синхронизируются с фрагментом исходной песни, а не с синтезированной речью.

- Длительность запроса (`requestSeconds`) — в пределах `lipSync` контекста: столько звука принимает провайдер видео. Срез WAV приложение режет той же длины от начала окна, запас после окна уходит в монтаж обрезкой.
- Первый кадр: рот и лицо открыты; головные уборы, шарфы и предметы из состояния `before` не закрывают губы.
- Аудиовход — только готовый точный срез песни (WAV), в запрос его передаёт приложение; в контексте он — `speech` (`path`, `sourceSeconds`). На этапах описания и промпта `speech` может ещё не быть: приложение режет WAV после описания, планируй длительность по окну плана. Не заменяй WAV синтезом или образцом тембра.
- Режим с точным аудиовходом должен быть явно объявлен в `capabilities`: слот аудио или аргумент lip sync. Аудиореференс голоса не равен воспроизведению точного WAV, а наличие аудиовхода само по себе не гарантирует lip sync. Если в переданных `capabilities` моделей со звуковым входом нет, приложение не запускает задание; если такого режима всё же нет, сообщи это понятной ошибкой.
- При `manualGeneration: true` видео речевого плана создаёт пользователь на сайте провайдера по одной опоре, срезу речи и видеопромпту, запроса к сервису нет. Поэтому пределы `lipSync` и требование режима с точным аудиовходом в `capabilities` к такому плану не относятся и не служат причиной отказа. `requestSeconds` — наименьшее целое число, удовлетворяющее `settings.duration_rule` относительно окна, без сетки длительностей моделей.
- Реплику приводи дословно из текста песни на исходном языке; промпт описывает артикуляцию, а голову и тело — спокойными, но живыми: дыхание и моргание без крупных движений. `D` не короче фразы; не ускоряй речь ради окна — при нехватке длины окно меняется в сценарии.
