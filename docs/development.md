# Разработка SongFrame

Руководство по запуску из checkout, устройству приложения, сборке и выпуску поставок. Возможности продукта и пользовательские инструкции находятся в [README](../README.md), обязательные правила разработки — в [AGENTS.md](../AGENTS.md).

Менеджер агентских заданий, API, права и ограничения описаны в [агентских заданиях](agents.md), предложения и применение сценария — в [сценарном процессе](scenario-workflow.md), согласования и границы приёмки — в [производственном процессе](production-workflow.md), ручные пробы — в [монтаже](montage.md). Контракты Python-инструментов находятся в [карте tools](../tools/README.md) и README каждого инструмента. Рецепт подготовки встроенного Python, медиа и проверок поставки поддерживается в [scripts/runtime](../scripts/runtime/README.md).

## Состав

Страницы «Производство», «Сцены», «Проверки», «Аниматик» и «Монтаж пробы» открываются через общий `RequireScenario`. Пока нет доступных сцен, используется один полноширинный `ScenarioRequired` с одинаковым сообщением и действиями; дочерняя страница и её проверки среды ещё не запускаются. Готовность сценария определяет общий `readScenarioRegistry`, независимо от наличия инструментов генерации. Статусы Python и провайдеров генерации вычисляются отдельно от наличия сцен.

```text
tools/              Инструменты на Python: запросы провайдеров генерации, приёмка, проверки, сборка аниматика, пакет для монтажёра
tools/testdata/     Синтетический проект-образец «Пробный клип» с небольшими тестовыми медиа
skills/             Тексты промптов, которые приложение вкладывает в задания агента: ai-clip-scenario, ai-clip-scene
templates/project/  Шаблон папки нового проекта: структура, README, .gitignore
src/main/           Главный процесс Electron: проекты, статус, исходники, среда, запуск инструментов
src/preload/        Мост window.api между рендерером и главным процессом
src/renderer/       Интерфейс: React + MUI, светлая и тёмная темы
src/shared/         Типы и контракт API, общие для обеих сторон
build/              Сборка приложения (build/app) и установщики (build/release); вне Git
```

## Зависимости разработчика и временные внешние зависимости

Таблица ниже относится к запуску из checkout и сборщику. В готовые Linux AppImage и Windows ZIP входят Python, Python-библиотеки, FFmpeg/ffprobe и клиенты встроенных [провайдеров генерации](providers/README.md). Отдельно устанавливать их пользователю не нужно. Веса модели устанавливаются отдельно по [инструкции по модели распознавания](../README.md#модель-распознавания). Разработка без `yarn prepare:runtime` может использовать системный Python; клиенты провайдеров генерации — Python-модули `tools/<id>_request/`, отдельно их устанавливать не нужно, а особенности подключения при запуске из checkout описаны в документах провайдеров.

Для запуска интерфейса из checkout нужны Node.js и Yarn; готовому приложению их отдельная установка не требуется. Страница «Среда» показывает готовность встроенных ресурсов и необязательных внешних CLI.

В корне checkout выполните `nvm install` и `nvm use`: обе команды читают `.nvmrc`, как CI и Release. Репозиторный `.gitignore` содержит исключение для этого файла, поэтому глобальное правило `.nvmrc` не мешает хранить общую версию в Git.

Модель установите по [инструкции по модели распознавания](../README.md#модель-распознавания); путь одинаков для разработки и готового приложения.

Если `pip` отказывается ставить пакеты в системный Python, добавьте `--break-system-packages` или используйте виртуальное окружение.

### Готовое приложение на Windows

Сборка выполняется на Linux командой `yarn dist:win`. Пользователь Windows получает готовый ZIP, распаковывает его целиком и запускает `SongFrame.exe`. Установка Node.js, Yarn, Python и pip не требуется. Для проверки встроенного runtime в ZIP есть `check-runtime.cmd`; инструкция лежит в `ПРОЧТИ.md` рядом с EXE.

Windows ZIP включает Python, FFmpeg/ffprobe и клиенты встроенных провайдеров; в VM проверены runtime, медиа, загрузка модели и распознавание; вход в провайдера проверялся прежним официальным CLI, собственный клиент провайдера в VM не проверялся. Модель устанавливается отдельно на любой ОС. Внешние Claude/Codex устанавливаются отдельно; менеджер агентских заданий приложения сейчас поддерживает только Linux.

Автоматическое распознавание на Linux и Windows запускается напрямую с `--allow-network`: флаг снимает проверку OS-изоляции, модель всё равно читается только с диска, скачивание отключено. Настраивать user namespaces или AppArmor для разметки не требуется.

## Запуск и проверки из checkout

Команды выполняются из корня checkout после установки [зависимостей разработчика](#зависимости-разработчика-и-временные-внешние-зависимости):

```sh
yarn install          # зависимости и бинарник Electron
yarn dev              # запуск с горячей перезагрузкой
yarn build            # сборка в build/app
yarn prepare:runtime  # встроенный Python и библиотеки для текущей ОС
yarn smoke:runtime    # проверка переноса runtime без Python в PATH
yarn start            # запуск собранного приложения
yarn typecheck && yarn test
yarn lint             # ESLint по src/, scripts/ и конфигурации сборки (ошибки и предупреждения не допускаются)
yarn format:check     # Prettier: проверка форматирования; yarn format переформатирует
yarn dist:linux       # AppImage со встроенными Python и FFmpeg, без весов модели в build/release
yarn dist:win         # Windows ZIP, собирается на Linux без Wine
```

Перед коммитом выполняется `yarn typecheck`. Сборка приложения находится в `build/app`, установщики — в `build/release`; обе папки вне Git. AppImage после сборки остаётся в штатной `build/release`: копирование бинарника за пределы репозитория требует явного поручения.

## Устройство и стиль кода

Исходники настольного приложения на Electron, TypeScript, React и MUI лежат в `src/main`, `src/preload`, `src/renderer` и `src/shared`. Главный процесс выполняет работу с файлами и процессами; renderer не обращается к файловой системе напрямую. Новая возможность проходит через функцию главного процесса, IPC и метод в `src/shared/api.ts`. Независимая от Electron логика главного процесса проверяется тестами `src/main/*.test.ts`. Просмотр и редактирование не требуют Python и FFmpeg — они нужны производству.

Страницы находятся в `src/renderer/src/pages/{PageName}/{PageName}.tsx`, экспортируются через `pages/{PageName}/index.ts` и `pages/index.ts`. Публичный `index.ts` страницы экспортирует только её. Внутренние компоненты, hooks, типы и функции остаются в папке страницы; общие для нескольких страниц компоненты — в `src/renderer/src/components`. Один компонент — один файл. Подробные правила, в том числе правила `AgentButton` и PythonLauncher, находятся в [AGENTS.md](../AGENTS.md#приложение).

Правила темы, структуры и компоновки интерфейса собраны в [документации UI](ui/README.md).

Стиль кода приложения задают `.prettierrc.json` (точка с запятой в конце выражения, одинарные кавычки, строки до 160 знаков, пустая строка в конце файла) вместе с `.editorconfig` (UTF-8, LF, отступ два пробела, в Python четыре) и `eslint.config.mjs` (рекомендованные правила ESLint и typescript-eslint, правила хуков React, импорты типов через `import type`); Prettier и ESLint не спорят благодаря `eslint-config-prettier`. Python-инструменты, шаблон и скиллы этими проверками не охвачены.

Стиль Python задаёт `pyproject.toml` (ruff); переформатирование существующего кода выполняется отдельным поручением. Изменение контрактов хранения одновременно вносится в `templates/project` и инструменты; существующие проекты обновляются по поручению. Данные клипов хранятся в отдельных проектах, а не в репозитории комплекса.

## Отладка

Переменные окружения для отладки: `SONGFRAME_LOCAL_DIR` (отдельная папка локального состояния), `SONGFRAME_ROUTE` (стартовый маршрут, например `#/environment`), `SONGFRAME_SCREENSHOT` (путь PNG: снимок окна и выход), `SONGFRAME_PRICING_FILE` (подмена базовой таблицы цен провайдера в тестах); тестовый провайдер `test` и его переменные — в [документации провайдеров](providers/README.md#тестовый-провайдер), отладочные переменные конкретного сервиса — в его документе. Клавиша F12 открывает инструменты разработчика.

### Журналы и отчёт для разработчика

Все журналы лежат в каталоге состояния (`localDir`: Linux `${XDG_CONFIG_HOME:-~/.config}/songframe`, Windows `%APPDATA%\songframe` или `SONGFRAME_LOCAL_DIR`) и переживают перезапуск и сбой программы.

- `jobs/<id>.log` — вывод задания инструментов; рядом `jobs/<id>.json` — его сведения `JobInfo` без текста лога (название, вид, проект, шаги со статусами, статус, `startedAt`/`finishedAt`, код, причина ошибки). Сведения записываются атомарно при старте, смене шага и завершении. При запуске окна `Jobs` загружает последние 200 заданий, более старые `.json` удаляются вместе с `.log`; задание, которое по сведениям ещё выполнялось, получает статус `interrupted` («Прервано закрытием или сбоем программы») и сохраняется так. Повреждённый файл сведений пропускается. Текст лога прошлого сеанса читается из файла по `jobs:get`/`jobs:copyText`. Служебные проверки поставки (`SONGFRAME_LINUX_SMOKE`, `SONGFRAME_RUNTIME_SMOKE`) журнал пользователя не загружают; смена ресурсов на странице «Среда» продолжает тот же журнал.
- `jobs/agent-<id>.json` — задания агента ([агентские задания](agents.md)).
- `logs/app.log` — журнал сбоев: строки `время [вид] текст`, продолжение стека с отступом. Первая строка сеанса `[session] Запуск: SongFrame …; Electron …; Node …; ОС …; архитектура …`. Пишутся `uncaughtException` и `unhandledRejection` главного процесса, `render-process-gone` и `unresponsive` окон, `child-process-gone`, ошибка запуска (`startup`) и ошибки renderer (`renderer:error`, `renderer:unhandledrejection`: `window` `error`/`unhandledrejection` подключены в `src/renderer/src/main.tsx` и уходят по каналу `diagnostics:rendererError`). Домашний каталог заменяется на `~`, похожие на токены значения скрываются; тела запросов и сообщения агента не пишутся. Больше 1 МБ — файл переименовывается в `logs/app.1.log` (хранится одна предыдущая копия).
- `logs/session.json` — `{ startedAt, version, pid, clean }`: при старте окна записывается `clean: false`, на `will-quit` — `clean: true`. Если прошлый сеанс не помечен чистым, это записывается в `app.log`, а окно один раз показывает предупреждение со ссылкой на «Журнал заданий».

Кнопка «Сохранить отчёт для разработчика» на странице «Журнал заданий» сохраняет через диалог один файл `songframe-report-<дата>.txt` (до 5 МБ): версии приложения, Electron, Node, ОС и архитектуры, packaged ли сборка, каталог состояния, признак аварийного прошлого сеанса, `app.1.log` и `app.log`, сведения последних 50 заданий инструментов с последними 200 строками их журналов и сводку последних 20 заданий агента (id, задача, провайдер, статус, время, код выхода, диагностика — без промптов и вывода). `settings.json`, файлы входа `providers/*/` и содержимое проектов в отчёт не входят; домашний каталог заменён на `~`. Кнопка «Скопировать журнал» у задания копирует его сведения и журнал в буфер обмена.

Чтобы получить сведения у пользователя (в том числе на Windows без Git и терминала): попросите открыть «Журнал заданий», нажать «Сохранить отчёт для разработчика» и прислать сохранённый файл. Если окно не открывается, тот же каталог состояния можно заархивировать вручную без `settings.json` и `providers/`.

## CI и релизы

GitHub Actions: `.github/workflows/ci.yml` на каждый pull request и push в `main` запускает `yarn lint`, `yarn format:check`, тесты релизного скрипта (`node --test scripts/release/release.test.mjs`), `yarn typecheck`, `yarn test`, набор тестов Python (`tools/run_tests --jobs` по числу ядер, с ffmpeg и Pillow на раннере) и тесты скриптов поставки `scripts/runtime/test_*.py`. Поставки в CI не собираются: перед изменениями сборки их проверяют локально ([проверка AppImage](#проверка-linux-appimage-и-выпуск) или скилл `songframe-build`), а для публикации обе собирает Release. Общий шаг `.github/actions/linux-appimage` проверяет переносимый Python и конечный AppImage в Docker; `.github/actions/windows-zip` запускает тесты `scripts/runtime/test_check_windows_zip.py` и проверяет состав и целостность ZIP без исполнения Windows-кода. Код не подписывается.

Ускорение: CI кэширует загрузку Electron и архив FFmpeg; Release дополнительно кэширует Electron и инструменты electron-builder, загрузки runtime (ключ — закреплённые версии `scripts/runtime/*lock*`), тестовую модель и слои проверочного Docker-образа (тег — хеш `linux-smoke.Dockerfile`, тот же вычисляет `smoke-appimage.mjs` и не пересобирает найденный образ). Поставки передаются задаче публикации артефактом без повторного сжатия и хранятся один день.

Для выпуска откройте **Actions → Release → Run workflow**, выберите ref/ветку и заполните оба обязательных поля: `version` — `X.Y.Z` без `v` (например, `0.2.0`), `description` — описание релиза. Workflow `.github/workflows/release.yml` заранее проверяет, что номер не занят тегом или релизом, и собирает обе поставки из одного точного SHA выбранного ref. Версия в `package.json` меняется только в сборочных checkout, без автоматического коммита в репозиторий.

Только после успеха обеих сборок отдельная задача публикации создаёт тег `vX.Y.Z` на этот SHA и черновик релиза, прикрепляет AppImage, Windows ZIP, SHA256, отчёты проверок и уведомления о лицензиях, затем публикует релиз. Существующие теги и релизы не перезаписываются. Ошибка сборки не создаёт публичный релиз; ошибка загрузки файлов оставляет черновик для разбора. Нативный Windows smoke в этот процесс не входит: VM-прогоны выполняются отдельно по явному поручению.

`yarn dist:*` подготавливает встроенный Python и включает его, инструменты и шаблон проекта в ресурсы приложения вне ASAR. Ресурсы определяются относительно приложения, путь checkout сборщика в код не записывается. Логи и локальное состояние packaged-приложения хранятся в userData. Системный Python/pip и отдельная установка Python-библиотек пользователю такой сборки не нужны. Подготовка, версии и проверки описаны в [scripts/runtime](../scripts/runtime/README.md).

Linux AppImage и Windows ZIP включают Python и FFmpeg/ffprobe. **Веса модели в поставки не входят:** их нужно один раз скачать по [инструкции по модели распознавания](../README.md#модель-распознавания). Модель хранится отдельно и используется повторно после обновления приложения. Распознавание работает локально на CPU/int8 либо NVIDIA CUDA, без обращения к Hugging Face во время анализа. В Windows VM проверены runtime, FFmpeg/ffprobe, вход в провайдера генерации (прежним официальным CLI; собственный клиент провайдера в VM не проверялся), загрузка модели и локальное распознавание; полный производственный цикл требует отдельной нативной приёмки. Клиенты встроенных провайдеров написаны на Python и входят в поставку вместе с инструментами ([документы провайдеров](providers/README.md)). На странице «Среда» сначала проверяется вход: без авторизации доступна кнопка «Войти», при действующей — «Сменить аккаунт»; токены входа хранятся в каталоге состояния приложения (`providers/<id>/`). Git устанавливается отдельно и необязателен для локального проекта и рабочих представлений, но нужен для истории/индекса; встроенным провайдерам не нужны системные Node.js/npm и отдельные программы. Внешние Claude/Codex по-прежнему устанавливаются отдельно. Проверка встроенного runtime не подтверждает доступность внешних провайдеров и всех производственных операций: их проверяют отдельно в пользовательском окружении. `yarn build` обновляет только `build/app`; для нового AppImage выполняйте `yarn dist:linux`.

### Проверка Linux AppImage и выпуск

`yarn dist:linux` собирает конечный файл в `build/release`. Веса модели не включаются. Сборщику нужны Node.js/Yarn, tar и zstd; пользователю готового приложения системные Python, Node.js, Yarn и FFmpeg не нужны. Для графического приложения остаются обычные библиотеки Linux-десктопа. Шрифт карточек аниматика DejaVu Sans входит в комплекс вместе с лицензией (`tools/render_animatic_cards/fonts/`), устанавливать его в систему не нужно.

Release использует общий шаг `.github/actions/linux-appimage`: сборка, проверка переносимого Python и smoke **конечного AppImage** в Ubuntu 22.04. Контейнер содержит графические библиотеки, виртуальный экран и espeak-ng для синтеза короткой тестовой речи; Python/Node/Yarn/Git/FFmpeg в ОС не устанавливаются. Сеть при запуске контейнера отключена. Загрузка тестовой tiny-модели происходит заранее в отдельный сборочный каталог `build/runtime/smoke-model`, за пределами упаковываемого runtime. Это техническая фикстура CI, а не выбранная пользователем модель.

Локально ту же проверку можно запустить с Docker и любой заранее скачанной моделью CTranslate2:

```sh
yarn prepare:smoke-model
yarn smoke:appimage --docker --model="$PWD/build/runtime/smoke-model" --output=/tmp/songframe-appimage-check
```

Для повторного прогона используйте новую папку отчёта. Smoke создаёт собственный проект с пробелами/кириллицей, загружает MP3, размечает его внешней моделью, сохраняет подтверждённую строку, строит каркас сцен/карточки и проверяет рабочую папку. Затем переносит проект, временно переименовывает AppImage **внутри build/release**, проверяет повторный запуск и состояние и возвращает файл на штатное место. Пользовательские проекты и текущий выбор не используются. Окна приложения, платные запросы и агентные CLI Claude/Codex не запускаются.

Контейнер использует extract-and-run, поскольку FUSE в нём недоступен; `--no-sandbox` задаётся только этому проверочному запуску. Настройки sandbox обычного приложения не меняются. `NO_CLEANUP` сохраняет распаковку до удаления контейнера. На обычном Linux основной вариант — прямой запуск AppImage. Если FUSE недоступен, поддерживается [официальный extract-and-run](https://docs.appimage.org/user-guide/troubleshooting/fuse.html#extract-and-run-type-2-appimages). Работа на произвольном старом дистрибутиве или CPU не обещается: Python-wheels/FFmpeg требуют glibc 2.28+, Linux x64 и совместимый CPU; целевая базовая проверочная ОС — Ubuntu 22.04, локальная — Ubuntu 24.04.

Перед упаковкой проверяется состав ресурсов и отсутствие весов/репозиторных тестов, сохраняются версии и уведомления поставщиков. Лицензии CPython и статических зависимостей извлекаются из полного архива того же выпуска python-build-standalone; недостающие в wheels тексты FlatBuffers/tokenizers закреплены URL и SHA256. В готовом приложении есть `resources/distribution.json` и `resources/THIRD_PARTY_LICENSES.md`, рядом с AppImage — их копии `linux-distribution.json` и `THIRD_PARTY_LICENSES.md`. После успешного smoke появляются `<имя>.AppImage.sha256` и `linux-smoke-result.json`; Release прикладывает эти файлы вместе с проверенным AppImage. Для Windows ZIP сборка (локальная или Release) создаёт `<имя>.zip.sha256` и `windows-archive-check.json`: проверяются CRC, ресурсы и целевая платформа архива, без нативного Windows smoke. Публикация разрешена только после успеха обеих сборок и проверок.

## Перенос приложения, состояние и проекты

На Linux настройки, текущий проект, история и журналы находятся в `${XDG_CONFIG_HOME:-$HOME/.config}/songframe` — постоянном userData, общем для разработки и AppImage. Файлы: `settings.json`, `current-project.json`, `projects.json`, журналы заданий в `jobs/`, журнал сбоев и файл сеанса в `logs/` ([журналы и отчёт](#журналы-и-отчёт-для-разработчика)). Они сохраняются после перемещения или обновления AppImage. Ресурсы `tools`, `templates`, `runtime` читаются из приложения, записи в каталог AppImage и временный mount не нужны. Файлы моделей хранятся отдельно в каталоге данных по [инструкции по модели распознавания](../README.md#модель-распознавания).

Повреждённый JSON не сбрасывается молча: сообщение указывает файл, его нужно исправить или перенести в резервную папку. Запись настроек и выбора проекта атомарная, при ошибке сохранения прежний файл остаётся целым.

`SONGFRAME_LOCAL_DIR` явно задаёт другую папку для `settings.json`, выбора, истории и журналов — например отдельную постоянную папку рядом с AppImage. Папку рядом с исполняемым файлом приложение само не выбирает: это может быть временная распаковка. Путь к каталогу состояния виден на странице «Среда»; ошибка доступа на запись показывает путь и причину. Интерфейсные предпочтения Electron (например, тема) хранятся в его userData.

Открытие проекта (включая восстановление выбранного проекта при запуске) ничего не пишет в его папку: служебных файлов, launcher и копий справочников в проекте нет, поэтому перенос приложения или проекта не требует обновлять его содержимое. Инструменты запускает приложение через общий PythonLauncher, явно передавая выбранный проект. Старая запись истории с отсутствующим путём сохраняется: её можно забыть в списке проектов, а перенесённую папку открыть заново.

Настройки приложения — обычный `settings.json` в локальном каталоге состояния: Linux `${XDG_CONFIG_HOME:-~/.config}/songframe`, Windows `%APPDATA%\songframe`. `SONGFRAME_LOCAL_DIR` явно задаёт другую папку; фактический путь виден на странице «Среда». Токены входа провайдеров генерации хранит их клиент в подпапке `providers/<id>/` того же каталога, атомарно и с ограниченными правами; файлы авторизации официальных программ сервисов не используются ([документы провайдеров](providers/README.md)).

### Свежесть производных файлов

Карточки сохраняют значимые поля `project_inputs: {name}`, а полный аниматик — `{name, animatic_video}`. Настройки генерации не являются входами уже созданных документов, карточек и видео. Сохранение настроек проекта не запускает Python и не рендерит карточки. `source_hashes` содержит только фактически использованные медиа; полный файл `project.json` в него не входит.

Это единственный формат квитанций и манифестов. При изменении контракта данные рабочего проекта и тестовых фикстур приводятся к нему отдельно; чтение не выполняет скрытую миграцию и не ищет прежние версии в Git. Отсутствующий или повреждённый `project_inputs` считается ошибкой данных.

### Настройки агента

Кнопка «Сохранить настройки агента» отдельно записывает выбор в общий `settings.json` в постоянной папке состояния. Пример блока без секретов:

```json
{
  "agent": {
    "provider": "codex",
    "model": "идентификатор-выбранной-модели"
  }
}
```

Старый файл без `agent` означает «Без агента»; этот вариант также можно выбрать в форме. Остальные поля, включая `toolsRootOverride`, сохраняются. Выбор текстового агента не меняет проектные `generation.video` и `generation.image` и файлы проектов.

## Модель распознавания

В готовом приложении модель скачивается кнопкой **«Скачать модель …»** в окне «Тайминги → Разметить». Кнопка запускает [download_whisper_model](../tools/download_whisper_model/README.md) фоновым заданием приложения со встроенными Python и `huggingface_hub`; системные Node.js, Yarn, Python, pip или отдельный загрузчик hf не нужны. Модель выбирается в окне, папка определяется ею: `${XDG_DATA_HOME:-$HOME/.local/share}/songframe/models/faster-whisper-<модель>` на Linux и `%LOCALAPPDATA%\songframe\models\faster-whisper-<модель>` на Windows. Индикатор и журнал видны в том же окне, повторное нажатие после ошибки использует уже скачанные файлы, после успеха папка выбирается автоматически. Права администратора для папки модели не нужны. Сведения о моделях и ручном скачивании — в [инструкции по модели распознавания](../README.md#модель-распознавания).

При разработке из checkout тот же инструмент можно вызвать системным Python с установленным `huggingface_hub`:

```sh
python3 -B tools/download_whisper_model/download_whisper_model.py --repository Systran/faster-whisper-medium --output "${XDG_DATA_HOME:-$HOME/.local/share}/songframe/models/faster-whisper-medium"
```

Репозитории остальных моделей перечислены в `src/shared/whisper-models.ts`: `Systran/faster-whisper-small`, `dropbox-dash/faster-whisper-large-v3-turbo`, `Systran/faster-whisper-large-v3`.

Модель загружается только с диска: `local_files_only`, `HF_HUB_OFFLINE` и отключение телеметрии сохранены. Устанавливать unshare и менять AppArmor не нужно. Переменная `SONGFRAME_MODEL_DIR` задаёт внешнюю модель для ручного CLI; параметр `--model` имеет приоритет.
