# Интерфейс SongFrame

Работай в корне репозитория; все пути ниже отсчитываются от него. Перед работой прочитай актуальные `AGENTS.md` и `docs/ui/README.md`. Для затронутой задачи используй `docs/ui/layout.md`, `theme.md` и `structure.md` из той же папки; предметные требования процесса ищи в его документации. При противоречии руководствуйся порядком приоритета из README. Документы UI описывают целевой стандарт, а не утверждают, что весь существующий интерфейс уже ему соответствует.

В общих подсказках говори о сущности «агент»; конкретное имя выбранного исполнителя бери из реестра по правилам UI-текстов. Не перечисляй программы в общей инструкции.

При добавлении или переносе подписей применяй `docs/ui/texts.md`: русские UI-тексты принадлежат чистым доменным модулям `frontend/src/shared/texts/`, включая подписи одной страницы. Сохраняй дословные формулировки, владельцев исключений и зависимости ссылок/операций от текста; не добавляй чужой ESLint-рецепт: текущие проверки перечислены в Taskfile и frontend/package.json.

Изучи затронутую страницу, связанные состояния и общие компоненты, прежде чем выбирать решение. Соблюдай границы задачи: приводи затронутые элементы к правилам, не переделывая соседние сценарии без необходимости; предметное исключение объясни и сохрани согласованность процесса. При ревью сообщай о расхождениях, не меняя код без поручения.

## Сначала готовые компоненты MUI

Перед реализацией элемента найди подходящий компонент в установленной MUI и проверь общие компоненты проекта. Используй готовые Accordion, Dialog, Menu, Tabs и другие контролы по их назначению; не воспроизводи их поведение вручную через HTML, CSS или новую React-обёртку. Например, раскрываемый раздел собирается из Accordion/AccordionSummary/AccordionDetails, а не из самодельного details/summary внутри Box.

Собственные компоненты нужны для предметной композиции и повторно используемой логики SongFrame, а не для дублирования библиотеки. Новую базовую обёртку вводи только при конкретной общей потребности, которую существующий компонент не покрывает; сначала проверь документацию MUI и уже принятый в проекте способ. Сохраняй встроенные доступность, клавиатурное управление и состояния библиотеки.

## Не перекладывать работу программы на пользователя

Проектируй обычный сценарий для человека, который не знает внутреннее устройство SongFrame и не обязан разбираться в терминах разработчика. От пользователя нужны решения о его намерении и предпочтениях, а вычислимые факты программа определяет сама.

- Наличие, пригодность и состояние ресурсов определяй автоматически в подходящий момент: при запуске, после изменения подключения или установки, перед требующей их операцией. Не добавляй ручные «Проверить», «Перепроверить», «Обновить» и другие промежуточные действия, если они лишь заставляют программу вычислить уже необходимое ей состояние. Длительная проверка показывает прогресс и сохраняет доступность независимых функций; неизменные данные не проверяются заново при каждом открытии страницы.
- Выбирай разумные значения по умолчанию. Не требуй пути, числа или режима, которые приложение может выбрать само. Необязательный перенос хранения на другой диск и редкое изменение подключения раскрываются отдельно, а не выглядят обязательным началом работы. Автоматическое определение состояния не разрешает скачивание, производство или платную отправку без предусмотренного согласования.
- Показывай сведения и действия по текущему состоянию. Готовому компоненту не нужны размеры предполагаемого скачивания и выключенная кнопка установки; отсутствующему — выдуманный путь уже установленного файла. Не повторяй текстом значение зелёного статуса и не предлагай несколько кнопок для одного пользовательского намерения.
- Подпись и значок действия должны объяснять фактический результат. Называй объект прямо: какие компоненты сохраняются в папке и когда её стоит менять. В обычном сценарии не используй внутренние термины вроде «пакеты», если человеку достаточно знать, что скачиваются инструменты или модели. Не называй действие именем поля настройки вроде «Забыть путь»; объясняй полезный результат для пользователя. Одинаковое намерение, например выбор уже имеющегося компонента, получает один вход: тип выбранных данных и необходимую обработку определяет программа.
- Используй одинаковые понятные названия в карточках, подсказках и инструкциях; не вводи сокращение, которого пользователь не видит на экране. Скрывай PATH, внутренние источники, хеши ревизий и служебные пути из обычного сценария, если они не помогают принять решение. Подсказки и выбор файлов должны соответствовать текущей ОС, а не заставлять пользователя выбирать из инструкций для других платформ.
- Отличай ожидаемый объём скачивания от фактически полученных байтов. Не выдавай размер закреплённого файла за гарантию будущего ответа сервера; интерфейс и проверка загрузки должны согласованно обрабатывать неизвестный размер и несовпадение содержимого.
- Ошибка называет недоступный инструмент или операцию, объясняет причину и предлагает подходящее действие. Технические подробности раскрываются по желанию; одинаковое сообщение не дублируется в странице и уведомлении. Проверку целостности поставки не выдавай за требование к работе внешнего инструмента.

При проверке интерфейса пройди обычный сценарий без знаний автора: уже установленные ресурсы получают готовность без ручных команд, после выбора или скачивания состояние обновляется само, а отсутствие зависимости объясняется без требования скачать заново уже имеющиеся данные. Если действие пользователя можно убрать без потери его выбора и контроля, убери его.

## Проверка решения

- Сопоставь с `layout.md` **все относящиеся к изменению** действия страницы, блоков, строк и диалогов, включая условные, недоступные и появляющиеся после операции. Проверь их расположение, приоритет, названия, значки, доступные имена и подсказки, подтверждения и последствия. Учитывай правила агентных кнопок и платных операций из `AGENTS.md` и документации процесса.
- Если есть общие действия страницы, проверь закреплённую панель в её контексте прокрутки: доступность от начала до конца страницы, перекрытия шапкой или содержимым, перенос кнопок и порядок слоёв. Используй общие компоненты по их назначению и сверяй структуру и границы Go/Wails с `structure.md`.
- Проверь светлую и тёмную темы, подписи, читаемость, контраст, видимый фокус и работу с клавиатуры. Проверь пустое состояние, загрузку, ошибку, причины недоступности и сохранение доступных действий при смене состояния, когда они относятся к изменению.
- Проверь минимальное и стартовое окно **1320×860** в обеих темах и, для сложной компоновки, более широкое рабочее окно. Меньшие размеры 960×640 и 1280×720 не входят в обязательную приёмку. Оцени доступную ширину рабочей области с учётом навигации, длинные пути и названия, перенос, обрезание и локальную прокрутку. Мобильную ширину не вводи как обязательное требование.

## Истории компонентов

При каждом изменении фронтенда или используемого им API применяй раздел «Актуальность при изменении фронтенда» в `docs/ui/storybook.md`. До реализации найди истории компонента, родительской страницы и их локальные модели API. Обнови весь затронутый контур в том же изменении; история нового блока не заменяет его рабочий сценарий в истории целой страницы. Новые экраны без прежнего покрытия тоже получают истории. Не прячь новую функцию общей заглушкой недоступности; если историям правка не нужна, обоснуй это конкретно.

Используй типизированные локальные модели `frontend/src/renderer/testing/` и явные API props/чистый provider; не запускай настоящий Wails binding, профиль, агент или сервис. Проверяй наблюдаемый итог изменённых переходов в `play`, критичные истории помечай `tags: ['ci']`. Обход `frontend/tests/storybook/stories.spec.ts` по умолчанию открывает все истории витрины, `STORYBOOK_TEST_CI=1` — только истории с меткой `ci`; новая история попадает в обход сама. Проверяй повторное открытие, смену темы, unsubscribe/таймеры и очистку состояния.

После `wails3 task storybook` выполняй затронутые браузерные сценарии на статической витрине через HTTP (`wails3 task check:storybook` либо `yarn test:storybook --grep "<группа>"` из `frontend/`). Dev-сервер/HMR не входят в приёмку. Укажи обновлённые истории, модели API и фактический браузерный результат либо ограничения; статическая сборка не доказывает прохождение взаимодействий, витрина дополняет нативную Wails-проверку.

## Проверки

Актуальные команды принадлежат корневому `Taskfile.yml` и `frontend/package.json`. Из корня: `wails3 task check:frontend` (типы/Vitest), `wails3 task check:format` (Go/frontend), `wails3 task check:ui` (сборка Storybook и Playwright). Из `frontend/` доступны адресные `yarn typecheck`, `yarn test`, `yarn format:check`, `yarn build-storybook`, `yarn test:storybook`.

Связь с Go — только контракт `window.api` поверх сгенерированных bindings; не создавай отдельные мосты и ручные валидаторы ответов Go. Если изменён используемый UI Go API, проверь обработчики `internal/app/`, доменные пакеты и тонкий адаптер `frontend/src/platform/`, затем выполни `wails3 task bindings`, соответствующие Go-тесты и проверки контракта (`wails3 task check:contracts` при изменении общих fixtures). Generated файлы `frontend/bindings/` вручную не правь; файловая система/процессы принадлежат Go, renderer использует Wails-сервисы через adapters.

Для видимых изменений проверь относящиеся сценарии в нативном приложении, если окружение позволяет. Браузерная витрина не подтверждает системные диалоги, drag-and-drop, WebKit-кодеки или работу установленного AppImage. В результате перечисли проверки и существенные ограничения. Сборка установщиков и публикация из UI-задачи не следуют; для отдельной Go-сборки используй `songframe-go-build`.
