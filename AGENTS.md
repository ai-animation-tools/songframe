# Правила комплекса SongFrame

Комплекс для производства музыкальных клипов с помощью ИИ-агента: инструменты, скиллы, шаблон проекта и настольное приложение. Данные каждого клипа живут в отдельной папке проекта, созданной из [шаблона](templates/project/README.md); здесь хранится только код, документация и тестовые данные.

## Параллельная работа

- Независимые задачи в непересекающихся областях проекта выполнять параллельно субагентами. Каждому давать конкретную подзадачу, границы файлов, критерии приёмки, минимальные обязательные правила и только релевантный контекст.
- Если достаточно отдельного задания, запускать субагента без наследования всего чата. Не поручать ему читать весь репозиторий: передавать нужные файлы и сведения, разрешая точечное чтение зависимостей по необходимости.
- У общего изменяемого файла должен быть один владелец; зависимые шаги выполнять последовательно. Основной агент распределяет работу, интегрирует результаты и проверяет итоговое изменение.

## Текущий проект

- Инструменты и скиллы работают с одной папкой проекта. Она определяется в таком порядке: аргумент `--project <папка>` в командной строке, переменная окружения `SONGFRAME_PROJECT`, файл `current-project.json` в постоянном каталоге состояния (его пишет приложение или [current_project](tools/current_project/README.md)), текущая папка, если в ней есть `plan/project.json`. Инструмент без проекта завершается с кодом 2.
- Пути `plan/...`, `assets/...`, `source/...` в командах и документации отсчитываются от папки проекта, а не от этого репозитория. В репозиторий комплекса данные клипов не записывать; состояние приложения и CLI хранится в userData либо SONGFRAME_LOCAL_DIR, не рядом с кодом.
- Перед работой над клипом прочитать `AGENTS.md` и `README.md` в папке проекта: они задают владельцев сведений, защищённые исходники и порядок генерации. Правила проекта имеют приоритет над привычками из других проектов.
- Эталонный проект служит образцом структуры и доступен только для чтения. Его расположение задаётся рабочим окружением; не вшивать путь эталона в инструкции и инструменты.

## Работа в репозитории

- Документацию, комментарии и сообщения коммитов писать по-русски; имена файлов, API и технические термины сохранять как есть. Комментарии кратко объясняют назначение решения.
- Не делать commit, push и публикацию без явного поручения. Платные запросы к сервисам генерации возможны только по правилам соответствующего скилла и с согласия пользователя.
- Приложение используют только два человека на своих компьютерах: владелец на Linux и его друг на Windows. Это локальное приложение, а не многопользовательский сервис. Не добавлять авторизацию, защиту от внешнего/параллельного доступа, обязательную сетевую изоляцию, дополнительные режимы безопасности и проверки «на всякий случай» без конкретной необходимости. Предпочитать простое решение; валидация данных, сохранность исходников и платных оригиналов, согласование платной отправки и защита от её случайного повтора остаются обязательными.
- Пути должны переживать перенос приложения/проекта и переустановку ОС: не вшивать абсолютные пути текущей машины, имя пользователя, checkout сборщика или временную папку AppImage. Ресурсы находить относительно приложения/комплекса, данные — относительно выбранного проекта, локальное состояние — в подходящем каталоге ОС. Абсолютные пути допустимо вычислять во время запуска и получать из пользовательского выбора; сохранённый путь может устареть, тогда достаточно понятной ошибки и повторного выбора.
- Нативные Windows-прогоны в VM выполнять только по явному поручению. CI и Release собирают Linux AppImage и Windows ZIP на Linux; проверка ZIP не исполняет Windows-код. Полную поддержку Windows не выводить из проверки отдельных сценариев или факта сборки ZIP. Запуск внешних Claude/Codex через менеджер заданий приложения поддерживается только на Linux; проектные launcher и встроенный Kling работают на обеих ОС.
- Разовые скрипты, отчёты и временные файлы хранить вне репозитория.

## Инструменты

Выбирать инструмент по [карте tools](tools/README.md) и читать README его папки; исходный код ради выяснения параметров не читать. Каждый инструмент лежит в `tools/<имя>/<имя>.py`, его тесты рядом как `test_*.py`, общие функции в `tools/common.py`. При добавлении или изменении инструмента обновлять README его папки и карту tools. Полный прогон тестов: `python3 -B tools/run_tests/run_tests.py`; он использует копию [проекта-образца](tools/testdata/README.md), настоящий проект не трогает. Стиль кода задаёт `pyproject.toml` (ruff), переформатирование существующего кода выполняется отдельным поручением.

## Приложение

Перед изменением интерфейса изучить и применять [правила UI](docs/ui/README.md): тему, структуру и компоновку страниц и элементов управления.

Страницы renderer лежат в `src/renderer/src/pages/{PageName}/{PageName}.tsx` и экспортируются через `pages/{PageName}/index.ts` и `pages/index.ts`. Страница собирается из самостоятельных компонентов в `pages/{PageName}/components/{ComponentName}.tsx` с локальным `components/index.ts`; один компонент — один файл. Публичный index.ts страницы экспортирует только саму страницу; внутренний barrel компонентов — только блоки, нужные снаружи их папки. Компоненты, используемые разными страницами, принадлежат общему `src/renderer/src/components`. Связанные только с одной страницей hooks, типы и функции остаются в её папке; не переносить монолит страницы целиком в одну новую обёртку.

Исходники приложения лежат в `src`: `main` (главный процесс, вся работа с файлами и процессами), `preload` (мост `window.api`), `renderer` (React + MUI), `shared` (типы и контракт API). Рендерер не обращается к файловой системе напрямую: любая новая возможность добавляется как функция главного процесса, канал IPC и метод в `src/shared/api.ts`. Логика главного процесса, не зависящая от Electron, проверяется тестами `src/main/*.test.ts` (`yarn test`); перед коммитом `yarn typecheck`. Страницы просмотра и редактирования не должны требовать Python и ffmpeg: они нужны только производству. Сборка идёт в `build/`, установщики в `build/release`; обе папки вне Git. Команды: `yarn dev`, `yarn build`, `yarn dist:linux`, `yarn dist:win`. AppImage после сборки оставлять в штатной `build/release`; не копировать бинарник за пределы репозитория без явного поручения.

Python запускается через общий `PythonLauncher`: в packaged только из `process.resourcesPath/runtime`, в dev допустим системный Python. Новые вызовы не должны самостоятельно искать Python или создавать второй spawn. Рецепт поставки и проверки — [scripts/runtime](scripts/runtime/README.md); `dist:*` собирает обе поставки на Linux; `dist:win` готовит Windows Python из закреплённых wheels и выпускает ZIP. Windows используется только для запуска готового приложения и проверки в VM, Node.js/Yarn/Python там не устанавливаются. Обе поставки включают FFmpeg/ffprobe через `yarn prepare:media` (`--target=win32-x64` для Windows); версии/хеши — `scripts/runtime/media-lock.json`. Веса faster-whisper устанавливаются отдельно в каталог данных пользователя или выбранную папку, в AppImage не входят. Окно разметки рекомендует модель по CPU/RAM и доступной NVIDIA CUDA, содержит кнопку фоновой загрузки и допускает ручной выбор; GPU не обязателен. Перед упаковкой проверяются ресурсы, в пользовательских действиях большие веса повторно не хешировать. Настройки settings.json, история, текущий проект и журналы используют одну постоянную папку состояния. В проектах управляемый launcher `.songframe/run-tool` на Linux либо `.songframe/run-tool.cmd` на Windows вызывает постоянный файл приложения в режиме `--songframe-tool`, документация и схемы копируются в служебную папку; после переноса приложение обновляет её при открытии проекта. Менять управляемые памятки AGENTS.md/README.md и известные ссылки схем VS Code; пользовательские правила и настройки сохранять. Git необязателен для рабочих представлений; индекс и история требуют Git. Официальный Kling CLI включён в resources/kling и работает на Node из Electron; отдельная установка Node/npm не нужна. Python получает SONGFRAME_KLING_EXECUTABLE/SONGFRAME_KLING_SCRIPT; ELECTRON_RUN_AS_NODE включается только для дочернего CLI. Авторизацию и её обычный файл обслуживает сам Kling CLI, нового хранилища токенов приложение не создаёт. Авторазметка не требует `unshare`; сохранять локальную загрузку модели и офлайн-настройки без новой подсистемы изоляции.

Кнопки, запускающие Claude/Codex или открывающие интерфейс взаимодействия с агентом, обозначать присланными SVG через общий `AgentButton` (`src/renderer/src/components/AgentButton.tsx`). Он использует сохранённого провайдера; для уже выполняющегося задания передавать его provider явно. Если действие адресовано внешнему агенту с неизвестным провайдером, передавать `provider={null}`: показываются оба знака. Условные действия согласования могут использовать `AgentIcon` как startIcon только при исполнителе agent. Кнопки отмены диалога, сохранения обычных файлов, локальных инструментов и прямых операций Kling не обозначать логотипами Claude/Codex.

## Скиллы

Скиллы лежат в [skills](skills/README.md) и описывают порядок работы агента; они вызывают инструменты комплекса с текущим проектом и не повторяют их контракты. Папки `.agents/skills` (Codex) и `.claude/skills` (Claude Code) содержат только символические ссылки на `skills/`; новый скилл добавляется папкой в `skills/` и двумя ссылками. Backend опор выбирается независимо в `generation.image`: Codex с `image_gen` и проектной моделью агента `generation.image.model` (путь CLI — из глобального `imageAgent`, пустая проектная модель — из конфигурации CLI) либо Kling image через адаптер; видео использует `generation.video` (Kling), текстовые этапы — глобально выбранный Claude Code или Codex. Наличие Codex CLI не подтверждает доступность его image tool. Скачанный image original выбирается как непринятый кандидат; опоры утверждаются отдельно. Согласования производства идут через приложение: агент пишет вопрос в `workflow.json` пакета (`shot_workflow ask`) и ждёт ответ (`wait`), пользователь отвечает кнопками на странице «Производство»; платная отправка — после ответа `send` по показанному SHA и цене либо по конкретному явному поручению `regenerate=true` на одну новую попытку показанного сохранённого запроса; такое поручение не разрешает следующие retries.

## Шаблон проекта

[templates/project](templates/project/README.md) копируется приложением при создании клипа. Изменение контрактов хранения (манифесты, пакеты, очередь, сборка) вносится в шаблон и в инструменты одновременно; существующие проекты обновляются по поручению.
