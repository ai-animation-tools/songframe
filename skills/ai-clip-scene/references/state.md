# Кастинг, сохраняющееся состояние и запись корректировок

Читать на этапе описания, перед каждой опорой и при любой корректировке постановки. Состояние складывается из трёх источников, у каждого свой владелец:

| Источник | Владелец | Что хранит |
| --- | --- | --- |
| `plan/cast.json` | Кастинг ([cast_registry](../../../tools/cast_registry/README.md)) | Сущности с кодами (`id`), их тип `kind`, имя, роль, внешность `appearance`, изображения в `source`, начальное состояние `initial_state`, словарь свойств `properties` по типам |
| `plan/scenes.json` | Реестр сцен | `state_from` и `state_changes` каждого плана: только изменения по сюжету, не повтор начального состояния |
| Вычисление | `scene_registry`, `continuity_brief` | `before`/`after` плана с наследованием по цепочке `state_from`, врезка словами и чек-лист по шаблонам словаря |

Отдельный редактируемый реестр состояния не ведётся. Код сущности из кастинга является ключом и в `references` плана, и в `state_changes`; типы сущностей открыты: персонажи, транспорт, локации, предметы, мир (`world`), животные и любые другие.

## Что читать на этапе 1

1. `python3 -B tools/scene_registry/scene_registry.py Mxx`: `before`, `after`, `scene_sha256`, постановка плана и его `references`.
2. `python3 -B tools/continuity_brief/continuity_brief.py Mxx`: заголовок с действием, строки «Сущность: свойство: значение» (мир первым, затем порядок кастинга) и раздел «Проверить по кадру» с вопросами. `--phase after` даёт состояние на последний кадр. `--paragraph` печатает один абзац для дословной вставки в промпт.
3. Для каждой сущности из `references` плана: `appearance` и изображения из кастинга (пути внутри `source/<папка типа>/...`). Сущность без изображения называется в карточке: её нужно нарисовать или загрузить до генерации, выдумывать внешность нельзя.
4. Словарь свойств: `python3 -B tools/cast_registry/cast_registry.py vocab`, когда нужно понять подпись или допустимые значения свойства; для типа без словаря действует общий набор `generic`.

## Врезка и чек-лист

- Врезка `--paragraph` вставляется дословно в промпт каждой опоры (для последней опоры фаза `after`) и в видеопромпт; её не пересказывают своими словами и не сокращают, кроме удаления сущностей, которые весь план остаются за кадром (см. [prompt-template.md](prompt-template.md)). Рядом с врезкой внешность героев описывается признаками из `appearance`, а не именами: внешнему сервису имена ничего не говорят.
- После получения каждой опоры и после получения видео пройди чек-лист из `continuity_brief Mxx` (для последней опоры и последнего кадра видео с `--phase after`): ответь на каждый вопрос по кадру и назови несоответствия в карточке. Это сверка с записанным состоянием, а не художественная оценка; несоответствие исправляется перегенерацией названной опоры либо, если неверна запись, правкой у владельца сведений.
- Пустой чек-лист означает, что у типа сущности нет шаблонов `checklist`: проверь хотя бы положение, контакт и состояние по строкам врезки.

## Что учитывать до каждой опоры

- Последствия прежних событий: загрязнение и влажность, повреждения одежды и внешности, усталость и развитие эмоций, состояние транспорта, положение и принадлежность предметов. Они действуют до предусмотренного сценарием изменения.
- Отсутствие героя в нескольких планах, смена ракурса, склейка или чистый референс из `source` не возвращают его в исходное состояние. Мытьё, переодевание и восстановление предмета не выдумывать.
- Для первого кадра используй `before`; изменения текущего плана происходят во время действия и дают `after`, а не появляются заранее.
- Вычисление учитывает всю цепочку сюжетных событий, не только соседний Mxx. Флешфорвард, возврат во времени и параллельные действия сопоставляй по сюжету: сцены со `state_from: null` стартуют с `initial_state` кастинга, а не с состояния соседнего по шкале плана.
- На склейке сверяй положения с фактическим первым кадром принятого клипа соседа: пропущенное перемещение уже входит в `before`. Устойчивое последствие отличай от временного положения предмета и разового жеста; принадлежность предмета (`owner`) не доказывает его положение.
- Для точного вида пятен и реквизита используй сохранённые изображения и при необходимости отдельный кадр `accepted_edit.video` нужного момента. Это адресная проверка, не повторный анализ всех видео; конец принятого участка не подменяй концом полного оригинала.
- При конфликте выбранного изображения с действующей постановкой обозначь расхождение до генерации; прежние assets, кастинг и сценарий молча не исправляй. Неизвестную деталь не объявляй установленной.

## Где записывать корректировки

Записывай действующую постановку без рассказа о том, кто и когда её изменил:

| Что изменилось | Куда записать |
| --- | --- |
| Внешность героя, его роль, начальное состояние, изображения | `plan/cast.json` (`appearance`, `role`, `initial_state`, `images`); после правки изображений `cast_registry sync` обновляет `references` реестра |
| Действие, камера, сторона объекта, взгляд, непрерывность, набор референсов, окно Mxx | Поля плана в `plan/scenes.json` |
| Сохраняющиеся последствия и их сюжетный источник | `state_changes` и `state_from` того плана, где событие происходит, только по словарю свойств; не копировать во все последующие |
| Новое свойство состояния для типа сущности | `properties` кастинга (ключ, подпись, подсказка, при необходимости шаблон `checklist`) |
| Правило всей последовательности | `direction` последовательности |
| Общие визуальные ограничения | `visual_direction` реестра |
| Общий сюжет | Файл идеи клипа из `source/manifest.json` только по прямому поручению; локальная смена ракурса его не меняет |
| Точный текст генерации и параметры | Текущий пакет; после принятия комплект assets |

После правки реестра или кастинга выполни `python3 -B tools/cast_registry/cast_registry.py check`, `python3 -B tools/lint_registry/lint_registry.py` и `python3 -B tools/update_scene_views/update_scene_views.py`. Конфликт с соседними планами уточняй у пользователя, не переписывай соседей произвольно. Повторный показ того же события оформляй ссылкой `{"scene": "Mxx", "phase": "same"}` по контракту [scene_registry](../../../tools/scene_registry/README.md), не дублируя изменения. Перед продолжением отложенного пакета `shot_workflow check` сверяет `scene_sha256`: изменение более раннего события или начального состояния затрагивает текущий план и возвращает затронутые материалы на согласование.

После изменения постановки принятие изменённого изображения или промпта недействительно; неизменённые совместимые входы повторного принятия не требуют. Старый замороженный запрос по новому описанию не отправлять, в том числе через `regenerate=true`: если постановка изменилась, идти по этапам.
