# Встроенный Python

Приложение поставляет один переносимый CPython для всех инструментов, включая вложенные вызовы через `sys.executable`. В разработке допускается системный Python 3.11+, но packaged-приложение использует только собственный комплект. Привязки к имени пользователя и checkout сборщика нет.

## Подготовка

Из корня репозитория на **Linux x64**: здесь собираются обе поставки:

```sh
yarn prepare:runtime
yarn prepare:media  # Linux FFmpeg/ffprobe, без модели
yarn prepare:runtime --target=win32-x64
yarn prepare:media --target=win32-x64  # Windows FFmpeg/ffprobe, тоже на Linux
yarn smoke:runtime
yarn typecheck
yarn test
yarn dist:linux     # На Linux
yarn dist:win       # Windows ZIP, тоже на Linux
```

Сборщику на Linux нужны Node.js/Yarn, сеть для первого получения ресурсов, `tar` и `zstd`. Системный Python и локальный venv для подготовки не нужны. `dist:*` сам вызывает подготовку нужного runtime. Wine не требуется: для Windows используются готовые CPython/wheels и Electron EXE. Иконку и метаданные PE встраивает штатный `resedit` из electron-builder прямо на Linux, без исполнения Windows-кода; цифровая подпись отключена. На Windows запускается только готовое приложение, без Node.js/Yarn/Python/pip.

`prepare-runtime.mjs` получает архив из [python-build-standalone](https://github.com/astral-sh/python-build-standalone/releases/tag/20261021), проверяет SHA256, распаковывает его в staging и устанавливает только зафиксированные wheels собственным `python -m pip`. Первый этап скачивает wheels, второй устанавливает их без индекса; версии и хеши заданы в `requirements-<platform>-<arch>.lock`. Для Linux проверка `pip check` и `runtime-probe.py` обязательна до появления готового manifest. Windows-комплект собирается на Linux из готовых `win_amd64` wheels: закреплённый PyPA installer размещает их по Windows-схеме (`Lib/site-packages`, `Scripts`, DLL рядом с Python), Windows-маркеры зависимостей проверяются отдельно. `installer` нужен только сборщику, он не входит в приложение. В manifest различаются сборочный host и факт нативной проверки; сборка на Linux не выдаётся за успешное исполнение Windows-библиотек.

При загрузке архивов CPython, FFmpeg и лицензий интерактивный терминал показывает число полученных байтов и, при известном размере, процент. Сообщения выводятся не чаще одного раза в 10 секунд, включая ожидание данных; после 120 секунд без данных загрузка завершается ошибкой. В неинтерактивном режиме периодический прогресс не выводится. Проверенный SHA256 архив атомарно помещается в кэш; при ошибке временный файл удаляется, прежний кэш сохраняется. Локальная проверка загрузчика без внешней сети: `node --test scripts/runtime/download.test.mjs`.

Архивы и wheels остаются в `build/runtime/downloads`. Готовый комплект лежит в `build/runtime/linux-x64/` или `build/runtime/win32-x64/`:

```text
python/              Интерпретатор, стандартная библиотека, site-packages, DLL/.so
licenses/            Лицензии wheels и их библиотек, packages.json
manifest.json        Версия Python, платформа, источник и хеши рецепта поставки
requirements.lock    Копия установленного набора
```

Linux использует `python/bin/python3`, Windows — `python/python.exe`. Лицензия Python сохраняется внутри его исходного комплекта (`lib/python3.12/LICENSE.txt` или `LICENSE.txt`). Готовые бинарники и кэш не входят в Git. При изменении рецепта удалить соответствующий `manifest.json` и повторить подготовку; при изменении lock-файлов комплект пересобирается автоматически.

## Состав и границы

- CPython **3.12.15**, выпуск python-build-standalone **20261021**, базовый x86-64/glibc на Linux и shared/MSVC на Windows. URL/хеши — в `runtime-lock.json`.
- faster-whisper **1.2.1**, CTranslate2 **4.8.3**, Pillow **13.0.0**, NumPy **2.5.4**, ONNX Runtime **1.31.0**, PyAV **19.0.2**, tokenizers **0.23.3**; всё транзитивное дерево закреплено отдельно для каждой ОС.
- Windows дополнительно включает `colorama` и `msvc-runtime`: DLL Visual C++ устанавливаются рядом с Python, ручная установка Redistributable не требуется. Сохраняется лицензия поставляемых DLL.
- По тегам выбранных wheels Linux требует **glibc 2.28+**. Граница CPU определяется всем комплектом, не только CPython: для готового CTranslate2 заявлен минимум SSE 4.1. Древние CPU и все дистрибутивы Linux не объявляются поддерживаемыми без испытаний. [Требования CTranslate2](https://opennmt.net/CTranslate2/hardware_support.html).
- GPU/CUDA не обязательны: без подходящей NVIDIA и библиотек используется CPU/int8; при готовой CUDA доступен автоматический выбор GPU. Лицензии и библиотеки, уже включённые поставщиками wheels, сохраняются.
- Шрифт карточек аниматика DejaVu Sans входит в инструменты (`tools/render_animatic_cards/fonts/`) вместе с лицензией и попадает в обе поставки; системный шрифт не нужен.
- **Linux AppImage и Windows ZIP включают FFmpeg/ffprobe** в `runtime/bin/` (в Windows — `ffmpeg.exe` и `ffprobe.exe`). Веса модели устанавливаются отдельно по [инструкции](../../README.md#модель-распознавания); старый каталог `models` исключён из упаковки. Локальная обработка не требует внешних Python/FFmpeg/Node; клиенты платных провайдеров генерации входят в Python-инструменты поставки; Git необязателен для рабочих представлений, но нужен для индекса и истории.
- Рецепт Windows ZIP рассчитан на сборку в Linux. Проверка Python 3.12.15, нативных импортов, вложенного интерпретатора, check_workspace и Jobs в Windows VM пройдена; также проверены FFmpeg/ffprobe, короткий медиапрогон, вход в провайдера генерации (прежним официальным CLI; собственный клиент провайдера в VM не проверялся), скачивание модели и распознавание. Полный производственный цикл не подтверждён этими проверками. Single-file portable exe не используется: большой комплект хранится обычной папкой рядом с EXE.

## Запуск из приложения

`src/main/python-runtime.ts` определяет интерпретатор, `python-launcher.ts` запускает инструменты. В packaged-режиме корень — `process.resourcesPath`; Python лежит в `runtime/python/`, инструменты — в `tools/`. Ресурсы доставляются `extraResources`, вне ASAR. Отсутствующий или неподходящий комплект даёт ошибку поставки, без подмены Python из PATH. Хеши больших файлов при пользовательских действиях не пересчитываются.

В dev сначала проверяется `build/runtime/<platform>-<arch>`, а при его отсутствии — Python из PATH. Windows `py -3` используется только для обнаружения настоящего `sys.executable`. Повреждённый подготовленный комплект не маскируется системным Python. Отрицательный результат не кэшируется: повторная проверка видит исправление.

`runTool` и Jobs используют один launcher, абсолютные **вычисленные** пути к скриптам и проекту, `shell: false`, UTF-8 и отключённый user site. `-X utf8` и `PYTHONUTF8=1` задают UTF-8 также для чтения файлов, что важно для русского JSON на Windows. Чужие `PYTHONHOME/PYTHONPATH/venv` не подменяют библиотеки. Шаг Jobs с `required: false` только сопутствующий, а `stop: false` позволяет продолжить следующие шаги после ошибки обязательного; журнал каждого задания ведёт Jobs. Короткий вызов ограничен 10 минутами, разметка — 30 минутами, шаг Jobs по умолчанию — двумя часами; `Step.timeoutMs` задаёт другой лимит. Таймаут завершает дерево процессов, включая вложенное распознавание.

Состояние dev и packaged-приложения находится в постоянном userData, на Linux — `${XDG_CONFIG_HOME:-$HOME/.config}/songframe`. SONGFRAME_LOCAL_DIR переопределяет settings.json, историю, текущий проект и журналы вместе. Python получает тот же SONGFRAME_LOCAL_DIR и явно выбранный проект. Подробнее — [перенос и состояние](../../docs/development.md#перенос-приложения-состояние-и-проекты).

Распознавание из `align_lyrics` запускается напрямую, без обязательного `unshare`: на Linux наличие этой команды не означает разрешение user namespaces. Сохраняются локальная загрузка модели и офлайн-настройки, настройки AppArmor/sysctl не меняются. См. [align_lyrics](../../tools/align_lyrics/README.md) и [transcribe_local](../../tools/transcribe_local/README.md).

## Проверки

`yarn smoke:runtime` копирует комплект в временную папку с кириллицей и пробелами, убирает Python из PATH дочернего процесса, проверяет нативные импорты, создание PNG, CPU-типы CTranslate2, вложенный интерпретатор и `check_workspace` на копии образца. Git и модель для этого не нужны; пользовательские проекты не открываются.

Для **настоящего упакованного приложения** предусмотрена переменная `SONGFRAME_RUNTIME_SMOKE`: путь JSON-отчёта. Приложение не открывает окно, создаёт временную фикстуру, выполняет импорты, вложенный Python, `check_workspace` через launcher и Jobs, сохраняет отчёт и завершается с кодом 0/1. Пример Linux после упаковки:

```sh
SONGFRAME_RUNTIME_SMOKE=/tmp/songframe-runtime-result.json SONGFRAME_LOCAL_DIR=/tmp/songframe-runtime-state build/release/songframe-<версия>-linux-x86_64.AppImage
```

AppImage проверяется таким же образом. Нужна доступная графическая сессия для Electron (в CI — Xvfb), хотя окно не создаётся. В packaged smoke PATH Python-процессов содержит только `runtime/bin`, без системных команд; самостоятельный Python smoke использует пустой PATH.

CI запускает полные наборы тестов приложения и Python, но поставки не собирает: их проверяют локально, а для публикации обе собирает Release на Linux. Общий шаг `.github/actions/linux-appimage` выполняет проверку переносимого Python и Docker smoke конечного AppImage; `.github/actions/windows-zip` собирает ZIP и запускает `scripts/runtime/check-windows-zip.py`. Скрипт проверяет CRC, состав ресурсов и целевую платформу ZIP, формирует SHA256 и `windows-archive-check.json`, но не исполняет Windows-код. Обе поставки и отчёты Release передаёт задаче публикации артефактами. Успех архивной проверки не подтверждает работу Windows FFmpeg или полного приложения: это проверяется отдельно нативно.

Ручной Release использует те же общие шаги и один SHA выбранного ref. Запуск: **Actions → Release → Run workflow**, обязательные `version` (`X.Y.Z` без `v`, например `0.2.0`) и `description`. До сборок проверяется, что тег/релиз `vX.Y.Z` не занят; `package.json` получает версию только внутри сборочных checkout, без автоматического коммита. После успеха обеих сборок отдельная задача создаёт тег на исходный SHA, черновик релиза, загружает обе поставки, SHA256, отчёты и лицензии, затем публикует его. Существующие теги/релизы не перезаписываются; ошибка сборки не создаёт публичный релиз, ошибка загрузки оставляет черновик. Подробнее — [CI и релизы](../../docs/development.md#ci-и-релизы).

### Проверка в Windows VM

Готовый ZIP из релиза или локальной сборки проверяется в Windows VM только по явному поручению. Сборочная проверка архива на Linux не заменяет этот нативный прогон.

Перенесите **готовый Windows ZIP**, распакуйте целиком в обычную папку и откройте `SongFrame.exe`. Node.js, Yarn, Python и pip устанавливать не нужно. Для проверки встроенного Python откройте `check-runtime.cmd` двойным щелчком; он использует только приложение и его ресурсы.

Отчёты `result.json` и `check.log` сохраняются рядом с EXE и `check-runtime.cmd`. CMD содержит только ASCII-команды с CRLF, без переключения кодировки; формат проверяется перед упаковкой. Он сначала переходит в папку приложения (включая UNC/shared folder через pushd), создаёт оба файла, затем запускает EXE. Начальный `stage: launcher` не является успешной проверкой: приложение заменяет его настоящим результатом. Если запуск не удался, отправьте оба файла и текст ошибки Windows. Можно перенести всю папку в каталог с кириллицей/пробелами и повторить запуск. Не переносите один EXE без ресурсов.

Для отдельной подготовки из Linux: `yarn prepare:runtime --target=win32-x64`. Выпуск ZIP: `yarn dist:win`. Во время сборки не исполняется Windows-код; нативные проверки выполняются отдельно, по явному поручению. Нативная проверка Python сама по себе не подтверждает распознавание с моделью и полный медиапрогон. После обновления ZIP запускайте check-runtime.cmd повторно: отчёт должен содержать проверку встроенных FFmpeg/ffprobe и короткого кодирования/чтения тестового файла.

## Проект и инструменты

Инструменты запускает только само приложение через общий PythonLauncher; отдельного режима командной строки и служебных файлов в папке проекта нет. Открытие проекта ничего в нём не записывает, поэтому перенос приложения или проекта не требует обновления путей. Тесты переноса выполняются без окна.

## Медиапоставка Linux и Windows

`yarn dist:linux` последовательно готовит Python, FFmpeg, код и AppImage, а `yarn dist:win` — Windows Python, FFmpeg и ZIP. Подготовка обеих поставок выполняется на Linux x64; `yarn prepare:media` по умолчанию готовит Linux, а `--target=win32-x64` выбирает Windows. Версии, URL и SHA256 закреплены в `media-lock.json`: FFmpeg BtbN `n8.1.3-9-g29e619e767`, сохранённый месячный выпуск `autobuild-2026-09-30-13-08`, GPL-сборка с libx264. Модель не скачивается и не включается в AppImage: фильтр упаковки исключает каталог `models` runtime, даже если в `build/runtime/linux-x64/models` остались веса старой раскладки checkout; их не удаляют, папку можно выбрать вручную в приложении.

[Источник FFmpeg](https://github.com/BtbN/FFmpeg-Builds/releases/tag/autobuild-2026-09-30-13-08). Архив и бинарники проверяются по SHA256. Windows использует статический GPL ZIP того же выпуска, указанный в `ffmpeg.windows`; его SHA256 сверен с официальным checksums.sha256 и digest GitHub release asset. ZIP распаковывает уже подготовленный Linux Python, Wine не требуется. GPL-текст и документация сборки сохраняются в `runtime/licenses/ffmpeg`. Linux дополнительно сохраняет вывод `-version` с configure; для Windows встроенные флаги configure извлекаются из PE в `ffmpeg-build.txt` и `ffprobe-build.txt`, без исполнения EXE. Windows media-manifest.json явно содержит `buildHost: linux-x64` и `nativeProbe: false`; это граница сборочной проверки, а результат запуска записывается отдельным отчётом в VM. Медиакомплект имеет отдельный `media-manifest.json`; `before-pack.cjs` повторно проверяет бинарники и хеши. Linux-бинарникам выставляется execute-bit. Целевые требования выбранной сборки FFmpeg: glibc 2.28+, Linux 4.18+; работа на остальных системах требует отдельных испытаний. На пользовательском компьютере пересчёта больших хешей нет.

Launcher вычисляет `runtime/bin` относительно `resourcesPath` и добавляет bin первым в PATH для обеих ОС. При отсутствующем bundled FFmpeg запуск инструмента завершается понятной ошибкой; системный бинарник не маскирует поломку. Каталог внешних моделей вычисляется от XDG_DATA_HOME (Linux) или LOCALAPPDATA (Windows). В окне автоматической разметки есть диагностика CPU/RAM/NVIDIA/CUDA, рекомендация, кнопка фоновой загрузки, ссылка «Файлы модели» и выбор своей папки. Кнопка фоновой загрузки запускает [download_whisper_model](../../tools/download_whisper_model/README.md) заданием приложения с Python и Hugging Face Hub из поставки. Установка системного Python, pip или hf не нужна. Прогресс виден в журнале задания; повторный запуск использует уже скачанные файлы. После успешной загрузки папка выбирается и сведения обновляются автоматически, без перезапуска; для модели, скопированной вручную, достаточно выбрать папку и нажать «Обновить сведения». Проверка наличия принимает vocabulary.txt и vocabulary.json. Распознавание сохраняет `local_files_only`, `HF_HUB_OFFLINE`, отключение телеметрии и прямой вызов без обязательного unshare. GPU определяется общим помощником `tools/transcribe_local/hardware.py`; CUDA 12/cuDNN 9 устанавливаются отдельно, иначе используется CPU. Рекомендации по памяти — приблизительные, свободную память и скорость моделью не измеряем.

Для настоящего ASR из готового приложения задайте `SONGFRAME_RUNTIME_SMOKE=/путь/result.json`, `SONGFRAME_MODEL_DIR=/путь/скачанной/модели` и **путь отдельной тестовой копии проекта** в `SONGFRAME_ASR_PROJECT`. Smoke использует встроенные Python/FFmpeg и внешнюю модель; PATH дочернего процесса содержит только runtime/bin, поэтому этот технический прогон идёт на CPU. Он записывает recognition.json рядом с отчётом и timing.json в указанную копию проекта. Не указывайте рабочий проект для технического прогона. Обычная проверка runtime не требует модели.

## Приёмка конечного Linux AppImage

`prepare-linux-licenses.mjs` дополняет install_only уведомлениями из полного CPython того же выпуска: архив, тексты FlatBuffers и tokenizers закреплены в linux-licenses-lock.json. Код/объектные файлы полного архива в приложение не копируются. `after-pack.cjs` проверяет ресурсы и execute-bit, исключение тестов/моделей, отсутствие checkout в коде и создаёт distribution.json/THIRD_PARTY_LICENSES.md. Перечень сохраняет реальные версии Python/JS-зависимостей и ссылки на полные тексты лицензий, включая Electron/Chromium, FFmpeg и шрифт карточек DejaVu Sans. Лицензии шрифтов берутся из папок `fonts/` инструментов (`tools/render_animatic_cards/fonts/`); шрифт без лицензии в той же папке останавливает упаковку.

`yarn smoke:appimage --docker --model=<внешняя папка> --output=<новая папка отчёта>` проверяет настоящий AppImage. Контейнер Ubuntu 22.04 запускает его без сети и системных Python/Node/Yarn/Git/FFmpeg. Внешняя модель монтируется только для чтения. Собственные исходники теста генерируются espeak-ng и встроенным FFmpeg, пользовательские клипы не открываются. Проверяются исходники и длительность, ASR, сохранение verified, scene_scaffold, карточки/представления, Jobs/журнал, перенос и перезапуск. Нативный вариант без Docker использует текущий DISPLAY и espeak-ng либо --audio=<WAV>; --extract включает extract-and-run при отсутствии FUSE.

Composite action `.github/actions/linux-appimage` используется Release. Публикация релиза разрешена после Linux smoke и успешной сборки/проверки Windows ZIP; журналы сохраняются и при ошибке. Контрольная сумма формируется только после успеха и повторного хеширования файла, временный перенос выполняется в пределах штатной build/release с восстановлением исходного имени. CI-фикстура tiny скачивается отдельно через prepare:smoke-model и не входит в приложение. Флаги контейнера --no-sandbox/NO_CLEANUP не меняют поведение обычного запуска.

## Клиенты провайдеров генерации

Отдельных программ провайдеров и Node в поставке нет: клиент каждого платного провайдера — Python-модуль его адаптера в `tools/<id>_request/` на стандартной библиотеке, без дополнительных wheels. Он входит в `resources/tools` вместе с остальными инструментами. after-pack (`linux-package.cjs`) и проверка Windows ZIP (`check-windows-zip.py`) читают таблицу `ADAPTERS` в `tools/media_adapters.py` и требуют в поставке модуль каждого перечисленного адаптера; имя сервиса в проверки не вшито. Особенности конкретного клиента — в [docs/providers](../../docs/providers/README.md). Проверка поставки (`smokeChecks` адаптера) импортирует клиент без сети, убеждается, что токены хранятся в каталоге состояния, и вызывает `media_request auth-status` без сохранённого входа.

На странице «Среда» строка провайдера помечена «в поставке» и показывает состояние входа через `media_request auth-status`: без входа доступна кнопка «Войти», при действующем — «Сменить аккаунт», при ошибке проверки — «Проверить вход». Вход выполняется в браузере (`media_request login`); токены провайдер хранит в каталоге состояния приложения (`providers/<id>/`), атомарно и с правами 0600 там, где ОС их поддерживает. Файлы авторизации официальных программ не читаются и в поставку не копируются. Подробности — в [docs/providers](../../docs/providers/README.md).

## Кнопка загрузки модели

Окно разметки запускает download_whisper_model через существующие Jobs и PythonLauncher. Задание относится к приложению, не требует проекта и пишет только выбранную стандартную папку весов; текущая модель и каталог отражаются в modelDownload у JobInfo. Повторный вызов той же модели возвращает выполняющееся задание. Журнал хранится штатно в userData/jobs; после закрытия диалога UI восстанавливает наблюдение через jobs.list/get. После успеха папка выбирается и сведения обновляются автоматически. «Обновить сведения» остаётся ручной диагностикой CPU/CUDA и стандартных папок, не запускает скачивание.
