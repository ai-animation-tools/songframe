# Разработка SongFrame

Руководство по запуску из checkout, устройству приложения, сборке и выпуску поставок. Возможности продукта и пользовательские инструкции находятся в [README](../README.md), обязательные правила разработки — в [AGENTS.md](../AGENTS.md).

Менеджер агентских заданий, API, права и ограничения описаны в [агентских заданиях](agents.md), предложения и применение сценария — в [сценарном процессе](scenario-workflow.md), согласования и границы приёмки — в [производственном процессе](production-workflow.md), ручные пробы — в [монтаже](montage.md). Контракты Python-инструментов находятся в [карте tools](../tools/README.md) и README каждого инструмента. Рецепт подготовки встроенного Python, медиа и проверок поставки поддерживается в [scripts/runtime](../scripts/runtime/README.md).

## Состав

Страницы «Производство», «Сцены», «Проверки», «Аниматик» и «Монтаж пробы» открываются через общий `RequireScenario`. Пока нет доступных сцен, используется один полноширинный `ScenarioRequired` с одинаковым сообщением и действиями; дочерняя страница и её проверки среды ещё не запускаются. Готовность сценария определяет общий `readScenarioRegistry`, независимо от наличия инструментов генерации. Статусы Python и Kling вычисляются отдельно от наличия сцен.

```text
tools/              Инструменты на Python: запросы Kling, приёмка, проверки, сборка аниматика, пакет для монтажёра
tools/testdata/     Синтетический проект-образец «Пробный клип» с небольшими тестовыми медиа
skills/             Скиллы агента: ai-clip-audio, ai-clip-scenario, ai-clip-scene
templates/project/  Шаблон папки нового проекта: структура, README, AGENTS.md, .gitignore
src/main/           Главный процесс Electron: проекты, статус, исходники, среда, запуск инструментов
src/preload/        Мост window.api между рендерером и главным процессом
src/renderer/       Интерфейс: React + MUI, светлая и тёмная темы
src/shared/         Типы и контракт API, общие для обеих сторон
build/              Сборка приложения (build/app) и установщики (build/release); вне Git
```

Отдельно устанавливать их пользователю не нужно. Веса модели устанавливаются отдельно по [инструкции по модели распознавания](../README.md#модель-распознавания). Разработка без `yarn prepare:runtime` может использовать системный Python; внешний Kling нужен лишь самостоятельным вызовам из checkout без подготовленного встроенного CLI.

В корне checkout выполните `nvm install` и `nvm use`: обе команды читают `.nvmrc`, как CI и Release. Репозиторный `.gitignore` содержит исключение для этого файла, поэтому глобальное правило `.nvmrc` не мешает хранить общую версию в Git.

### Готовое приложение на Windows

Сборка выполняется на Linux командой `yarn dist:win`. Пользователь Windows получает готовый ZIP, распаковывает его целиком и запускает `SongFrame.exe`. Установка Node.js, Yarn, Python и pip не требуется. Для проверки встроенного runtime в ZIP есть `check-runtime.cmd`; инструкция лежит в `ПРОЧТИ.md` рядом с EXE.

Windows ZIP включает Python, FFmpeg/ffprobe и Kling CLI; runtime, медиа, вход Kling, проектные launcher, загрузка модели и распознавание проверены в VM. Модель устанавливается отдельно на любой ОС. Внешние Claude/Codex устанавливаются отдельно; менеджер агентских заданий приложения сейчас поддерживает только Linux.

Автоматическое распознавание на Linux и Windows запускается напрямую с `--allow-network`: флаг снимает проверку OS-изоляции, модель всё равно читается только с диска, скачивание отключено. Настраивать user namespaces или AppArmor для разметки не требуется.

## Запуск и проверки из checkout

Команды выполняются из корня checkout после установки [зависимостей разработчика](#зависимости-разработчика-и-временные-внешние-зависимости):

```sh
yarn install          # зависимости и бинарник Electron
yarn dev              # запуск с горячей перезагрузкой
yarn build            # сборка в build/app
yarn prepare:runtime  # встроенный Python и библиотеки для текущей ОС
yarn smoke:runtime    # проверка переноса runtime без Python в PATH
yarn start            # запуск собранного приложения
yarn typecheck && yarn test
yarn lint             # ESLint по src/ (ошибки и предупреждения не допускаются)
yarn format:check     # Prettier: проверка форматирования; yarn format переформатирует
yarn dist:linux       # AppImage со встроенными Python и FFmpeg, без весов модели в build/release
yarn dist:win         # Windows ZIP, собирается на Linux без Wine
```

Перед коммитом выполняется `yarn typecheck`. Сборка приложения находится в `build/app`, установщики — в `build/release`; обе папки вне Git. AppImage после сборки остаётся в штатной `build/release`: копирование бинарника за пределы репозитория требует явного поручения.

## Устройство и стиль кода

Исходники настольного приложения на Electron, TypeScript, React и MUI лежат в `src/main`, `src/preload`, `src/renderer` и `src/shared`. Главный процесс выполняет работу с файлами и процессами; renderer не обращается к файловой системе напрямую. Новая возможность проходит через функцию главного процесса, IPC и метод в `src/shared/api.ts`. Независимая от Electron логика главного процесса проверяется тестами `src/main/*.test.ts`. Просмотр и редактирование не требуют Python и FFmpeg — они нужны производству.

Страницы находятся в `src/renderer/src/pages/{PageName}/{PageName}.tsx`, экспортируются через `pages/{PageName}/index.ts` и `pages/index.ts`. Публичный `index.ts` страницы экспортирует только её. Внутренние компоненты, hooks, типы и функции остаются в папке страницы; общие для нескольких страниц компоненты — в `src/renderer/src/components`. Один компонент — один файл. Подробные правила, в том числе правила `AgentButton` и PythonLauncher, находятся в [AGENTS.md](../AGENTS.md#приложение).

Правила темы, структуры и компоновки интерфейса собраны в [документации UI](ui/README.md).

Стиль кода приложения задают `.prettierrc.json` (точка с запятой в конце выражения, одинарные кавычки, строки до 160 знаков, пустая строка в конце файла) вместе с `.editorconfig` (UTF-8, LF, отступ два пробела, в Python четыре) и `eslint.config.mjs` (рекомендованные правила ESLint и typescript-eslint, правила хуков React, импорты типов через `import type`); Prettier и ESLint не спорят благодаря `eslint-config-prettier`. Python-инструменты, шаблон и скиллы этими проверками не охвачены.

Стиль Python задаёт `pyproject.toml` (ruff); переформатирование существующего кода выполняется отдельным поручением. Изменение контрактов хранения одновременно вносится в `templates/project` и инструменты; существующие проекты обновляются по поручению. Данные клипов хранятся в отдельных проектах, а не в репозитории комплекса.

## Отладка

Переменные окружения для отладки: `SONGFRAME_LOCAL_DIR` (отдельная папка локального состояния), `SONGFRAME_ROUTE` (стартовый маршрут, например `#/environment`), `SONGFRAME_SCREENSHOT` (путь PNG: снимок окна и выход), `SONGFRAME_KLING_CLI` и `SONGFRAME_PRICING_FILE` (подставной CLI Kling и отдельный файл тарифов для прогонов производства без расхода). Клавиша F12 открывает инструменты разработчика.

## CI и релизы

GitHub Actions: `.github/workflows/ci.yml` на каждый pull request и push в `main` запускает `yarn lint`, `yarn format:check`, `yarn typecheck`, `yarn test` и набор тестов Python (`tools/run_tests`, с ffmpeg и Pillow на раннере). CI также собирает Linux AppImage и Windows ZIP на Linux и сохраняет их как artifacts. Общий шаг `.github/actions/linux-appimage` проверяет переносимый Python и конечный AppImage в Docker; `.github/actions/windows-zip` проверяет состав и целостность ZIP без исполнения Windows-кода. Код не подписывается.

Для выпуска откройте **Actions → Release → Run workflow**, выберите ref/ветку и заполните оба обязательных поля: `version` — `X.Y.Z` без `v` (например, `0.2.0`), `description` — описание релиза. Workflow `.github/workflows/release.yml` заранее проверяет, что номер не занят тегом или релизом, и собирает обе поставки из одного точного SHA выбранного ref. Версия в `package.json` меняется только в сборочных checkout, без автоматического коммита в репозиторий.

Только после успеха обеих сборок отдельная задача публикации создаёт тег `vX.Y.Z` на этот SHA и черновик релиза, прикрепляет AppImage, Windows ZIP, SHA256, отчёты проверок и уведомления о лицензиях, затем публикует релиз. Существующие теги и релизы не перезаписываются. Ошибка сборки не создаёт публичный релиз; ошибка загрузки файлов оставляет черновик для разбора. Нативный Windows smoke в этот процесс не входит: VM-прогоны выполняются отдельно по явному поручению.

`yarn dist:*` подготавливает встроенный Python и включает его, инструменты и шаблон проекта в ресурсы приложения вне ASAR. Ресурсы определяются относительно приложения, путь checkout сборщика в код не записывается. Логи и локальное состояние packaged-приложения хранятся в userData. Системный Python/pip и отдельная установка Python-библиотек пользователю такой сборки не нужны. Подготовка, версии и проверки описаны в [scripts/runtime](../scripts/runtime/README.md).

Linux AppImage и Windows ZIP включают Python и FFmpeg/ffprobe. **Веса модели в поставки не входят:** их нужно один раз скачать по [инструкции по модели распознавания](../README.md#модель-распознавания). Модель хранится отдельно и используется повторно после обновления приложения. Распознавание работает локально на CPU/int8 либо NVIDIA CUDA, без обращения к Hugging Face во время анализа. В Windows VM проверены runtime, FFmpeg/ffprobe, встроенный Kling и вход, проектные launcher, загрузка модели и локальное распознавание; полный производственный цикл требует отдельной нативной приёмки. Официальный Kling CLI хранится в репозитории в `vendor/kling-cli`, входит в поставку и использует Node из Electron. Сборка копирует его из vendor без скачивания из npm. На странице «Среда» сначала проверяется вход: без авторизации доступна кнопка «Войти», при действующей — «Сменить аккаунт»; авторизацию сохраняет сам CLI в штатной папке `.kling` пользователя, приложение не создаёт отдельного хранилища токенов. Git устанавливается отдельно и необязателен для локального проекта и рабочих представлений, но нужен для истории/индекса; для Kling не нужны системные Node.js/npm и отдельная установка CLI. Внешние Claude/Codex по-прежнему устанавливаются отдельно. Проверка встроенного runtime не подтверждает доступность внешних провайдеров и всех производственных операций: их проверяют отдельно в пользовательском окружении. `yarn build` обновляет только `build/app`; для нового AppImage выполняйте `yarn dist:linux`.

### Проверка Linux AppImage и выпуск

`yarn dist:linux` собирает конечный файл в `build/release`. Веса модели не включаются. Сборщику нужны Node.js/Yarn, tar и zstd; пользователю готового приложения системные Python, Node.js, Yarn и FFmpeg не нужны. Для графического приложения остаются обычные библиотеки Linux-десктопа и шрифты, в частности DejaVu Sans для карточек.

Существующие CI и Release используют общий шаг `.github/actions/linux-appimage`: сборка, проверка переносимого Python и smoke **конечного AppImage** в Ubuntu 22.04. Контейнер содержит графические библиотеки, виртуальный экран и espeak-ng для синтеза короткой тестовой речи; Python/Node/Yarn/Git/FFmpeg в ОС не устанавливаются. Сеть при запуске контейнера отключена. Загрузка тестовой tiny-модели происходит заранее в отдельный сборочный каталог `build/runtime/smoke-model`, за пределами упаковываемого runtime. Это техническая фикстура CI, а не выбранная пользователем модель.

Локально ту же проверку можно запустить с Docker и любой заранее скачанной моделью CTranslate2:

```sh
yarn prepare:smoke-model
yarn smoke:appimage --docker --model="$PWD/build/runtime/smoke-model" --output=/tmp/songframe-appimage-check
```

Для повторного прогона используйте новую папку отчёта. Smoke создаёт собственный проект с пробелами/кириллицей, загружает MP3, размечает его внешней моделью, сохраняет подтверждённую строку, строит каркас сцен/карточки и проверяет рабочую папку. Затем переносит проект, временно переименовывает AppImage **внутри build/release**, проверяет повторный запуск/launcher/состояние и возвращает файл на штатное место. Пользовательские проекты и текущий выбор не используются. Окна приложения, платные запросы и внешние агентные CLI не запускаются.

Контейнер использует extract-and-run, поскольку FUSE в нём недоступен; `--no-sandbox` задаётся только этому проверочному запуску. Настройки sandbox обычного приложения не меняются. `NO_CLEANUP` сохраняет распаковку до удаления контейнера для вложенного запуска launcher; служебный вывод загрузчика не принимается за JSON самого инструмента. На обычном Linux основной вариант — прямой запуск AppImage. Если FUSE недоступен, поддерживается [официальный extract-and-run](https://docs.appimage.org/user-guide/troubleshooting/fuse.html#extract-and-run-type-2-appimages). Работа на произвольном старом дистрибутиве или CPU не обещается: Python-wheels/FFmpeg требуют glibc 2.28+, Linux x64 и совместимый CPU; целевая базовая проверочная ОС — Ubuntu 22.04, локальная — Ubuntu 24.04.

Перед упаковкой проверяется состав ресурсов и отсутствие весов/репозиторных тестов, сохраняются версии и уведомления поставщиков. Лицензии CPython и статических зависимостей извлекаются из полного архива того же выпуска python-build-standalone; недостающие в wheels тексты FlatBuffers/tokenizers закреплены URL и SHA256. В готовом приложении есть `resources/distribution.json` и `resources/THIRD_PARTY_LICENSES.md`, рядом с AppImage — их копии. После успешного smoke появляются `<имя>.AppImage.sha256` и `linux-smoke-result.json`; Release прикладывает эти файлы вместе с проверенным AppImage. Для Windows ZIP общая сборка CI/Release создаёт `<имя>.zip.sha256` и `windows-archive-check.json`: проверяются CRC, ресурсы и целевая платформа архива, без нативного Windows smoke. Публикация разрешена только после успеха обеих сборок и проверок.

## Перенос приложения, состояние и проекты

На Linux настройки, текущий проект, история и журналы находятся в `${XDG_CONFIG_HOME:-$HOME/.config}/songframe` — постоянном userData, общем для разработки и AppImage. Файлы: `settings.json`, `current-project.json`, `projects.json`, журналы в `jobs/`. Они сохраняются после перемещения или обновления AppImage. Ресурсы `tools`, `templates`, `runtime` читаются из приложения, записи в каталог AppImage и временный mount не нужны. Файлы моделей хранятся отдельно в каталоге данных по [инструкции по модели распознавания](../README.md#модель-распознавания).

Повреждённый JSON не сбрасывается молча: сообщение указывает файл, его нужно исправить или перенести в резервную папку. Запись настроек и выбора проекта атомарная, при ошибке сохранения прежний файл остаётся целым.

`SONGFRAME_LOCAL_DIR` явно задаёт другую папку для `settings.json`, выбора, истории и журналов — например отдельную постоянную папку рядом с AppImage. Папку рядом с исполняемым файлом приложение само не выбирает: это может быть временная распаковка. Путь к каталогу состояния виден на странице «Среда»; ошибка доступа на запись показывает путь и причину. Интерфейсные предпочтения Electron (например, тема) хранятся в его userData.

Открытие проекта (включая восстановление выбранного проекта при запуске) обновляет управляемые памятки `AGENTS.md`/`README.md`, известные записи схем в `.vscode/settings.json` и служебную папку `.songframe`. В управляемых памятках приведены команды и для Linux, и для Windows: смена ОС не переписывает одну инструкцию в другую. Пользовательский текст вне управляемых памяток, остальные настройки, комментарии JSONC и завершающие запятые сохраняются. В проекте без управляемых маркеров чужие правила и конфигурация не изменяются. Файлы `source`, реестры сцен и материалы `assets` при обновлении не переписываются.

В новых проектах команды и ссылки относительные. `.songframe` содержит короткую памятку, справочники инструментов/скиллов, схемы и launcher; полный README приложения, Python и исходники инструментов туда не копируются. Эта папка исключает себя из Git и может быть восстановлена открытием проекта. Из корня проекта на Linux:

```sh
./.songframe/run-tool check_workspace --json
./.songframe/run-tool update_scene_views --check
```

В Windows из PowerShell или CMD используются `.\.songframe\run-tool.cmd check_workspace --json` и `.\.songframe\run-kling.cmd --version`. Launcher сам определяет папку клипа, передаёт её Python-инструменту и вызывает постоянный файл приложения: AppImage на Linux либо EXE на Windows. В dev используется установленный Electron с текущим checkout. Если приложение или проект перемещены, откройте проект заново — приложение обновит launcher. Если проект скопирован другому пользователю, сделайте то же самое. Старая запись истории с отсутствующим путём сохраняется: её можно забыть в списке проектов, а перенесённую папку открыть заново.

Есть и прямой режим без окна, использующий тот же встроенный Python:

```sh
"/путь/к/SongFrame.AppImage" --songframe-tool check_workspace --project "/путь/к/клипу" --json
```

Выбор проекта в прямом CLI сохраняет прежний порядок: `--project` → `SONGFRAME_PROJECT` → файл текущего проекта → cwd с `plan/project.json`. При открытии проекта на другой ОС приложение заменяет служебные launcher и обновляет служебные справочники и управляемые навыки под неё. Памятки проекта содержат инструкции для обеих ОС; неизвестные файлы и пользовательские правила сохраняются.

Настройки приложения — обычный `settings.json` в локальном каталоге состояния: Linux `${XDG_CONFIG_HOME:-~/.config}/songframe`, Windows `%APPDATA%\songframe`. `SONGFRAME_LOCAL_DIR` явно задаёт другую папку; фактический путь виден на странице «Среда». Авторизация Kling хранится отдельно штатным CLI в `~/.kling/.credentials` (Windows — `%USERPROFILE%\.kling\.credentials`); приложение не заводит второе хранилище токенов.

### Свежесть производных файлов

Карточки сохраняют значимые поля `project_inputs: {name}`, а полный аниматик — `{name, animatic_video}`. Настройки генерации не являются входами уже созданных документов, карточек и видео. Сохранение настроек проекта не запускает Python и не рендерит карточки. `source_hashes` содержит только фактически использованные медиа; полный файл `project.json` в него не входит.

Это единственный формат квитанций и манифестов. При изменении контракта данные рабочего проекта и тестовых фикстур приводятся к нему отдельно; чтение не выполняет скрытую миграцию и не ищет прежние версии в Git. Отсутствующий или повреждённый `project_inputs` считается ошибкой данных.

### Настройки агента

Кнопка «Сохранить» в настройках агента отдельно записывает выбор в общий `settings.json` в постоянной папке состояния. Пример блока без секретов:

```json
{
  "agent": {
    "provider": "codex",
    "model": "идентификатор-выбранной-модели"
  }
}
```

Старый файл без `agent` означает «Без агента»; этот вариант также можно выбрать в форме. Остальные поля, включая `toolsRootOverride`, сохраняются. Выбор текстового агента не меняет проектные `generation.video` и `generation.image` и файлы проектов.

## Модель распознавания из терминала

### Linux

Для готового приложения не нужны системные Node.js, Yarn, Python, pip или отдельный загрузчик hf. Для ручного запуска откройте проект в приложении, затем терминал **в папке этого проекта** и выполните команду ниже. Она вызывает встроенный загрузчик через проектный launcher. Пример для medium:

```bash
./.songframe/run-tool download_whisper_model --repository Systran/faster-whisper-medium --output "${XDG_DATA_HOME:-$HOME/.local/share}/songframe/models/faster-whisper-medium"
```

Если приложение рекомендует large-v3, замените в команде репозиторий на `Systran/faster-whisper-large-v3` и имя конечной папки на `faster-whisper-large-v3`. Для turbo используйте `dropbox-dash/faster-whisper-large-v3-turbo` и папку `faster-whisper-large-v3-turbo`. Кнопка в приложении сама учитывает выбранную модель.

### Windows

В готовый Windows ZIP уже входят Python и библиотека для скачивания модели. Отдельные Python, pip, hf, Node.js и Yarn не нужны. Для ручного запуска откройте проект в приложении, затем PowerShell **в папке этого проекта** и выполните команду ниже. Пример для medium:

```powershell
$modelDir = Join-Path $env:LOCALAPPDATA 'songframe\models\faster-whisper-medium'
.\.songframe\run-tool.cmd download_whisper_model --repository Systran/faster-whisper-medium --output $modelDir
```

Другую модель выбирайте по [таблице моделей](../README.md#модель-распознавания), меняя репозиторий и имя конечной папки. Кнопка в приложении сама учитывает выбранную модель и её папку. Права администратора для папки модели не нужны.

На обеих ОС [download_whisper_model](../tools/download_whisper_model/README.md) скачивает комплект целиком и показывает прогресс в терминале. Повторный запуск использует уже скачанные файлы. Если загрузка прервалась, повторите ту же команду.

Если medium уже есть от прежней сборки в `build/runtime/linux-x64/models/faster-whisper-medium`, можно перенести её в каталог данных или просто выбрать эту папку — скачивать заново не обязательно. Загрузка и выбор папки через приложение описаны в [инструкции по модели распознавания](../README.md#модель-распознавания).

Модель загружается только с диска: `local_files_only`, `HF_HUB_OFFLINE` и отключение телеметрии сохранены. Устанавливать unshare и менять AppArmor не нужно. Переменная `SONGFRAME_MODEL_DIR` задаёт внешнюю модель для ручного CLI; параметр `--model` имеет приоритет.

Любой инструмент принимает `--project <папка>` вместо выбранного проекта; подробности в [карте tools](../tools/README.md).
